# Experimental Rust API

All Rust service binaries require hostname- and certificate-verified PostgreSQL TLS by default. `NOVU_POSTGRES_CA_FILE` adds a PEM CA bundle. `NOVU_POSTGRES_ALLOW_INSECURE=true` forces plaintext and is only for disposable local fixtures. See the [TLS test](scripts/test-postgres-tls.sh); client-certificate authentication and production deployment remain incomplete.

The bounded SendGrid delivery webhook requires API migration `0004` and an environment-specific Base64 DER P-256 public key inserted in `novu_rust_sendgrid_webhook_keys`. It verifies signed raw requests and records minimal deduplicated delivery evidence. It is not the full Novu webhook contract or automatic delivery reconciliation; see the [implementation status](../../../RUST_IMPLEMENTATION_STATUS_KO.md) for privacy, retention and deployment limitations.

Apply API migrations `0008`–`0009` and worker migrations `0057`–`0058` before deploying the updated API. Signed SendGrid webhook batches lock associated email jobs in ID order before recording evidence. A signed `swallow_dispatch_id` is associated only when the same job and environment contain a matching hash for the accompanying `swallow_dispatch_proof`. The raw proof is never stored in PostgreSQL; protect provider access and logs because possession permits replay. Email retry decisions and workers check this evidence under the job lock to avoid resending a request already observed by SendGrid. The API database role needs queue row-lock privileges; email workers and the operator tool need read access to the event and audit tables. Legacy and unmatched events are not associated with individual dispatch attempts, and callbacks received after dispatch begins cannot cancel it.

The optional Twilio status webhook uses migration `0005` and the four environment variables `NOVU_TWILIO_WEBHOOK_ENVIRONMENT_ID`, `NOVU_TWILIO_WEBHOOK_ACCOUNT_SID`, `NOVU_TWILIO_WEBHOOK_URL` and `NOVU_TWILIO_WEBHOOK_AUTH_TOKEN`. The configured URL must be the exact public HTTPS callback without query parameters. It validates Twilio form signatures and stores deduplicated status evidence without phone numbers; it does not resolve unknown jobs or update delivery state. Migration `0006` enables a signed `/jobs/{job-uuid}` suffix, and `0007` with worker migration `0055` enables `/jobs/{job-uuid}/attempts/{dispatch-uuid}` to bind evidence to an individual dispatch. Set the worker's `NOVU_TWILIO_STATUS_CALLBACK_BASE_URL` to exactly the same base URL to opt in; explicit message callbacks take precedence. `delivery-reconcile sms-evidence ENV JOB` displays linked evidence; SMS retry decisions also require read access to that event table and refuse matching or ambiguous evidence already present. A callback does not itself resolve a job or prove user receipt. New callbacks include a dispatch ID; legacy job-only and explicitly configured callbacks may not identify an individual attempt. During the retry interval, a same-environment retry audit record serves as evidence that an attempt existed. Apply worker migration `0054` and grant the API database role read access to the attempt and reconciliation tables. Deleting the job or audit record removes this legacy fallback; deleting the job also removes its dispatch IDs. The API DB role must also read the dispatch-ID table and have permission to lock queue rows (`SELECT` plus `UPDATE` privilege on the queue table). Job-linked callbacks lock the job to serialize with dispatch checks. One account/environment per API process is supported. The token requires a proper secrets mechanism and the endpoint still needs an external HTTPS boundary. See the implementation status for limits.

This is an incomplete, isolated implementation for comparison with Novu at commit `895388f37efe9e06de0aa333e5727303e6ad6853`. **It is not a production service or a drop-in Novu replacement.** The fixture schema is not a migration from Novu and neither an API-key management endpoint nor a workflow management endpoint exists.

`POST /v1/events/trigger` has a limited path for `Authorization: ApiKey …`, SHA-256 key lookup scoped to an environment with an associated-user existence check, recipient validation, and the missing, inactive and no-step stored-workflow outcomes. Fixture workflows support limited in-app, manually configured SendGrid email, and Twilio SMS steps for supported string and object recipients: the API enqueues a job and the experimental Rust worker creates or updates subscribers and messages in PostgreSQL. The message may contain simple Handlebars-style paths resolving to strings, booleans, safe integers or missing values. Other active workflows and unsupported trigger options return 501. `processed` means the job was accepted, not that a message was delivered; the worker must run separately.

`GET /v2/subscribers/:subscriberId` retrieves experimental subscribers within the API key's environment, exposing stored profile fields, timestamps and selected channel/online fields. Selected channel credentials and presence state are implemented; complete channel and subscriber management contracts remain incomplete.

By default the Rust Inbox guard requires the JWT `_id` to match the current subscriber internal ID. Setting `NOVU_ALLOW_RECREATED_SUBSCRIBER=true` restores the original Inbox guard, which resolves by environment and external subscriber ID without matching `_id`. The reference comparison confirms an old unexpired token is rejected after deletion but can access the recreated subscriber after the same external ID is reused. Reusing IDs for different people can therefore expose the new Inbox to the previous token holder. The reference WS gateway instead routes using the token `_id`; Rust follows the original API behavior only in compatibility mode; the WS gateway still uses the token `_id`. Complete token revocation and session policy are not implemented.

Migration `0050` stores the internal subscriber identity on in-app messages and scopes Inbox, WS and deletion operations to it. Legacy rows use the linked notification identity if available, otherwise the current subscriber identity at migration time; prior ownership cannot be reconstructed when that link is missing. The migration drops the external-ID foreign key, allowing historical orphan messages, and changes the idempotency index to internal identity. Back up and validate existing data before migration; retention of historical orphans is not implemented. The reference comparison covers selected count, bulk read and deletion cases after external-ID reuse.

Subscriber deletion also removes experimental email, SMS and push message history scoped to the environment and the deleted internal subscriber ID. Apply worker migrations through `0049` for the corresponding cleanup indexes; each history insert adds an index write. The original-server race comparison covers deletion during a push attempt and verifies preservation of other internal IDs and environments; complete message and connection deletion semantics and arbitrary concurrency remain incomplete or unverified.

Migration `0051` supports manually configured multiple FCM integration identities and per-integration device tokens. A named integration selects that identity; otherwise the most recently created active integration is selected. Individual and paged subscriber reads expose the channels in registration order, and provider deletion removes all FCM channels. The reference comparison covers selected API operations and mocked multi-integration delivery; integration management APIs and complete routing are still incomplete.

The trigger accepts a limited legacy `overrides.fcm` object: nonempty `deviceTokens` string arrays, string-valued `data`, and `type` of `data` or `notification`. Global and step-specific `providers.fcm` also accept selected data and notification fields after migration `0052`. The [worker README](../../worker/rust-queue/README.md) describes the compared behavior and remaining routing and provider limitations. These values are stored in PostgreSQL job payloads.

Experimental FCM-only `PUT` and `PATCH /v1/subscribers/:subscriberId/credentials` replace or append deduplicated device tokens, respectively, while an empty array clears them. `DELETE /v1/subscribers/:subscriberId/credentials/fcm` removes the channel. Apply worker migrations through `0054` and create a fixture row in `novu_rust_fcm_integrations` for the environment; this is not an integration management API or production credential store. A fixed maximum of 100 tokens is enforced per integration channel; the reference can change this limit using a feature flag. Selected over-limit errors include the deduplicated count and limit as in the reference. Deleting an already absent FCM channel still updates the subscriber timestamp. The reference harness compares selected credential operations, v2 subscriber list channels across two pages, the same external ID in two environments, and subsequent mocked push delivery. Repeated PUT/PATCH requests with the same deduplicated tokens preserve `updatedAt`; a PATCH containing only a subset can still update it, matching selected reference cases. Other providers, full integration management, complete validation and broader timestamp behavior remain incomplete or unverified. Device tokens are stored in PostgreSQL, individual subscriber responses perform a separate channel lookup, and nonempty list pages perform one batched channel lookup scoped to the environment. Concurrent channel updates during pagination are unverified. A no-op or conflict performs an extra read; a conflicting update can be retried up to four times before returning an internal error.

`POST /v2/subscribers` supports creating or updating subscribers with selected `firstName`, `lastName`, `email`, `phone`, `avatar`, `locale` and `data` values, and limited `failIfExists` values. Basic subscriber ID validation and trimming are supported; unsupported fields and full validation are incomplete. An omitted or null `data` becomes an empty object, which GET and POST responses omit; PATCH can return an explicitly supplied empty object. The operation is scoped to the authenticated environment; this is not a complete subscriber management API.

`PATCH /v2/subscribers/:subscriberId` supports partial updates of selected `firstName`, `lastName`, `email`, `phone`, `avatar`, `locale` and `data` values, including explicit nulls and replacement of the whole `data` object. Invalid types for these fields return a limited 422 validation response; unsupported fields return 501. Full Novu input validation and permissions are not implemented. The update is scoped to the authenticated environment and serializes concurrent updates to one subscriber.

`DELETE /v2/subscribers/:subscriberId` deletes an environment-scoped experimental subscriber, their experimental in-app messages, implemented preferences and topic memberships atomically. The deletion covers selected experimental endpoints and connection records; other Novu deletion side effects and all queued-job semantics remain incomplete.

`GET /v2/subscribers/:subscriberId/notifications/count` supports JSON `filters` arrays with `read`, `seen`, `archived` and `snoozed` booleans or null, tag arrays, `{or: [...]}`, and `{and: [{or: [...]}, ...]}`, and the reference's 100-per-filter maximum. Count filters also support `severity` as a valid string, array, empty array, or null; `0032_experimental_message_severity.sql` is required. Other query options are not implemented; unsupported input, including invalid tag or severity filters, is rejected with 501 rather than the reference validation error. Messages written by the experimental worker start unread, unseen and unarchived.

`POST /v2/subscribers/:subscriberId/notifications/read`, `archive` and `read-archive` update the experimental message states and timestamps. Empty bodies, tag filters and bounded data filters are supported; management `contextKeys` select messages with any overlapping key; an empty array does not restrict the operation. They publish a best-effort unread count refresh for the experimental WS service; webhooks, analytics and interaction traces remain unsupported.

`POST /v2/subscribers/:subscriberId/notifications/seen` supports all messages, tag and bounded data filters, or a list of 24-hex message IDs; IDs take precedence over filters and an empty list is a no-op. A nonempty operation publishes a best-effort unseen count refresh. Management `contextKeys` can be combined with IDs and match overlapping keys; webhooks and trace side effects are not supported. Migration `0005` assigns deterministic IDs to old prototype rows; these IDs are not imported from an existing Novu database.

`GET /v2/subscribers/:subscriberId/notifications` exposes experimental messages and IDs using `read`, `seen`, `archived`, and single or repeated `tags` OR filters, `limit`, `offset`, and a same-environment `after` cursor. Nested and bracketed tag query forms are not implemented. Each referenced experimental workflow must have `inbox_metadata` set; for example: `{"id":"64a000000000000000000004","identifier":"greeting","name":"greeting","critical":false,"tags":[],"severity":"none","payloadAsData":true}`. `payloadAsData` controls the original V0-style payload mapping and is not returned in the DTO. Missing metadata, unsupported options and unsupported severity return 501. Tags are captured at trigger time; historical data created before migration `0006` lacks delivery timestamps and has empty tags. This is not a complete Inbox implementation or a Novu data migration.

With `JWT_SECRET` configured, the experimental `/v1/inbox/notifications` list, count, individual read/unread/archive/unarchive/snooze/unsnooze/delete and bulk seen/read/archive/read-archive/delete routes accept an HS256 subscriber JWT. Signature, `widget_user` audience, expiration and not-before are verified, and the subscriber is rechecked within the token's environment. Lists, counts and individual mutations require the exact session context key set. As in the reference, bulk mutations match any overlapping context key, and an empty context applies no context filter: a bulk operation can therefore affect other contexts for the same subscriber. Stored `snoozed_until` values are reflected in lists, counts and individual mutation responses; the manual unsnooze endpoint clears existing snoozed state and preserves read status. Snooze creates a delayed job atomically with message state, and manual unsnooze cancels one matching pending job. Full context handling, complete snooze input and plan semantics, actions, the complete WebSocket contract and user JWT authentication remain unimplemented; subscriber tokens do not authorize `/v2/subscribers` or trigger APIs. Mutations publish bounded best-effort count events; full event, webhook and trace behavior remains unsupported. The secret must match the issuing server and must be managed securely.

The experimental `POST /v1/inbox/session` requires `0002_experimental_inbox_session.sql` and an explicit `novu_rust_inbox_environments` row with application identifier, active in-app status, HMAC policy and response settings. `JWT_SECRET` signs a 15-day subscriber token. When HMAC is required, `INBOX_HMAC_KEYS_JSON` must contain an environment-ID-to-array-of-plaintext-key mapping in the process environment; only keys whose SHA-256 hashes are present and enabled in `novu_rust_api_keys` for that environment are accepted. No HMAC key is written to the database or returned. With HMAC disabled, an existing subscriber's profile is updated only if a valid HMAC is supplied. An HMAC-enabled environment with no configured keys fails closed. This is test configuration, not a production secrets-management or migration solution. String and rich context values with restricted ASCII type and ID are supported. Session creation preserves existing context data; accepted triggers replace explicitly supplied data. A separate context HMAC is checked when required; integer-valued JavaScript binary64 numbers, including large values, are supported for signing. Noninteger signing remains unsupported, and large-number storage and all numeric edge cases are not fully verified. Simple in-app template expressions can use `context.<type>.id` and `context.<type>.data`; the worker reads the latest environment-scoped data at processing time, adding one query per job with context. Workflow conditions and full channel behavior remain unsupported; limited email and SMS steps also use selected context expressions. Default schedules, keyless operation, real integration selection, configurable JWT lifetime, complete validation and side effects are not implemented. Context persistence requires worker migrations `0010_experimental_context.sql`, `0011_experimental_context_data.sql`, `0012_experimental_context_timestamps.sql`, and `0013_experimental_context_cursor.sql`; existing messages default to empty context. Selected context session, HMAC and worker delivery cases were compared against the reference server; the full context contract remains unverified.

`DELETE /v2/subscribers/:subscriberId/notifications/:notificationId` deletes one experimental in-app message, scoped to the API key's environment and subscriber. `POST /v2/subscribers/:subscriberId/notifications/delete` deletes all or tag- and data-matched messages for that subscriber; context filters are rejected. Both publish a best-effort unread count refresh; webhooks, analytics and traces remain unsupported.

Apply migrations `0008` and `0009` after `0007`: Inbox message `data` is stored separately from trigger `payload`, and list and bulk endpoints accept JSON-string `data` filters with scalar, OR and AND groups and up to two levels of objects. Some MongoDB array traversal, missing-field and numeric path behavior is supported and compared against MongoDB, but the full range of MongoDB array and BSON semantics remains unverified. Invalid structures return 501 rather than the reference validation error. Existing prototype rows have no historical `data`; the experimental worker currently does not populate it from a workflow result. Query performance at scale is untested.

`PATCH /v2/subscribers/:subscriberId/notifications/:notificationId/{read,unread,archive,unarchive}` updates an individual experimental message and returns its Inbox DTO. Context filters and complete Socket.IO, webhook, analytics and trace behavior are not supported; selected best-effort count events are implemented. Apply worker migration `0007` after `0006`: it records whether read and archive dates are absent or explicitly null. Historical nulls lost before this migration cannot be reconstructed.

Subscriber create, patch and the experimental trigger accept null and a conservative ASCII subset of email addresses; the in-app renderer supports `subscriber.email`. Quoted or non-ASCII addresses return 501, and invalid trigger email errors do not yet match Novu. A separate experimental SendGrid email workflow and worker exist; see the worker README for their configuration and limitations.

This is a narrow prototype, not a compatible Inbox: the message list supports only a subset of DTO fields and filters, and complete snooze semantics and action APIs, full real-time delivery, full Handlebars support, complete preferences, integration selection, conditional steps, full topic behavior, and complete trigger handling for timezone and channel credentials remain missing or unverified. Template expressions with helpers, blocks, floating-point numbers, unsafe integers, arrays and objects are rejected; branding is limited to the default color. User JWT/OAuth, complete subscriber sessions, user membership and role-based permission checks, tenant overrides, validation error details, payload schemas, rate limits, complete external channels, API/SDK coverage, and many other behaviours are not implemented. Its transaction ledger retains keys indefinitely; this differs from Novu's tier-dependent retention and has not been verified against its duplicate-trigger semantics. Generated transaction IDs use the reference timestamp-and-base36 format; collision and cross-runtime behavior have not been validated against the running reference service. The prototype database connection uses `NoTls` and must not be exposed as a production configuration.

## Verification

- `cargo test --locked`: unit tests and a differential test which extracts the original TypeScript recipient-validation function from the current checkout, executes it with Node.js type stripping, and compares a bounded fixture set with the Rust function. This tests that function only, not the original HTTP server. Requires Node.js with `--experimental-strip-types` support.
- `./scripts/test-postgres.sh`: starts a disposable PostgreSQL 17 Docker container bound to a random loopback port, runs HTTP-router + database integration tests (including queue, worker, subscribers and static in-app messages), and removes the container. The test asserts selected results from original Novu source/e2e tests; it does not run the original server.
- `tests/reference_http_compare.py` and `tests/reference_in_app_compare.py` compare selected HTTP cases and one in-app delivery with separately running, equivalent **disposable** original and Rust environments; their docstrings list required environment variables and fixtures. The in-app test creates a synthetic subscriber and message on both sides. These tests do not establish full compatibility.
- `tests/reference_subscriber_compare.py` compares four subscriber retrieval/authentication cases when equivalent disposable fixtures and both servers are available; error timestamps are checked for format but not equality.
- `tests/reference_subscriber_workflow_compare.py` compares trigger responses, selected message fields and subscriber retrieval after creation, update and clearing of profile properties with both workers running. See its docstring for fixture requirements; generated subscriber IDs and timestamps are excluded from response comparison.
- `tests/reference_subscriber_patch_compare.py` compares a bounded PATCH and GET sequence using separately running disposable original and Rust servers with equivalent seeded fixtures. It checks each PATCH's response timestamp against its own preceding GET and excludes independently assigned update times from cross-server equality.
- `tests/reference_subscriber_create_compare.py` compares a bounded POST and GET sequence on disposable original and Rust servers; it creates synthetic subscribers and excludes independently generated IDs and timestamps from cross-server equality.
- `tests/reference_subscriber_delete_compare.py` compares deletion, message and subscription cleanup, orphaned subscription preference cleanup, other subscriber/environment preference isolation, and recreation on disposable servers; the original MongoDB must support transactions. Channel resources, concurrent deletion and queued jobs are not compared.
- `tests/reference_notification_count_compare.py` compares selected count filters, errors and the cap on equivalent fixture messages, and mutates disposable databases and flushes the dedicated Redis instance. The in-app workflow comparison also exercises the count API after both workers run.
- `tests/reference_notification_bulk_compare.py` compares unfiltered bulk transitions, selected stored states and timestamp-presence rules, counts and errors; it does not compare events or webhooks. The workflow comparison also exercises these transitions after both workers run.
- `tests/reference_notification_seen_compare.py` compares selected and all-message seen operations, input errors and subscriber isolation with equivalent fixtures. The workflow comparison also marks each worker-generated message seen by its own generated ID.
- `tests/reference_notification_list_compare.py` creates three notifications through both original and Rust workers and compares bounded listing, payload, filters, cursor and offset pagination, four individual state changes and resulting DTOs and lists. It then assigns equivalent tags directly in each disposable database and compares selected tag list, count and bulk operation filters. Generated identifiers and timestamps are checked for format but excluded from cross-server equality. It does not compare realtime events or webhooks.
- `tests/reference_data_array_compare.py` compares selected dotted-path, array, null and numeric-index matching cases directly against a disposable MongoDB and PostgreSQL. It requires migrations `0008` and `0009` in the PostgreSQL fixture and does not test the full API contract.
- `tests/reference_inbox_session_compare.py` compares selected session and HMAC cases and cross-checks issued JWTs against both disposable servers. It changes the dedicated reference integration and flushes its Redis; do not run it against shared services. `tests/reference_sdk_smoke.cjs` runs the reference-built `@novu/js` session, list and count against the Rust server and creates a subscriber.
- `tests/reference_notification_delete_compare.py` compares individual and unfiltered bulk deletion, errors, counts and subscriber isolation using disposable fixtures. The workflow listing comparison also deletes worker-generated messages and compares the resulting lists. Neither compares deletion events or webhooks.
- `cargo fmt --check` and `cargo clippy --all-targets -- -D warnings`.

The DB test drops and recreates its experimental queue, subscriber, message, transaction, workflow, and API key tables. If running it manually, use **only a disposable database**:

```sh
TEST_DATABASE_URL='postgresql://USER:PASSWORD@localhost:5432/DISPOSABLE_DATABASE' \
  cargo test --locked --test api_postgres -- --ignored
```

The API binary requires `DATABASE_URL` and defaults to listening on `127.0.0.1:3000` (`LISTEN_ADDR` overrides it). The worker can be started with `cargo run --manifest-path ../../worker/rust-queue/Cargo.toml --bin in-app-worker`, with the same `DATABASE_URL`. Neither creates schema or seeds data. Apply the experimental API migration and queue migrations `0001`–`0058` in order to an empty disposable database. For an existing experimental schema, apply any missing queue migrations before starting the new API and worker. These files are not a production migration system or a MongoDB migration. The worker recovers expired leases for its in-app job kind; database errors terminate the process.

`tests/reference_context_query_compare.py` runs isolated MongoDB and PostgreSQL containers to compare the original exact-read and bulk-overlap query predicates, including legacy missing context and environment isolation. It is a database predicate comparison, not a full Novu server or SDK test.

Experimental API-key `POST /v2/contexts` and `GET`, `PATCH`, `DELETE /v2/contexts/:type/:id` support environment-scoped context CRUD and replace data on update. List supports type, id and literal case-insensitive search, created/updated ordering and forward/backward cursor pagination, with a maximum supported page size of 1,000. PostgreSQL-generated cursor IDs cannot be exchanged with MongoDB cursors; cross-database migrations and complete cursor edge cases are unverified. Bridge URLs and SSRF checks, user JWT permissions and exact validation errors are not implemented. Existing context timestamp history cannot be recovered by migration 0012. Selected CRUD, search and forward/backward cursor cases have been compared against the reference API; generated timestamps and cursor values differ independently.

`tests/reference_context_session_compare.py` compares selected rich-context sessions, HMAC, cross-server JWTs and unread counts using directly seeded messages. It changes the disposable integration HMAC policy and flushes Redis; never run against shared services. It does not verify worker delivery or realtime events.

To compare integer HMAC serialization with the reference package, set `NOVU_CANONICAL_JSON` to its installed `@tufjs/canonical-json` package path and run `cargo test integer_formats_match_reference -- --ignored`.

Subscriber `locale` is accepted on create, PATCH, Inbox session profiles and trigger recipients and is exposed as `subscriber.locale` to the limited in-app renderer. Selected locale grammar cases are compared to validator.js 13.15.26 by `tests/reference_locale.rs` in the worker crate. Values longer than 1,024 bytes are rejected, unlike the reference. Localization itself and timezone-based scheduling are not implemented.

Subscriber `timezone` is accepted in the same paths as locale. Validation uses a checked-in Node 22.23.4 / ICU 78.3 generated name/alias set plus numeric offsets; other runtime and time-zone data versions may differ. The generator is `apps/api/rust-contracts/tools/generate-timezones.cjs`, and the worker crate has an ignored Docker differential test `reference_timezone`. This does not implement timezone-aware scheduling or conversion.

`NOVU_REFERENCE_SOURCE=/absolute/path/to/built/reference ./scripts/test-reference-subscribers.sh` starts disposable reference API, MongoDB, Redis and PostgreSQL, then runs selected subscriber create/PATCH HTTP comparisons, including locale and timezone. It requires the reference API build and Docker images already present, uses synthetic credentials, and cleans up its own containers. It does not test worker delivery or SDKs.

Experimental `GET /v2/subscribers` supports exact email/phone/subscriber ID filters, case-insensitive literal name search, `_id`/`updatedAt` ordering and forward/backward cursors, with a maximum supported page size of 1,000. New subscriber IDs use a shared PostgreSQL-backed timestamp/prefix/counter generator to preserve sequential creation order. Existing IDs are unchanged; MongoDB uses a process-specific prefix, so cross-process ordering can differ; data migration, concurrent pagination, Unicode case folding and full fields/permissions are unverified. `tests/reference_subscriber_list_compare.py` compares selected filters and updated-time pagination against the original API and is included in the disposable reference runner.

Apply worker migration `0014_experimental_subscriber_objectid.sql` before starting the API and worker. It retains existing subscriber IDs, adds an environment/ID uniqueness index, and adds a shared ID generator. Existing duplicate IDs can prevent the index from being created. The generator reads one tiny identity row per subscriber upsert and its sequence cycles after 24 bits; clock rollback, sequence wrap, multi-process ordering against MongoDB and large-scale load have not been verified.

Experimental global subscriber preferences require worker migration `0015_experimental_global_preferences.sql`. `GET/PATCH /v2/subscribers/:id/preferences` and `GET .../preferences/global` cover the single-in-app workflow subset. The worker reads the global in-app setting once per recipient, and subscriber deletion cascades the settings. The API was compared against a reference fixture with one in-app workflow and no workflow-resource preference; a bounded original-worker comparison covers disabled global in-app with a normal and an explicitly read-only workflow. Migration `0016_experimental_workflow_preferences.sql` adds manually configured workflow-resource read-only, all-enabled and in-app-enabled fields; important workflows are not automatically mapped to these settings. Subscriber/workflow in-app overrides are supported with migration `0017_experimental_subscriber_workflow_preferences.sql`; user/workflow precedence, schedules, context-specific settings, webhooks and realtime events remain unsupported. Migration `0018` stores a per-recipient `canceled`/`preference` result when delivery is skipped, independently of the completed batch queue job. These results survive subscriber deletion and are not the full Novu jobs model or API; historical outcomes are not backfilled.

Set `NOVU_TEST_PREFERENCE_DELIVERY=1` when running `scripts/test-reference-subscribers.sh` to compare the bounded preference delivery flow with the original worker. `NOVU_REFERENCE_GENERIC` can also point to the built reference application-generic package for `cargo test --test reference_preference -- --ignored` in the worker crate.

Workflow-specific subscriber in-app preferences support workflow identifier, internal ID and a provided slug; the original API and worker were compared for selected override, global reset, critical rejection and delivery cases. Workflow metadata must include ID, name and critical flag; automatic slug generation is limited to simple lowercase ASCII names, otherwise a slug must be supplied. Multi-workflow ordering, complete validation and other preference types remain unverified.

Migration `0019` adds subscriber online state. API-key `PATCH /v1/subscribers/:id/online-status` updates it, records the current time on offline updates, and preserves that time on online updates; v2 subscriber reads and lists expose the state. This does not implement Socket.IO connection tracking or real-time presence. Historical state is not migrated from MongoDB. The v1 response models a newly created subscriber (`__v: 0` and no `lastOnlineAt` when null), so legacy MongoDB version values and explicit-null versus absent dates are not preserved.

Migration `0020` adds experimental topics and memberships; `0021` restricts deleting a topic with members. API-key v1 endpoints support topic creation, individual retrieval, rename and deletion, membership assignment/removal and individual membership retrieval. `GET /v1/subscribers/:id?includeTopics=true` returns topic keys; deleting a subscriber cascades its memberships. Selected cases were compared with the original API. Topic recipients are supported for the experimental single in-app workflow: the worker resolves memberships during processing, deduplicates overlaps with direct recipients, and applies the union of topic exclusions to topic recipients. This adds one subscriber query for each job with topics; selected deliveries were compared with the original worker. Subscription preference evaluation is experimental and limited to single in-app steps; context filtering, large fan-out paging, traces and timing under concurrent membership changes are unimplemented or unverified. v2 subscription features beyond creation, listing, single lookup, name update and deletion, full v1 subscriber fields, MongoDB migration and ordering across multiple topics also remain unsupported or unverified.

The v1 topic list supports exact key/name filters and page/pageSize pagination with sizes 1–10. The reference returns an internal error for `pageSize=0`, which is reproduced. Selected filters, page boundaries and errors were compared against the original. Rows are ordered by generated ID; the original query has no explicit sort, so migrated or multi-process ordering can differ. Full numeric query parsing and concurrent pagination are not implemented or verified.

Migration `0022` adds optional topic names and custom data. API-key `POST /v2/topics` supports upsert and `failIfExists`; `GET/PATCH /v2/topics/:key` retrieves and updates the topic, with `data: null` clearing data. v1 reads expose the same data. `DELETE /v2/topics/:key` deletes the topic and its memberships atomically, even when members exist, and retries up to three times on a concurrent membership FK conflict. Selected response, validation, deletion and cross-version cases were compared with the original API, whose existing-topic upsert returns HTTP 201. Full validation and Unicode/numeric serialization boundaries, MongoDB migration, v2 subscriptions, continued deletion contention and user JWT permissions remain incomplete or unverified.

The v2 topic list supports literal case-insensitive key/name search, `_id`, `createdAt`, `updatedAt`, `key` and `name` ordering, forward/backward cursors and optional cursor inclusion. Selected pages, null-name behavior and errors were compared with the reference. MongoDB type-bracketed comparisons can make a page after a null-name cursor empty even when string-named topics follow. Unicode case folding, unusual numeric inputs, high-volume counts, cursor migration and concurrent changes remain unverified.

Experimental single-in-app triggers accept an actor ID or supported subscriber profile. The worker upserts that actor, excludes them from topic fan-out unless directly addressed, and resolves supported actor fields in templates. This adds one subscriber upsert and an advisory lock target per actor-bearing job. The prototype batches actor and recipient changes in one transaction, unlike the reference's separate stages; actor message metadata, topic conditions, other channels, full validation and concurrent update behavior are not implemented or verified.

Migration `0023` gives topic subscriptions an independent internal ID and environment-unique identifier, preserving multiple subscriptions for one subscriber/topic. It backfills legacy v1 rows with Novu’s default identifier in one transaction; ambiguous identifier collisions abort the migration and require manual resolution. `GET /v2/topics/:key/subscriptions/:identifier` supports the default context-feature-flag-off behavior and returns stored names and context keys; limited stored subscription preference results are supported; feature-flag-on lookup is not implemented. The v2 subscription create endpoint supports API-key requests with subscriber IDs or named identifiers, idempotent existing subscriptions, the 10-per-subscriber limit, and partial errors. Reference tests create subscriptions through both APIs and exercise selected in-app deliveries. Context and the full subscription preference contract remain incomplete. This is not full compatibility. Creation currently uses one topic upsert and one subscriber query plus up to three queries per found subscriber; same-identifier races, identifier collisions, count-limit concurrency, input validation and failure atomicity do not fully match Novu. The new unique index adds an index write per membership insertion; v1 topic expansion retains its existing subscriber lookup index.

Migration `0024` adds an environment/topic/subscription-ID index for `GET /v2/topics/:key/subscriptions`. The listing supports subscriber and exact context-key filtering, forward/backward ID cursors and capped counts. The reference ignores the requested `orderBy` on this endpoint and sorts by subscription ID; the implementation does the same. Tests compare selected API cases on original Novu and Rust, with context-key records inserted directly in disposable databases because context-scoped creation remains unsupported. Multiple workers, large datasets, unusual numeric inputs and user JWT authorization remain unverified or unsupported. This index adds one index write per subscription insert or delete; listing performs a topic lookup, capped count and page query, plus a cursor lookup and opposite-page existence query where applicable.

Migration `0025` preserves whether a subscription name is absent or explicitly null. Existing non-null names are marked present; historical SQL null names cannot be reconstructed and remain absent. API-key `PATCH /v2/topics/:key/subscriptions/:identifier` supports name changes, empty and null names, and a no-op request. Selected nonempty preferences are supported; an empty array clears stored preferences for that subscription and subscriber. Selected create/update/get behavior, timestamps, authentication and error cases were compared with the original. Context-enabled mode, subscription preferences, user JWT permissions, concurrent updates and all validation edge cases remain unimplemented or unverified. The management request adds one topic lookup and one subscription read/update, with no worker hot-path queries.

`DELETE /v2/topics/:key/subscriptions` supports identifier- and subscriber-based deletion, mixed requests and partial errors. The original merges identifier and subscriber lookup results without deduplication, so its response can report the same subscription twice; this implementation preserves that response behavior while deleting the underlying rows once. Run `NOVU_TEST_MONGO_REPLICA=1` with `scripts/test-reference-subscribers.sh` to compare against an original MongoDB replica set, and additionally set `NOVU_TEST_PREFERENCE_DELIVERY=1` to test post-deletion in-app delivery. Original Novu also deletes subscription-specific workflow preferences in its transaction; the experimental PostgreSQL table is cleared in the same deletion statement. Subscriber, topic and other-environment records are preserved. PostgreSQL membership deletion is atomic, but the pre-deletion lookups and response are separate statements, and concurrency, full validation and user JWT permissions remain unverified or incomplete. Each request performs a topic lookup, up to two membership queries and one subscriber lookup, then one delete; no worker hot-path queries were added.

Migration `0026` stores subscription-scoped preferences by environment, subscriber, subscription, workflow and context hash. v2 subscription deletion removes these rows atomically; clearing preferences via PATCH removes only rows for the subscription’s subscriber. As in the tested original, v1 removal and force topic deletion leave orphan preference records, so no subscription foreign key is used. A single-subscription GET exposes stored settings and selected workflow metadata. Reference lifecycle tests seed preferences directly; API and delivery comparisons also create and update settings through both APIs. The worker evaluates these settings for the experimental single in-app topic path; other channels and full delivery compatibility remain unimplemented. Context-hash creation, data migration, full workflow metadata and context-enabled behavior remain unimplemented or unverified. The new index costs one index write per preference insert/delete; single-subscription GET adds one preference lookup. Worker lookup costs are described below.

The topic worker reads subscription-specific preferences during fan-out, allows the subscriber if any selected subscription passes, and gives a non-null JSON Logic condition precedence over enabled. A non-boolean result or evaluation error is false; direct recipients bypass topic preferences. Selected outcomes and conditions were compared with the original worker and json-logic-js. This is not a full JSON Logic/JavaScript, context, actor or subscriber compatibility claim. The workflow internal ID must be present in inbox_metadata.id; when it is missing and a selected subscription has stored preferences, the job fails rather than bypass the setting. Each topic fan-out performs up to one indexed preference lookup per subscription in the expansion query, increasing database and memory work with membership count. Full preference creation/update, other channels, traces and complete concurrency semantics remain unsupported or unverified.

Subscription creation and update support selected workflow identifier, internal ID and tag filters with enabled values and JSON Logic conditions. Creation preserves existing subscription settings; PATCH replaces them. Requests return 501 when required internal IDs or tag metadata are missing, and complete validation, context-enabled behavior, all workflow types and concurrency remain unverified. Resolution currently loads all workflows in the environment; creation adds one write per selected workflow per new subscription and existing subscriptions add a preference read. PATCH deletes the old settings, inserts replacements individually and updates the name separately, matching the original operation order. A failure can leave settings removed or partially recreated, and the overall change is not atomic.

The replica-set comparison enables MongoDB test commands only in its disposable container to inject insertion and update failures. It compares selected HTTP 500 responses and resulting subscription state against the original. Concurrent uniqueness conflicts use the already stored preference; one PostgreSQL contention case was tested, while broader concurrency and partial multi-workflow failures remain unverified.

Migration `0027` indexes subscription cursors by environment and subscriber. `GET /v2/subscribers/:subscriberId/subscriptions` supports topic-key and exact context-key filters, ID-based pagination and stored subscription preferences. Selected responses and cursors are compared against original Novu; context-bearing and cross-bound preference fixtures are inserted directly into disposable test databases. The default context feature flag is assumed off for preference lookup. Missing user JWT permissions, context-enabled behavior, all validation boundaries, large data sets, concurrent updates and complete workflow metadata remain unimplemented or unverified. Each request performs a subscriber lookup, capped count, page and optional cursor/probe queries, plus one batched preference lookup for a nonempty page. The index adds a write per membership insert/delete.

Migration `0029_experimental_delivery_history.sql` adds an optional array of delivery timestamps used in Inbox list and individual mutation responses. NULL falls back to the existing single `delivered_at` value; an empty array remains empty. The worker appends a timestamp during automatic unsnooze and can emit a limited real-time event; the complete reference payload is not implemented.

For the bounded scheduled-unsnooze reference comparison, run the subscriber comparison script with `NOVU_TEST_MONGO_REPLICA=1 NOVU_TEST_PREFERENCE_DELIVERY=1 NOVU_TEST_UNSNOOZE_DELIVERY=1` and optionally `NOVU_TEST_SNOOZE_ONLY=1`. Both APIs create delayed jobs and their workers deliver the automatic unsnooze. The worker updates state and completes the queue job atomically and publishes a best-effort WS event; original retry and execution-detail contracts are not implemented.

Migration `0003_experimental_snooze_policy.sql` provides an optional per-organization maximum in milliseconds. Missing rows use the free-tier 24-hour maximum; NULL is unlimited. Policy rows require external configuration and are not synchronized with Novu subscription tiers. Snooze supports RFC 3339 strings and integer Unix milliseconds; other JavaScript date conversions, all validation and concurrent scheduling cases, and notifications/events on snooze or unsnooze are not fully implemented or verified.

`0032_experimental_message_severity.sql` preserves both the severity value and whether the field was present, so the `none` count filter includes absent fields but excludes explicit null. The [reference comparison](tests/reference_count_severity_compare.py) uses directly seeded message fixtures and covers valid scalar/array severity filters, null, empty arrays, and combinations with read/tags. Run it with `NOVU_TEST_SEVERITY_ONLY=1` and `NOVU_REFERENCE_SOURCE` set. The experimental single-step worker supports workflow severity and trigger `overrides.severity`; broader workflow types and channel delivery remain unimplemented; invalid severity error responses and high-volume performance are not compared. The new columns add storage but no index; severity filtering evaluates each candidate message in the existing capped count query.

Notification lists accept one or repeated `severity` parameters, and notification DTOs return stored message severity independently of workflow severity. Missing and explicit-null severity map to `none` in the DTO, while filtering distinguishes them. The reference comparison uses directly seeded messages and workflow metadata; full workflow creation, non-default severity delivery, other list query forms, invalid-input errors and multi-tenant or context scenarios remain unverified.

The single in-app worker resolves workflow severity when processing the job unless `overrides.severity` is provided. Jobs from the previous implementation without `severityOverride` keep their queued severity snapshot. The worker writes that severity and Inbox session counts exclude snoozed messages and cap each severity at 100. The [WS delivery comparison](../../ws/rust-ws/tests/worker_delivery.cjs) covers a medium workflow default, a high override, SDK delivery and session counts before and after snooze. The queued severity comparison pauses both workers, triggers a new workflow, changes its severity, and verifies the result and an explicit override after resuming. The reference has an optional in-memory workflow cache and Rust does not; cached-workflow behavior, invalid overrides, other step types and providers remain unverified or unsupported. The session performs five bounded count subqueries for total and severity buckets.

For new queue entries the worker resolves the workflow by environment and trigger identifier before processing, including when a severity override is set; a missing workflow fails without delivery. The queued reference comparison also covers deletion and recreation under the same identifier while workers are paused. The source trigger queue is configured in the disposable test to retain the failed job so its failure reason can be inspected. Older queue entries retain their original prototype behavior, and workflow caching and deletion or changes after the worker lookup are not equivalent yet. New queue entries use the current single in-app content and workflow tags; previous-format queue entries retain their snapshots.
