API migration `0070` adds a transactional fence to the optional JWT revocation policy. Apply it, grant the API DB login EXECUTE on `public.novu_rust_operator_token_guard(bytea,bytea,bytea,bytea)` in addition to the 0067 function, and deploy the new API code to every instance. The trusted guard owner needs schema USAGE and EXECUTE on the 0067 revocation-check function; protect the owner, revocation table and trigger. With `check_token_revocation:true`, each experimental operator DB operation takes a shared transaction-scoped advisory lock for the token and rechecks revocation in the same SQL statement as the protected operation. Denylist INSERT, UPDATE and DELETE take the exclusive lock through a trigger. If a revocation has the lock first, a subsequent guarded operation waits and then rejects after commit; if an operation has it first, the revocation waits for that DB transaction to finish. A response already produced or an HTTP response delayed after its DB transaction cannot be recalled. The earlier initial check remains and fails closed if unavailable.

The fence requires `READ COMMITTED`; other isolation levels are rejected because an old snapshot cannot safely recheck after waiting. Each API operation must remain a single statement on its normal autocommit connection; future endpoints must use the guard too. Disabled/old API instances, API-key paths, direct calls to protected SQL functions, privileged trigger bypass, TRUNCATE, DB restore and asynchronous failover bypass or weaken this protection. Advisory lock hash collisions can serialize unrelated tokens, and slow operations or long revocation transactions can delay each other. The migration installs a table trigger and may need a DDL lock; measure production contention. Inspection remains a separate point-in-time read and may show false before commit. Docker PostgreSQL tests exercise both lock orderings, a real read and write through the in-process router, least-privilege guard owner, unsupported isolation rejection and legacy-policy regression. Real IdP, every endpoint, load, multi-host failover and split brain remain unverified.

API migration `0027` adds `inspect` for a retained token file. An authorized database administrator grants the registered environment administrator the additional permission:

For rolling termination, the API handles SIGTERM and Ctrl-C. `SWALLOW_API_DRAIN_SECONDS` (default 0, range 0–300) sets an optional interval during which readiness returns 503 and new application requests return 503 while the listener remains available; liveness remains 200. `SWALLOW_API_DB_CONNECTIONS` selects 1–16 independent PostgreSQL connections per API process (default 1). Each connection has its own router and reconnect loop; requests remain on the selected connection for the entire request. `SWALLOW_API_DB_ROUTING=round-robin` is the default; `least-inflight` chooses the available slot with the fewest active HTTP request handlers, rotating ties. Invalid policies fail startup. Selection and the counter increment are serialized with a short process-local lock; counters drop when the handler future completes or is cancelled. This is a request-count heuristic, not DB load measurement: background health probes and SQL that continues after a cancelled request are not counted, and a blocked or freshly reconnected slot can still receive requests. It does not guarantee that every request succeeds. Existing in-flight requests are never automatically replayed after a disconnection; a failed or lost response may represent a committed write and must be reconciled. The API listens while all connections are unavailable and returns 503 until at least one reconnects. Each connection is probed and reconnected independently after a disconnection or failed health probe. `SWALLOW_API_DB_HEALTH_TIMEOUT_SECONDS` (default 30) and `SWALLOW_API_DB_HEALTH_INTERVAL_SECONDS` (default 10) accept 1–300 seconds; reconnect attempts occur every two seconds using the original `DATABASE_URL`. A blocked query can delay a probe and cause that connection to be discarded. A TCP failure can take an interval plus timeout to detect. Changing host/port or connection count requires restart. Increasing the count also increases DB sessions, concurrent startup/retry attempts and query load; account for every API replica and the database connection limit.

`SWALLOW_API_MAX_INFLIGHT_PER_CONNECTION` optionally limits active forwarded HTTP handlers per connection slot for either routing policy. It accepts 0–1000; the default 0 means unlimited and invalid values fail startup. When all connected slots are at the limit, the API immediately returns 503 `Server busy`, `Retry-After: 1` and `Cache-Control: no-store`; it does not queue or retry the request. Health endpoints bypass the limit. Counters are per process and slot, not shared across replicas, and persist across a slot reconnect while old handlers are still running. They exclude health probes and database work that survives request cancellation, so this is not a hard PostgreSQL concurrency limit. A caller must retry only when appropriate for its operation; a lost response can still correspond to a committed write. This setting does not protect the worker or Socket.IO server and does not establish HA. Docker PostgreSQL tests exercise both routing policies with blocked requests, a saturated response and recovery; production load and multi-replica limits have not been validated.

No request is automatically replayed after connection loss. An in-flight write may have committed even if its response failed; clients must use operation-specific idempotency and verify state before retrying. Request and audit records include identities and reasons; protect access and retention. Audit pages contain at most 50 UUID-ordered entries, are not chronological and do not form a single snapshot. Direct DB edits and rejected requests are not audited.

Trusted security-definer owners require EXECUTE on the existing operator self function and internal helper functions, SELECT and row-lock privileges on identity and administration tables, SELECT/INSERT/DELETE on all ten channel grant tables, and appropriate SELECT/INSERT access on request and audit tables. The audit viewer function additionally needs row locks and audit SELECT. The trusted API login need not directly read or change those tables. Protect the function owners, schema and API login: direct function invocation can impersonate registered identities. Existing optional JWT token-revocation fencing applies. Tests cover signed test JWTs, environment isolation, grant separation, actual channel reads, replay/conflict including concurrent identical requests, audit and revocation waiting on a lock; they do not establish external IdP, production HA or complete Novu compatibility.

### Resource-scoped channel-access administrators

Apply API migration `0082` to provision an administrator for individual providers without granting the broad `channel_access_grant_admins` privilege. A trusted DBA inserts identity-specific rows in `public.novu_rust_operator_jwt_channel_access_grant_scopes` with `resource` set to `resend`, `sendgrid`, `twilio`, `fcm` or `slack`, and independent `can_read`/`can_write` booleans. For example:

```sql
INSERT INTO public.novu_rust_operator_jwt_channel_access_grant_scopes
 (issuer,subject,client_id,environment_id,resource,can_read,can_write)
VALUES ('ISSUER','SUBJECT','CLIENT','ENVIRONMENT','sendgrid',true,true);
```

The actor must already be provisioned and enabled. Existing broad admin rows retain their original permissions; a broad permission overrides narrower rows, so remove broad rows when restricting an actor. Each scoped administrator can manage both `result` and `jobs` for that provider if granted write; this does not itself grant the administrator access to the results. The request receipt path requires current write permission for the recorded provider. An absent request returns `found:false` only to an actor with some channel write permission. Audit viewing remains a separate environment-wide grant and is not filtered by provider. The trusted function owners need EXECUTE on `public.novu_rust_operator_jwt_channel_access_scope_check(text,text,text,text,bigint,boolean,text)` and SELECT plus row-lock privileges on the new scope table, in addition to the earlier permissions. No scope is automatically assigned. Protect the scope table, function owners, schema and trusted API login.

PostgreSQL tests cover provider isolation, independent read/write, receipt authorization after scope changes, broad-admin compatibility and revocation while a read waits. A browser/API fixture verifies one scoped provider and denial for another. Production authorization deployment, external IdP, HA and complete Novu compatibility remain unverified.
