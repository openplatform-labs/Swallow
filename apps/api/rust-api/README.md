웹훅 묶음 준비 상태 기반 라우팅 시험: 임시 PostgreSQL과 두 실제 API 프로세스 앞에 테스트 전용 준비 상태 인식 프록시를 배치했다. 한 인스턴스의 Resend 파일이 손상되면 해당 인스턴스 직접 요청은 503이고 프록시는 다른 인스턴스로 합성 서명된 Resend·Twilio 요청을 전달했다. 파일 복구 후 원래 인스턴스를 다시 사용하고, 양쪽 Twilio 파일이 잘못되면 프록시는 503을 반환해 이벤트를 추가하지 않았다. 이 프록시는 시험 코드이며 운영용 로드밸런서가 아니다. 단일 호스트·관리자 DB 계정·합성 서명 시험으로 실제 공급자, 네트워크 분리, 운영 로드밸런서와 다중 호스트 HA는 미검증이다. `TEST_PG_BIN=/path/to/postgresql/bin scripts/test-resend-webhook-bundle-local.sh`로 재현한다.

웹훅 키를 API 준비 상태에 선택적으로 반영: `SWALLOW_API_READY_REQUIRE_RESEND_WEBHOOK_BUNDLE=true` 또는 `SWALLOW_API_READY_REQUIRE_TWILIO_WEBHOOK_BUNDLE=true`를 각각 지정하면 `/health/ready`는 기존 DB 조건에 더해 선택한 묶음 파일의 유효성을 요구한다. 둘 다 설정할 수도 있고 기본은 각각 false다. 건강 검사 활성화와 해당 묶음 재읽기 설정이 필요하며 별도 파일 상태 경로 활성화는 필수가 아니다. 잘못된 값이나 구성 누락은 시작을 거절한다. 실패하면 전체 API 인스턴스의 준비 상태가 503이 되지만 요청 라우팅을 직접 차단하지 않는다. 두 파일 검사는 병렬이고 기존 웹훅 요청과 파일 읽기 슬롯을 공유하므로 지나친 검사 빈도·지연된 파일 시스템은 준비 상태에 영향을 줄 수 있다. DB가 준비되지 않으면 파일 검사를 생략한다. 이 판정은 순간 상태이며 공급자 키 일치·이벤트 수신·전체 HA를 보장하지 않는다. 임시 PostgreSQL과 실제 API 네 개에서 미선택·각각 선택·모두 선택을 비교하고 파일 오류·복구와 잘못된 시작 설정을 확인했다. 실제 로드밸런서·다중 호스트·운영 HA는 미검증이다. `TEST_PG_BIN=/path/to/postgresql/bin scripts/test-resend-webhook-bundle-local.sh`로 재현한다.

Twilio 웹훅 토큰 파일 상태 감시: 토큰 묶음 재읽기를 구성하고 `SWALLOW_API_HEALTH_ENDPOINTS_ENABLED=true` 및 `SWALLOW_API_TWILIO_WEBHOOK_BUNDLE_HEALTH_ENABLED=true`를 지정하면 `GET /health/twilio-webhook-bundle`이 파일 검증 결과를 200 또는 503으로 반환한다. 응답에는 상태만 포함하며 캐시하지 않는다. 묶음 재읽기 없이 상태 검사만 활성화하거나 잘못된 설정은 시작 시 거절한다. 이 인증 없는 경로의 네트워크 접근을 제한하고 인스턴스마다 감시한다. 요청 검증과 같은 파일 읽기 슬롯을 사용하며 순간적인 파일 읽기·형식만 확인하므로 실제 Twilio 토큰 일치나 이벤트 수신을 보장하지 않는다. 별도 준비 상태 조건을 선택하지 않으면 기존 준비 상태와 라우팅에는 영향을 주지 않는다. 실제 API·임시 PostgreSQL·경보 실행기 및 스케줄러에서 오류와 복구를 확인했다. 실제 Twilio와 다중 호스트 HA는 미검증이다. 경보 연계는 [워커 README](../../worker/rust-queue/README.md)를 참고한다.

Twilio 웹훅 토큰 무중단 파일 교체: 선택적으로 `NOVU_TWILIO_WEBHOOK_TOKEN_BUNDLE_FILE`에 단일 줄 JSON `{"current":"...","previous":"..."}`을 담은 일반 파일을 지정한다. `previous`는 생략하거나 null로 둘 수 있으며 기존 현재·이전 토큰 환경 변수 또는 파일과 동시 지정할 수 없다. 기존 환경 ID·계정 SID·공개 콜백 URL과 선택형 계정 일치 검사는 그대로 적용된다. 파일을 완성한 뒤 같은 파일시스템에서 원자적으로 교체하고, 새 토큰과 이전 토큰을 겹쳐 배포한 다음 이전 토큰을 제거한다. 파일 접근과 권한을 보호하고 비밀을 로그에 기록하지 않는다.

요청의 경로·형식 검사 후 서명 검증 직전에 파일을 읽는다. 누락·잘못된 JSON·중복 토큰·2초 시간 초과 또는 인스턴스별 16개 읽기 슬롯 포화는 HTTP 503으로 실패하며 이전 토큰을 유지하지 않는다. 완료되지 않는 파일 읽기는 타임아웃 후에도 해당 슬롯을 점유한다. 이미 시작된 요청은 이전 스냅샷을 쓸 수 있고 인스턴스별 전환은 독립적이다. 기존 개별 토큰 방식은 시작 시 읽는다. 임시 PostgreSQL·합성 Twilio 서명으로 중첩·폐기·오류·복구를 검증하고 시작 설정 시험 6건을 수행했다. 실제 Twilio 회전·재전송·다중 호스트 HA는 미검증이며 파일 상태 감시·경보는 위 최신 항목을 참고한다. 재현은 `TEST_PG_BIN=/path/to/postgresql/bin scripts/test-resend-webhook-bundle-local.sh`.

Resend 웹훅 키 파일 상태 감시: 선택형 묶음 재읽기를 구성하고 `SWALLOW_API_HEALTH_ENDPOINTS_ENABLED=true`, `SWALLOW_API_RESEND_WEBHOOK_BUNDLE_HEALTH_ENABLED=true`를 지정하면 `GET /health/resend-webhook-bundle`이 현재 파일을 검증해 정상 200, 실패·시간 초과·동시 읽기 포화 503을 반환한다. 응답은 상태만 포함하며 `Cache-Control: no-store`다. 키 재읽기 없이 감시만 활성화하거나 잘못된 설정은 시작 시 거절한다. 인증 없는 경로이므로 네트워크 접근을 제한하고 인스턴스마다 따로 감시한다. 이 검사는 파일 형식과 읽기 가능성의 순간 상태만 확인하며 공급자의 실제 서명·키 일치, 전송 또는 이벤트 수신을 증명하지 않는다. 검사는 웹훅 요청과 같은 파일 읽기 슬롯을 사용하므로 폴링 부하를 고려한다. 별도 준비 상태 조건을 선택하지 않으면 기존 준비 상태와 라우팅에는 영향을 주지 않는다. 실제 API 프로세스·임시 PostgreSQL·경보 실행기 및 스케줄러에서 오류·복구와 발송 결과 불명 경보의 중복 억제를 확인했다. 실제 공급자 경보와 다중 호스트 HA는 미검증이다. 경보 연계는 [워커 README](../../worker/rust-queue/README.md)를 참고한다.

Resend 웹훅 서명 키 무중단 파일 교체: 선택적으로 `NOVU_RESEND_WEBHOOK_SECRET_BUNDLE_FILE`에 단일 줄 JSON 파일 `{"current":"whsec_...","previous":"whsec_..."}` 경로를 지정한다. `previous`는 생략하거나 null로 둘 수 있다. 환경 ID는 기존 `NOVU_RESEND_WEBHOOK_ENVIRONMENT_ID`를 사용하며 기존 현재·이전 키 환경 변수와 파일 설정을 동시에 지정하면 거절한다. 시작 시 파일·키를 검증하고 각 유효 형식 요청의 서명 검증 직전에 일반 파일을 다시 읽는다. 새 파일을 같은 파일시스템에서 완성한 뒤 원자적으로 rename하거나 시크릿 마운트의 심볼릭 링크를 원자 교체한다. 전환 시 새 키와 이전 키를 함께 넣고 전달 상태를 확인한 뒤 이전 키를 제거한다. 보유자의 파일 접근 권한·소유권을 제한하고 비밀을 로그에 남기지 않는다.

파일이 없거나 잘못됐거나 중복 키이면 이전 키를 유지하지 않고 HTTP 503을 반환한다. 요청당 2초 읽기 제한과 인스턴스별 최대 16개 동시 파일 읽기를 적용하며 제한 초과도 503이다. 읽기 작업 자체가 파일 시스템에서 멈추면 타임아웃 후에도 해당 작업은 끝날 때까지 슬롯을 점유한다. 검증을 이미 시작한 요청은 읽은 이전 스냅샷을 사용할 수 있고 각 API 인스턴스의 파일 반영은 독립적이다. 이 기능은 파일 갱신·공급자 설정을 자동화하지 않으며, 재전송을 가정해 이벤트 유실이 없다고 판단해서는 안 된다. 기존 개별 키 방식은 시작 시 읽는 동작을 유지한다. 임시 PostgreSQL과 합성 서명으로 교체·중첩·폐기·오류·복구를 검증하고 프로세스 시작 설정 및 시크릿 비노출 시험을 수행했다. 실제 Resend 키 회전·다중 호스트 HA와 파일 시스템 장애는 미검증이다. 재현: `TEST_PG_BIN=/path/to/postgresql/bin scripts/test-resend-webhook-bundle-local.sh`.

FCM 반복 선점 권한 위임: API 0116은 기존 FCM 위임 관리자의 범위를 `claim-health`와 `claim-list`까지 확장한다. 동일 요청 ID 재제출, 조건부 변경, 자기 권한 변경 거절과 기존 감사 기록을 적용하며 한 권한 회수는 다른 권한을 유지한다. 기존 `can_read`·`can_write` 위임 관리자에게 새 권한 관리가 가능해지므로 적용 전에 관리자를 검토한다. 함수 소유자는 `novu_rust_operator_jwt_fcm_unrecorded_claim_grants`의 SELECT·INSERT·UPDATE와 기존 위임 테이블 권한이 필요하다. 최초 위임 관리자와 API DB 로그인 `alert_view`는 DBA가 별도 등록한다. 임시 PostgreSQL·제한 로그인에서 두 권한의 API 접근, 회수, 재제출 및 자기 변경 거절을 확인했다. 브라우저–API 위임은 [대시보드 README](../../dashboard/swallow/README.md)의 최신 시험을 참고하며 실제 외부 IdP·운영 HA는 미검증이다.

Optional readiness gate for operator key reload: set `SWALLOW_API_READY_REQUIRE_OPERATOR_KEYS=true` with `SWALLOW_API_HEALTH_ENDPOINTS_ENABLED=true` and operator JWT file reload configured. The default is false. When enabled, `/health/ready` returns 503 if the last poll failed or its result is stale, in addition to its existing DB, draining and other configured checks. This check is independent of exposing `/health/operator-keys` and applies to both `retain` and `reject`. Invalid values or missing prerequisites fail startup. It is a process-local snapshot: initial health means startup validation succeeded, and a 200 response is not proof that the IdP, permissions, all tokens or database writes work. A load balancer using this readiness endpoint can remove **all** API traffic from an unhealthy instance, even if non-operator routes and retained keys still work; a shared failure can remove every instance. ## Optional operator token introspection

Experimental operator JWT routes can optionally check token activity with an [RFC 7662](https://www.rfc-editor.org/rfc/rfc7662) endpoint on every request, after the existing pinned signature and claims verification. Configure the existing `SWALLOW_OPERATOR_JWT_CONFIG` or `SWALLOW_OPERATOR_JWT_CONFIG_FILE` and set these variables on every API instance:

```text
SWALLOW_OPERATOR_INTROSPECTION_URL=https://issuer.example/oauth/introspect
SWALLOW_OPERATOR_INTROSPECTION_CLIENT_ID=swallow-api
SWALLOW_OPERATOR_INTROSPECTION_CLIENT_SECRET_FILE=/run/secrets/operator-introspection
SWALLOW_SECRET_REGULAR_FILES_ONLY=true
SWALLOW_OPERATOR_INTROSPECTION_TIMEOUT_SECONDS=5
# Optional, per API process; omitted means no concurrency limit.
SWALLOW_OPERATOR_INTROSPECTION_MAX_IN_FLIGHT=100
```

Use either `SWALLOW_OPERATOR_INTROSPECTION_CLIENT_SECRET_FILE` or `SWALLOW_OPERATOR_INTROSPECTION_CLIENT_SECRET`, not both. Protect the secret and endpoint configuration. The timeout defaults to 5 seconds and accepts 1–30. Incomplete or invalid configuration fails startup. HTTPS is required; `SWALLOW_OPERATOR_INTROSPECTION_ALLOW_LOOPBACK_HTTP=true` permits loopback HTTP only for local tests. Redirects are refused. The endpoint must support `client_secret_basic`; opaque tokens are not accepted because JWT verification remains mandatory.

An inactive token or conflicting returned identity claims is rejected with 401; endpoint failure, timeout, invalid or oversized response returns 503. Returned issuer, subject, client ID, token ID, audience, expiration and not-before are checked when present; an earlier returned expiration also limits the DB authorization. Local `check_token_revocation` remains separately configurable and can be combined with introspection. No cache or retry is used: every protected request depends on endpoint availability and adds latency and load. `SWALLOW_OPERATOR_INTROSPECTION_MAX_IN_FLIGHT` optionally limits concurrent checks per API process to 1–1024; omission leaves them unlimited. Invalid values fail startup. A saturated instance returns 503 immediately without contacting the IdP, and releases the slot on completion, failure, timeout or cancellation. This is not a cluster-wide limit, a rate limit, or a guarantee that an IdP has stopped processing a timed-out request; configure all replicas and capacity accordingly. An IdP revocation immediately after the check can race an in-flight operation; this is not a cross-system transactional fence. Configure all replicas, secure transport and secrets, synchronize clocks, and monitor the IdP independently; the API readiness endpoint does not check it. API keys and other authentication routes are unaffected.

Unit and startup tests use a local mock IdP. A real API process with a restricted DB login and disposable local PostgreSQL 17 tested active/inactive responses, claim mismatches, malformed/oversized replies, timeout, local revocation, expiry while waiting for a DB lock, concurrency saturation and recovery; the existing channel permission integration test also passed. The trusted guard owner needs schema USAGE and EXECUTE on the 0067 revocation-check function; protect the owner, revocation table and trigger. With `check_token_revocation:true`, each experimental operator DB operation takes a shared transaction-scoped advisory lock for the token and rechecks revocation in the same SQL statement as the protected operation. Denylist INSERT, UPDATE and DELETE take the exclusive lock through a trigger. If a revocation has the lock first, a subsequent guarded operation waits and then rejects after commit; if an operation has it first, the revocation waits for that DB transaction to finish. A response already produced or an HTTP response delayed after its DB transaction cannot be recalled. The earlier initial check remains and fails closed if unavailable.

The fence requires `READ COMMITTED`; other isolation levels are rejected because an old snapshot cannot safely recheck after waiting. Each API operation must remain a single statement on its normal autocommit connection; future endpoints must use the guard too. Disabled/old API instances, API-key paths, direct calls to protected SQL functions, privileged trigger bypass, TRUNCATE, DB restore and asynchronous failover bypass or weaken this protection. Advisory lock hash collisions can serialize unrelated tokens, and slow operations or long revocation transactions can delay each other. The migration installs a table trigger and may need a DDL lock; measure production contention. Inspection remains a separate point-in-time read and may show false before commit. Docker PostgreSQL tests exercise both lock orderings, a real read and write through the in-process router, least-privilege guard owner, unsupported isolation rejection and legacy-policy regression. Real IdP, every endpoint, load, multi-host failover and split brain remain unverified.

`SWALLOW_API_DB_CONNECTIONS` selects 1–16 independent PostgreSQL connections per API process (default 1). Each connection has its own router and reconnect loop; requests remain on the selected connection for the entire request. `SWALLOW_API_DB_ROUTING=round-robin` is the default; `least-inflight` chooses the available slot with the fewest active HTTP request handlers, rotating ties. Invalid policies fail startup. Selection and the counter increment are serialized with a short process-local lock; counters drop when the handler future completes or is cancelled. This is a request-count heuristic, not DB load measurement: background health probes and SQL that continues after a cancelled request are not counted, and a blocked or freshly reconnected slot can still receive requests. It does not guarantee that every request succeeds. Existing in-flight requests are never automatically replayed after a disconnection; a failed or lost response may represent a committed write and must be reconciled. The API listens while all connections are unavailable and returns 503 until at least one reconnects. Each connection is probed and reconnected independently after a disconnection or failed health probe. `SWALLOW_API_DB_HEALTH_TIMEOUT_SECONDS` (default 30) and `SWALLOW_API_DB_HEALTH_INTERVAL_SECONDS` (default 10) accept 1–300 seconds; reconnect attempts occur every two seconds using the original `DATABASE_URL`. A blocked query can delay a probe and cause that connection to be discarded. A TCP failure can take an interval plus timeout to detect. Changing host/port or connection count requires restart. Increasing the count also increases DB sessions, concurrent startup/retry attempts and query load; account for every API replica and the database connection limit.

`SWALLOW_API_MAX_INFLIGHT_PER_CONNECTION` optionally limits active forwarded HTTP handlers per connection slot for either routing policy. It accepts 0–1000; the default 0 means unlimited and invalid values fail startup. When all connected slots are at the limit, the API immediately returns 503 `Server busy`, `Retry-After: 1` and `Cache-Control: no-store`; it does not queue or retry the request. Health endpoints bypass the limit. Counters are per process and slot, not shared across replicas, and persist across a slot reconnect while old handlers are still running. They exclude health probes and database work that survives request cancellation, so this is not a hard PostgreSQL concurrency limit. A caller must retry only when appropriate for its operation; a lost response can still correspond to a committed write. This setting does not protect the worker or Socket.IO server and does not establish HA. Docker PostgreSQL tests exercise both routing policies with blocked requests, a saturated response and recovery; production load and multi-replica limits have not been validated.

No request is automatically replayed after connection loss. An in-flight write may have committed even if its response failed; clients must use operation-specific idempotency and verify state before retrying. JWT and webhook configuration is read at process startup and reused on reconnection; operator JWT signing keys can optionally be reloaded from a file as described above. Other configuration and secrets require controlled restarts. Sustained multi-replica traffic, load-balancer behavior, DB role/primary promotion, TLS failover and network partitions remain unverified. Liveness returns 200 while the HTTP process responds, even when the database is down. By default readiness returns 200 if at least one currently active connection responds to `SELECT 1`; otherwise it returns 503. The optional writable check is described above. It uses the configured DB health timeout, does not automatically replay requests, and returns `Cache-Control: no-store`. It checks connectivity only, not database schema, permissions, webhook secrets, provider availability, or the ability to complete actual requests. The probe checks all active connections concurrently using the same connections as normal requests, adding up to the configured connection count in DB queries per readiness request. Existing privileged DB access and SECURITY DEFINER functions can bypass row isolation.

`operator_smtp_scope` uses disposable PostgreSQL, a restricted API DB login and test JWTs to verify independent authorization, identity-isolated request IDs, concurrent replay, conflict, audit rollback and revocation. The browser fixture exercises the built dashboard and real HTTP API with a test JWT. External IdP, production privileges and multi-host HA are not verified.

### SMTP unknown-outcome operator API (migration 0132)

After worker migrations through 0222 and API migration 0132, a trusted DBA may grant an existing operator JWT identity an environment-specific row in `novu_rust_operator_jwt_smtp_resolution_grants`, setting `can_accept` and `can_retry` independently. The restricted API DB login separately needs the matching `can_accept` / `can_retry` setting in `novu_rust_smtp_resolvers` (including its current role OID), plus `EXECUTE` on `public.novu_rust_operator_jwt_smtp_resolve(text,text,text,text,bigint,uuid,uuid,uuid,bigint,text,text)` and `public.novu_rust_operator_jwt_smtp_resolution_request(text,text,text,text,bigint,uuid,text)`. No JWT or DB decision grant is created by default; a DBA provisions and revokes them. Neither the existing SMTP review grants nor audit viewer grants confer decision authority.

`POST /v1/experimental/operator/smtp-resolution?environmentId=ENV` accepts `requestId`, `jobId`, `attemptRevision` (null for pre-dispatch retry after API 0138 and worker 0224), decimal-string `failureRevision`, `decision` (`accepted` or `retry`) and a nonempty `reason`. Use the revisions from the SMTP attention listing. A successful new request returns `recorded: true, replayed: false`; repeating the identical request as the same JWT identity returns `replayed: true`. Changed request content or stale revisions return 409. `GET /v1/experimental/operator/smtp-resolution-request?environmentId=ENV&requestId=UUID&decision=accepted|retry` retrieves only that identity's request and requires current permission for the decision. Request IDs are isolated between JWT identities even when they share the API DB login. The JWT request table records the user identity and the worker resolution table records the DB login and a deterministically derived request ID; both commit together. The JWT request and worker audit tables are sensitive and DBA-managed. The dashboard can submit and look up decisions, manage their JWT grants, and display DB-level decision history as described below.

`accepted` means an operator determined the relay accepted the message, not that it arrived in a mailbox. `retry` requeues the job and can duplicate a message if the operator's external evidence is wrong. Neither choice verifies relay evidence automatically. See the worker README for the decision and audit CLI, migration requirements and limits.

`TEST_PG_BIN=/opt/homebrew/opt/postgresql@17/bin scripts/test-smtp-resolution-local.sh` runs an isolated local PostgreSQL integration test using signed test JWTs and a restricted API login. It covers separate JWT and DB permissions, environment isolation, stale revisions, repeated and conflicting requests, two identities sharing a request ID, failure rollback, retry requeue and revocation. It does not run an HTTP server or browser, a real IdP, actual external delivery or production HA.

### SMTP decision grant delegation (migration 0133)

JWT decision grants can be managed through `/v1/experimental/operator/smtp-resolution-grants`, with `/request` and `/audit` for request recovery and delegation history. The resource is `smtp-resolution`, with independent `accepted` and `retry` permissions. A trusted DBA first provisions environment-specific `novu_rust_operator_jwt_smtp_resolution_grant_admins` (separate read/write flags) and `novu_rust_operator_jwt_smtp_resolution_grant_audit_viewers`, and grants the API login EXECUTE on the corresponding read, change, request and audit functions. Existing administrators are not automatically granted these privileges. This manages JWT grants only; the API DB login's own SMTP resolver permissions still require separate DBA provisioning.

A change checks the expected current value, rejects changes to the actor's own issuer/subject, binds a request ID and reason to the change, and writes an audit record transactionally. Replaying the same request returns its original result; changed contents or stale expectations conflict. Audit pages use UUID order rather than commit order, so they are not a complete ordered event stream; use an independent audit export when complete collection is required. `TEST_PG_BIN=/opt/homebrew/opt/postgresql@17/bin scripts/test-smtp-resolution-local.sh` validates both decision and delegation with restricted API DB logins and signed test JWTs, including audit rollback and permission revocation. The dashboard browser test is described in its README. An external IdP and production HA were not tested.

### SMTP decision history API (migration 0134)

`GET /v1/experimental/operator/smtp-resolution-history?environmentId=ENV&jobId=UUID` returns the worker's job-specific resolution history. For subsequent pages supply both `beforeActorOid` and `beforeRequestId` from `next`. Failure revisions are decimal strings so JavaScript preserves the full 64-bit value. A DBA must provision the JWT identity in `novu_rust_operator_jwt_smtp_resolution_history_viewers`, independently provision the API DB login in `novu_rust_smtp_resolution_audit_viewers`, and grant the API login EXECUTE on `public.novu_rust_operator_jwt_smtp_resolution_history(text,text,text,text,bigint,uuid,oid,uuid)`. These grants do not authorize decisions; decision grants do not authorize history. JWT history viewer grants can be delegated after migration 0136, as described below.

The actor and request ID describe the DB-level resolution. After API migration 0135, new JWT decisions also include an explicit operator identity and original request ID, as described below. Results can contain operator-entered reasons, which should not contain secrets or personal data. Records are not an externally tamper-proof log and concurrent commits may appear before an already-read cursor. The API integration test covers both authorization layers, environment isolation, pagination, revocation, and 64-bit revisions with signed test JWTs and disposable local PostgreSQL. External IdP and production HA are not tested.

### SMTP JWT decision attribution (migration 0135)

New JWT decisions capture issuer, subject, client ID and original JWT request ID against the DB audit record in the same transaction. If attribution cannot be stored, the decision and job changes roll back. The separately authorized history API returns `operator` with these fields; CLI decisions and records created before migration 0135 return `operator: null` and are not retrospectively guessed. DB administrators can modify stored audit data; this is not an externally tamper-proof log. Identity data is visible to history viewers, so provision that permission accordingly. Integration tests verify separate identities sharing a DB login and request ID, failure rollback and older unattributed records. The browser test checks the displayed identity with a fixture JWT; real IdP and production HA remain unverified.

### Delegating SMTP history access (migration 0136)

The existing SMTP decision grant administrators can additionally manage `smtp-resolution:history` through the same grant API and dashboard. **This expands the authority of existing read and write grant administrators**: they can now inspect or grant access to resolution history, including operator identities and reasons. Review their existing grants before applying this migration. Delegation history and requests use the existing audited, conditional and idempotent path, and self-granting remains forbidden. A JWT history grant is independent of decision grants and the API DB login still needs its separately DBA-provisioned history viewer permission.

The API integration test checks actual target history access, independent revocation and audit-failure rollback. `TEST_POSTGRES_MODE=local scripts/test-smtp-history-grants-browser.sh` in the dashboard directory verifies delegation, a target JWT decision and history lookup, and denial after revocation against the real API and disposable PostgreSQL. ### Finding an acknowledged SMTP failure (worker 0223, API 0137)

API migration 0138 extends the existing `retry` decision to failed SMTP jobs with no current attempt; see the worker README for deployment order, expanded permissions and prior-delivery limitations. ### Discord operator decisions and rate-limit guidance (worker 0225, API 0139)

A trusted DBA provisions an existing JWT identity in `novu_rust_operator_jwt_discord_resolution_grants`, with independent `can_accept` and `can_retry` flags. The API DB login separately needs its own row in `novu_rust_discord_resolvers` with matching decision permissions, current role OID, and EXECUTE on `public.novu_rust_operator_jwt_discord_resolve(text,text,text,text,bigint,uuid,uuid,uuid,bigint,text,text)` and `public.novu_rust_operator_jwt_discord_resolution_request(text,text,text,text,bigint,uuid,text)`. No grants are created by default.

`POST /v1/experimental/operator/discord-resolution?environmentId=ENV` accepts `requestId`, `jobId`, `attemptRevision` (null only for retry without a current attempt), decimal-string `failureRevision`, `decision` (`accepted` or `retry`) and `reason`. The request can be looked up with `GET /v1/experimental/operator/discord-resolution-request?environmentId=ENV&requestId=UUID&decision=accepted|retry`; it is scoped to the JWT identity and requires its current decision and DB permissions. Repeated identical requests are replayed; conflicting inputs or stale revisions return 409. Different JWT identities sharing a DB login have isolated request IDs. JWT and DB audit records commit with the decision. The JWT request table records identity. Decision grants can be delegated as described below; a decision audit viewer is not yet implemented.

The existing Discord attention endpoint now includes `retryAfterSeconds` and `retryNotBefore` when a matching 429 attempt provides guidance. The latter is computed from the DB attempt update time and is advisory, depends on clock accuracy and does not account for other senders. The `retry` decision immediately requeues the job and can duplicate a message; `retry_after` schedules a matching 429 attempt after its recorded guidance (worker 0226 and API 0140). Independently verify the outcome and rate limit. Prior acknowledged failures remain hidden from the attention list. The local API tests cover restricted DB login, signed test JWTs, independent authorization, identity-scoped requests, stale revisions, audit failure rollback, revocation and 429 guidance. The dashboard browser test covers two decisions, request lookup and guidance. Neither validates real Discord, real IdP nor production HA.

API migration 0140 adds `retry_after` to Discord decision requests and request lookup using the existing JWT and DB retry grants. It requires worker migration 0226 and an unchanged rejected 429 attempt with valid stored guidance; see the worker README for deployment order and rate-limit limitations. The existing grants gain this additional choice.
