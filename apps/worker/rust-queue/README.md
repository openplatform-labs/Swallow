# Experimental worker operations

**Current deployment guidance:** apply API and worker migrations in order through the latest version before deploying matching binaries. Read [the current implementation status](../../../RUST_IMPLEMENTATION_STATUS_KO.md) for migration prerequisites, role identity, grants, options and known limitations. This is not yet full Novu compatibility or verified production HA. Do not blindly replay older permission migrations: once newer permissions are granted, old constraints can fail and old functions can weaken authorization. Use `migrate-worker` to track each service migration history as described below. Review existing schemas before changing them.

## Service migration history

Use a trusted migration DB login and `DATABASE_URL`. Apply each service in dependency order: `migrate-worker apply api ../../api/rust-api/migrations`, `migrate-worker apply worker migrations`, then `migrate-worker apply ws ../../ws/rust-ws/migrations` (paths are relative to this directory). The legacy `migrate-worker apply migrations` remains an alias for worker. The runner validates contiguous files and SHA-256 history, serializes concurrent runs with a PostgreSQL advisory transaction lock, and applies all pending SQL and history rows for the selected service atomically. API, worker and WS have separate history tables and share the same database advisory lock. Re-running skips recorded files; altered or missing historical files are rejected. Migration 0023's own transaction wrapper is incorporated into the runner transaction. Other standalone transaction-control lines are rejected. Protect the migration directory, history table, public schema and function owners; manual SQL bypasses this history. Applying all pending migrations together can hold locks for a long time. Cross-service atomicity, automatic dependency validation, recovery after uncertain commit acknowledgement, production permissions and scale are not handled or verified.

An existing untracked service anchor table is not automatically migrated. Only after independently verifying the existing schema and exact applied worker version may a trusted administrator run `migrate-worker baseline SERVICE MIGRATION_DIR VERSION I-VERIFIED-THE-EXISTING-SCHEMA`, then `apply`. Baseline records local checksums without inspecting or changing the schema: an incorrect version or mismatched files can hide missing migrations. Anchor-table detection is not a comprehensive discovery of every possible partial schema. A disposable PostgreSQL test covers real API, worker and WS migrations in dependency order, reruns, checksum mismatch, rollback, concurrent runners and explicit baseline; production upgrade and restoration are untested.

`send-delivery-alert ENV GRACE_SECONDS HEARTBEAT_MAX_SECONDS COOLDOWN_SECONDS` sends enabled unhealthy environment checks to configured Slack and/or Resend email destinations. Apply worker migrations in order through `0094` and the relevant API migrations; see the current status document for dependencies. The sender DB login also needs an explicit `alert_send` row in `novu_rust_delivery_operator_grants` for that environment. Configure Slack with `SWALLOW_ALERT_SLACK_WEBHOOK` or `SWALLOW_ALERT_SLACK_WEBHOOK_FILE`; email uses `SWALLOW_ALERT_EMAIL_TO`, `NOVU_RESEND_FROM`, and `NOVU_RESEND_API_KEY` or `NOVU_RESEND_API_KEY_FILE`. Both destinations may be used together. Give each destination a stable, non-secret `SWALLOW_ALERT_SLACK_TARGET_ID` or `SWALLOW_ALERT_EMAIL_TARGET_ID` (default `default`); use a new ID if the destination changes. Environment and target IDs have restricted ASCII syntax. Only the environment and aggregate status of enabled checks are sent. Slack URLs must use the official Slack or Slack Gov HTTPS webhook hosts, and redirects are disabled. Credentials are not stored in PostgreSQL.

Alert checks are selectable independently of transport. By default the existing Resend check remains enabled. Set `SWALLOW_ALERT_RESEND_ENABLED=false` to omit it, set `SWALLOW_ALERT_QUEUE_MAX_WAIT_SECONDS` to 1–86400 to include overdue queue jobs and expired leases, and set `SWALLOW_ALERT_ATTEMPTS_ENABLED=true` to include unknown or stranded SendGrid, Resend, Twilio and FCM attempts. Booleans must be exactly `true` or `false`; at least one check must be enabled. The positional grace and heartbeat arguments are still required integers but are ignored when Resend checking is disabled. Each enabled check requires its existing migrations and DB read permissions. If a check fails, the command runs the other checks and attempts an alert naming the failed checks, then exits 1 even if a destination accepts it. Invalid thresholds fail before checking or sending. Monitor execution errors independently: a DB outage can prevent both checking and delivery. All enabled signals share a destination slot. The default cooldown can delay a second incident; optionally choose `SWALLOW_ALERT_COOLDOWN_POLICY=new-condition` after migration `0085` to bypass an accepted cooldown for a newly observed problem category. This does not bypass unknown or rejected outcomes. Checks are separate snapshots, not one atomic view. They do not detect every failure or prove receipt.

Use an authorized grant administrator to provision the exact DB login and environment, for example:

```sh
delivery-reconcile operator-grant ENV scheduler-login alert_send "change ticket"
delivery-reconcile operator-grant ENV reviewer-login alert_retry "change ticket"
```

Grant `alert_accepted` separately when needed. Bootstrap the grant administrator as described in the current status document; the management function records the login's current role OID and an audit entry. A direct three-column insert leaves the OID unset on current installations and will not authorize the login. Restrict function owners, the schema and direct table privileges.

Migrations `0090` and `0091` add optional monitoring of all unacknowledged failed queue jobs. Set `SWALLOW_ALERT_FAILED_JOBS_ENABLED=true` to include the count in alerts. `check-failed-jobs ENV` and `list-failed-jobs ENV [AFTER_JOB]` require `alert_view` and EXECUTE on `novu_rust_failed_queue_count(text)` and `novu_rust_failed_queue_list(text,uuid)`. A separately granted `queue_ack` login with EXECUTE on `novu_rust_ack_failed_queue(text,uuid,text,text)` can use `ack-failed-job ENV JOB OPERATOR REASON`. It records the current attempt/error snapshot, without changing the job or suppressing separate uncertain-delivery and Slack checks. A transition away from and back to failed, or a changed attempt count or error while failed, advances a database failure revision and returns the job to attention even if the later error is identical. An UPDATE that leaves status, attempts and error unchanged is not a new failure; identical failures before migration 0091 cannot be distinguished retroactively. Historical failures are included, overlapping checks can alert twice, and failure diagnostics are stored in the protected acknowledgement table. Do not reapply 0090 after 0091: it can replace the new acknowledgement function with an incompatible older version. Direct writes to failure revisions or changes to the trigger bypass the protection. Listings omit payload and error text, page by UUID and are not a consistent snapshot. Disposable PostgreSQL tests cover restricted logins, a directly enqueued push workflow job that the FCM worker fails before dispatch when the subscriber is absent, acknowledgement, worker reprocessing, CLI, pagination and blocked mock alert routing. A separate original/Rust server comparison triggers a real push workflow over HTTP, deletes the subscriber before processing, compares selected failure and non-delivery behavior, and then exercises the Rust failure monitoring and acknowledgement CLI. This monitoring CLI has no original counterpart in the comparison. Providers are mocked; real FCM requests, external alert receipt and all failure combinations remain untested.

## Independent database probe alert

`send-database-alert MONITOR_ENV TARGET_LABEL COOLDOWN_SECONDS` probes a target PostgreSQL connection and `SELECT 1` while storing alert reservations in a separately provisioned alert-state database. Set `DATABASE_URL` to the alert-state database and `SWALLOW_DB_PROBE_URL` to the target; place them in independent failure domains. `SWALLOW_DB_PROBE_TIMEOUT_SECONDS` defaults to 5 and accepts 1–60 seconds. Apply API/worker migrations and provision the monitor environment, `alert_send` and the selected delivery/observation function permissions in the state DB. Existing Slack and Resend settings, `SWALLOW_ALERT_SCOPED_DELIVERY`, and cooldown policy apply. Default destination IDs are `db-TARGET_LABEL`; optional `SWALLOW_DB_ALERT_SLACK_TARGET_ID` and `SWALLOW_DB_ALERT_EMAIL_TARGET_ID` override them. Use unique non-secret IDs for each target/destination. Labels accept 1–48 ASCII alphanumeric, dot, hyphen or underscore characters and are included in the alert; URLs and credentials are not.

Exit 0 means the probe succeeded; 2 means the probe failed, including when alert delivery needs review; 1 means configuration, state DB or dispatch failed. Authentication or transient latency can produce a failed probe without proving the whole DB is down. Run under an external scheduler and monitor its execution and the state DB independently. The shared PostgreSQL TLS settings apply to both connections. The probe and initial state DB connection have timeouts. `SWALLOW_DB_ALERT_OPERATION_TIMEOUT_SECONDS` limits each destination observation and each full reservation/send/result operation (default 30, range 1–300 seconds); it is not a single deadline for the whole command. An operation can time out after the provider received the request, leaving an uncertain outcome that requires the existing lease recovery and operator procedure. Database-side queries or locks may persist briefly after a network interruption, so supervise the process and DB independently. Shared failure domains, unsampled outages, unknown provider outcomes and actual recipient delivery remain limitations. `scripts/test-database-alert.sh` stops and restarts one of two disposable PostgreSQL containers and checks limited-login, a locked state row, a blocked alert slot and state-DB failure behavior; separate local mock HTTP verifies alert content and unknown recovery after a send timeout. No real external alert was sent.

For an explicit best-effort fallback when the alert-state DB cannot be reached at initial connection, set `SWALLOW_DB_ALERT_STATE_FAILURE_MODE=send-uncoordinated`; the default is `report-only`. The fallback directly sends the target probe result and state-DB failure to configured Slack and/or Resend, even when the target is healthy. It cannot consult DB permissions, reserve slots, apply cooldowns or preserve audit/outcome state. Every invocation uses a new Resend idempotency key, so repeated or concurrent invocations can duplicate messages; unknown outcomes cannot be reconciled by the DB tools. It does not retry internally, attempts both destinations independently and returns 1 even if a provider accepts. A connection failure includes authentication failures. The fallback is not used for errors after the state DB connection succeeds, where a prior request may already have started. Protect the scheduler, configuration and credentials and independently monitor its exit status. Mock HTTP tests cover the two fallback transports and independent failure handling; the actual CLI fallback against external providers and multi-host outages are not tested.

Migration `0094` replaces the raw diagnostic text in queue and Slack acknowledgement unique indexes with a fixed-size SHA-256 digest. This permits long, incompressible diagnostics that exceeded PostgreSQL B-tree entry limits; the full diagnostic remains in the restricted audit row, and the digest is also sensitive derived data. The migration rebuilds indexes and may hold locks, so assess database size and schedule before applying. Do not replay 0091/0092 afterward. A digest collision is theoretically possible. Disposable PostgreSQL 17 tests reproduce the prior failure and verify upgrade, reapplication, existing records, idempotence and recurrence; production scale and other PostgreSQL versions have not been tested.

Migration `0089` adds environment-scoped aggregate functions for queue, attempt, Resend and Twilio health. Set `SWALLOW_ALERT_CHECK_SCOPED_ACCESS=true` for the alert command or `SWALLOW_MONITOR_SCOPED_ACCESS=true` for `check`, `check-queue`, `check-resend`, `check-twilio`, and provider metrics commands. Provision `alert_view` and EXECUTE only on the functions used: `novu_rust_queue_health(text,integer)`, `novu_rust_delivery_health(text)` and `novu_rust_provider_health(text,text,integer,integer)`. These checks do not require direct queue or attempt-table reads. Slack checks use the separate `slack_view` and `SWALLOW_ALERT_SLACK_SCOPED_ACCESS` settings. The default false retains direct queries. Checks are separate snapshots and not a guarantee of delivery. Scoped health, environment isolation, permissions, equivalence and CLI behavior using a restricted DB login were tested against disposable PostgreSQL; operational privileges and external alert receipt remain unverified.

With migration `0093`, the `new-condition` cooldown policy also observes recovery: after a successful check clears a condition from an accepted slot, the same condition can bypass cooldown if it recurs. Grant the sender EXECUTE on `public.novu_rust_observe_alert_conditions(text,text,text,integer,integer)` and its environment's `alert_send`. Failed or disabled checks are not considered recovered; dispatching, unknown or rejected slots are not changed. A recovery and recurrence between scheduled observations is not detected, and concurrent schedulers can observe different snapshots. An observation failure is reported with exit 1 while other eligible alert dispatches are still attempted. The default destination policy does not use this function. Disposable PostgreSQL verifies restricted-login CLI recovery, repeated incident reservation, failed/disabled checks and unknown-slot preservation; actual external alert delivery and distributed failures remain unverified.

With migration `0088`, set `SWALLOW_ALERT_SCOPED_DELIVERY=true` to reserve and finish alert attempts through the restricted `novu_rust_reserve_alert(text,text,text,integer,integer)` and `novu_rust_finish_alert(text,text,text,uuid,text,integer)` functions. Grant EXECUTE on both and the environment-specific `alert_send` permission to the sender; the delivery path then needs no direct alert-slot or attempt table privileges. Health checks still need their own access. A reservation is bound to the authenticated session login and its role OID: another login cannot finish it. Revoking `alert_send` prevents new reservations but an already-started request can finish if that login retains function EXECUTE. Revoking function access or stopping the process can instead leave the result unknown. Shared DB logins do not identify individuals and `alert_send` is not target-specific. Direct table access and old binaries bypass this boundary; protect the function owner, schema and tables. Default `false` retains the existing direct-table path. Docker PostgreSQL tests cover scoped concurrent senders, revocation, late responses and mock Slack/Resend delivery using a restricted DB login; production roles and external alert receipt remain unverified.

The command initializes and dispatches each configured destination independently: a malformed destination or dispatch error does not prevent attempting the other one. It returns exit 1 if any configuration or dispatch operation failed, even if another channel was accepted or the checks were healthy; exit 2 indicates a destination requiring review when no other error occurred. Generic errors avoid logging credentials. Inspect each destination and monitor exit 1 separately; a shared database or health-check failure can still prevent all delivery. The CLI tests exercise independent configuration and dispatch failures against blocked database slots; actual external delivery in a partial-failure case has not been tested.

PostgreSQL reservations fence concurrent schedulers. Accepted attempts have a 60-86400 second cooldown measured from dispatch start; a new incident during cooldown may be delayed. Rejected and ambiguous attempts block further sends until operator review. Expired leases become unknown when a later run checks the slot; late responses cannot overwrite recovery. A transport failure may still mean provider acceptance. Both channels are attempted independently, subject to shared database and health-check availability. Provider acceptance is not proof of user receipt. Run through an external scheduler and independently monitor command errors, missing executions, and database outages.

`delivery-reconcile check-alert-delivery ENV` reports unknown, rejected, and expired slots (exit 2; errors exit 1). `alert-status ENV` shows up to 100 non-secret targets. A DB login explicitly granted `alert_retry` or `alert_accepted` and EXECUTE on `public.novu_rust_resolve_alert(text,text,text,text,text,text)` (migration `0086`) can use `alert-resolve ENV CHANNEL TARGET retry|accepted OPERATOR REASON` without direct alert table access; audit rows identify the DB session user. With migration `0087`, `SWALLOW_ALERT_STATUS_SCOPED_ACCESS=true`, `alert_view` and EXECUTE on `public.novu_rust_alert_status(text)` and `public.novu_rust_alert_health(text)`, status and health use environment-scoped functions instead of direct table reads. Accepted is limited to unknown outcomes. Before retrying, independently verify non-acceptance: a mistaken retry can duplicate an alert. Protect grant and audit tables and direct SQL access; shared DB logins do not identify individuals, and audit tampering is unresolved. See the grant-lock deployment instructions below for the limits of revocation. Mock HTTP and disposable PostgreSQL cover both destinations, cooldown, concurrency, stale-response fencing and audited recovery. Real Slack or alert-email delivery, external schedulers and full HA have not been tested.

# Experimental PostgreSQL queue primitives

The experimental `slack-worker` sends **standalone** PostgreSQL chat jobs through Slack `chat.postMessage` using `NOVU_SLACK_ENVIRONMENT_ID` and either `NOVU_SLACK_BOT_TOKEN` or `NOVU_SLACK_BOT_TOKEN_FILE`, plus `DATABASE_URL`. Apply worker migrations through `0071`. The token is read once, uses the shared 16 KiB single-line secret rules, and never goes in the queue or attempt record. Run under a supervisor. A job has kind `experimental_slack_chat` and payload `{"channel":"C123","text":"hello","blocks":[...]}`; `blocks` is optional, and `channel` accepts a Slack channel or user ID. The caller must authorize and enqueue the job in the correct environment. Payloads contain message text and target in PostgreSQL and must be protected. This is **not connected to workflow execution, subscriber credentials or Novu chat/integration APIs**, and has no subscriber deletion or preference revalidation. It supports text and native block arrays only; rich-card rendering, provider overrides, webhook targets, all validation and full original behavior remain unimplemented. Use only in an isolated evaluation environment.

The worker records `dispatching` before posting and fences state updates with a 60-second lease. Expired leases before the attempt return to pending; after an attempt they become `unknown` and are not automatically resent. A `2xx` Slack response is accepted only with `ok: true` and nonempty channel and timestamp. Slack `fatal_error`, `internal_error`, network errors, 5xx, redirects, malformed or oversized replies and incomplete success are unknown; a small list of known rejection errors and HTTP 4xx other than 408 and 409 are rejected. Provider responses and tokens are not logged. These outcomes describe API acceptance, not a person's reading. [Slack documents](https://docs.slack.dev/reference/methods/chat.postmessage) that some errors can occur after partial success. A worker or DB failure still requires external supervision; no Slack callback reconciliation exists.

`delivery-reconcile check-slack ENV` counts unknown, rejected and stranded attempts, returning 2 if any require review, 0 when clear, and 1 on errors. Set `SWALLOW_ALERT_SLACK_JOBS_ENABLED=true` to include those counts in configured operational Slack/email alerts. To make an explicit, audited operator decision, provision `slack_retry` or `slack_accepted` in `novu_rust_delivery_operator_grants` for the exact environment and DB login, grant that login EXECUTE on `public.novu_rust_resolve_slack(text,uuid,text,text,text)` from migration `0083`, and run `delivery-reconcile slack-resolve ENV JOB retry|accepted OPERATOR REASON`. These permissions are distinct from existing notification or alert decisions; `accepted` is allowed only for an unknown attempt and is an operator assertion without a provider ID. Retry permits unknown or rejected outcomes; independently confirm non-acceptance first, because an incorrect retry can duplicate a message. The audit is not tamper-proof and DB access must prevent direct modifications. Apply `0071` after `0067` and `0068`; do not reapply older grant-constraint migrations after issuing Slack grants. Use `list-slack ENV [AFTER_JOB]` with `slack_view` and the 0081 list function to identify affected jobs without payloads; this is not provider evidence.

Worker migration `0092` preserves existing Slack workflow acknowledgements but adds a revision so the same pre-dispatch failure or missing-endpoint result is counted again after a state transition. Changes to attempts or error also advance the revision; a no-op update does not. Similar recurrences before migration cannot be distinguished retroactively. Apply `0092` before deploying the updated tools, replace old monitoring binaries, and do not reapply `0081`, `0082` or `0084` afterward because they overwrite the revised functions. Protect the revision trigger and tables from direct writes. Disposable PostgreSQL tests cover upgrade and reapplication, recurrence in both categories and existing Slack workflow/CLI behavior; production upgrade and all concurrent failures remain unverified.

Docker PostgreSQL and loopback HTTP tests cover simultaneous claims, pre/post-dispatch expiry, late-response fencing, tenant scope, secret file configuration, monitoring and audited decisions. A pinned Novu provider comparison covers two channel/user core payloads with mocked HTTP. Real Slack delivery, full original errors, channel workflow and management APIs, arbitrary provider configuration, load and full HA are not tested or implemented.

`twilio-projection-worker` optionally projects Twilio SMS callbacks to the separate `twilio_delivery_result` on queue jobs and SMS history. Apply worker migrations through `0069` and API Twilio webhook migrations through `0007`, configure the attempt-specific signed callback URL, `DATABASE_URL` and `NOVU_TWILIO_ENVIRONMENT_ID`, and run under a supervisor. A current accepted attempt with a known provider SID and matching attempt-specific callback is required. Results are `delivered`, `failed`, `pending`, `conflicting`, or `unknown`; missing, legacy, unrecognized, or ambiguous evidence is unknown. With a current dispatch-bound callback, contradictory terminal statuses, different SIDs, a duplicate provider SID within the environment, or multiple accounts conflict. Callbacks can be delayed or lost, so later scans may change results; the value is a provider report, not proof of reading. The projection leaves queue status, message status and dispatch state unchanged and does not retry or automatically resolve an unknown attempt. A retry via the updated reconciliation tool clears both result columns in the same transaction. Apply `0069`, then replace all old reconciliation binaries before starting the projector: old retry code does not clear the result. `sms-delivery` now also returns `providerIdKnown` and flags a mismatched SID or multiple accounts as conflict.

`delivery-reconcile check-twilio ENV GRACE_SECONDS HEARTBEAT_MAX_SECONDS` exits 2 for old non-cancelled SMS jobs whose result is not `delivered`, or an absent/stale projector heartbeat; healthy is 0 and errors are 1. Thresholds are 1–86400 seconds. `check-twilio-metrics` returns the same counts as Prometheus gauges and exits 0 after a successful query even when unhealthy. To include this check in Slack and/or email alerts, set both `SWALLOW_ALERT_TWILIO_GRACE_SECONDS` and `SWALLOW_ALERT_TWILIO_HEARTBEAT_MAX_SECONDS`; omit both to disable it. These thresholds are independent of the positional Resend thresholds and may be combined with other checks. One missing or invalid threshold fails configuration. Failed checks are named in attempted alerts and still produce exit 1. Schedule the commands externally and independently monitor DB errors, missing executions and destination delivery.

Age is measured from job `available_at`, including jobs that have not yet been dispatched; future and cancelled jobs are excluded. Old failures remain counted until resolved or removed, and an environment without SMS traffic still needs a projector heartbeat when this check is enabled. A heartbeat can be fresh while locked jobs were skipped. A provider's delivered report is not proof of reading; lost or unlinked callbacks may cause prolonged alarms. Current checks scan historical jobs and have not been load-tested. Docker PostgreSQL tests the real CLI, metrics, heartbeat, thresholds, failure isolation and a blocked destination; real Slack/email delivery of an SMS alert is not tested.

The worker scans up to 100 jobs per page, skips locked jobs, updates a per-environment heartbeat only after a full pass, reconnects on DB errors and waits 30 seconds between scans. Monitor heartbeat age, failures and process health independently; scans are not proof that locked rows were evaluated and repeated history scans have untested costs. Event evidence is limited to callbacks bound to the current dispatch; a single callback account is not verified against a stored attempt account, and older/custom callbacks may be unlinked. Duplicate-SID detection is snapshot-based and is reevaluated on later scans. Each known SID adds an indexed lookup; migration 0069 adds the index and associated write cost. Docker PostgreSQL tests synthetic records, a separate worker process, matching and conflicting SIDs, status changes, tenant isolation, row locks and retry cleanup. Real Twilio delivery/webhooks, API exposure of the result, missed callback reconciliation, load, and full HA remain untested or unimplemented. [Twilio recommends callback and periodic reconciliation](https://www.twilio.com/docs/messaging/guides/outbound-message-logging).

`NOVU_TWILIO_PROJECTION_DB_TIMEOUT_SECONDS` controls the Twilio projector's per-operation DB timeout, default 30 seconds, range 1–300. The worker also sets session-level PostgreSQL `statement_timeout` to the same value; use a direct connection or a session-affine pool, because transaction pooling can lose or leak this setting. Connection, environment check, each page, each individual projection and heartbeat write are timed separately; a whole scan can take longer. On timeout the connection driver is stopped and the worker reconnects after two seconds. Tune the threshold for expected DB latency: too low can repeatedly abort progress. An interrupted transaction may remain on the server until the server detects disconnection, especially during a network partition. Docker tests exercise a blocked heartbeat, timeout and reconnection, two worker processes, and a database-container restart. These are selected failure scenarios, not proof of production failover or network-partition recovery; monitor the heartbeat and process externally.

For the Resend worker, `NOVU_RESEND_API_KEY_FILE` can reference a mounted secret file instead of `NOVU_RESEND_API_KEY`. Setting both fails startup. The file is read once at startup; no automatic rotation or external secrets manager is implemented. Restrict file and process access.

The FCM worker also supports mounted credentials: `NOVU_FCM_ACCESS_TOKEN_FILE` for a single-provider token, `NOVU_FCM_PRIVATE_KEY_FILE` for a multiline PKCS#8 PEM service-account key, and `NOVU_FCM_INTEGRATIONS_FILE` for the existing multi-integration JSON (which may be formatted across lines). Each replaces its same-named inline variable; setting both sources for the selected credential is an error. The integration map still takes precedence over single-provider settings, and within single-provider mode a configured access token takes precedence over service-account fields. Unselected settings are not checked. The token uses the shared 16 KiB single-line secret rules; the PEM is limited to 64 KiB and the JSON to 1 MiB, including when passed inline. Files must be nonempty UTF-8 without NUL. Malformed, unavailable or oversized files fail startup without printing file paths or secrets. Credentials are read once; operators must protect file permissions, mounts and process memory, and restart workers to rotate them. Static access tokens do not auto-refresh. Docker PostgreSQL tests worker startup with local fixture token, generated PEM and multi-integration JSON plus source conflicts and oversized input; no real FCM request or secret-manager integration is tested.

`src/resend.rs` provides a bounded Resend email HTTP adapter with optional idempotency keys and mock HTTP tests. The `resend-worker` consumes `experimental_resend_email` jobs. With migration `0061`, a workflow with `email_provider=resend` creates those jobs; the restricted experimental API can change that setting and the worker rechecks subscriber identity, preferences and workflow before rendering. Standalone manually prepared jobs have no such revalidation; integration management and automatic webhook state updates remain incomplete. Apply worker migrations through `0062`, set `DATABASE_URL`, `NOVU_RESEND_ENVIRONMENT_ID`, `NOVU_RESEND_API_KEY`, `NOVU_RESEND_FROM`, and optionally `NOVU_RESEND_SENDER_NAME`. Queue payloads contain recipient addresses and content; credentials are passed in the environment. Restrict both. The worker records each attempt before dispatch using `swallow/<job UUID>` as the idempotency key. Expired pre-attempt leases requeue; expired attempts, network failures, malformed success responses, HTTP 409 and 5xx remain unknown without automatic retry. Other non-2xx responses are rejected. `check`, `list`, and manual `retry`/`accepted` include these attempts; Resend manual retry requires migrations `0060` and `0063`. The operator must independently verify non-acceptance before retrying or acceptance before marking accepted. Resend retains idempotency keys for [24 hours](https://resend.com/docs/dashboard/emails/idempotency-keys); a later retry can duplicate mail. Direct byte attachments (including CID) and string headers are supported; attachments are limited to 20 MiB of raw data. Workflow-trigger attachments, provider custom data and explicit attachment dispositions remain unsupported. Mock HTTP and disposable PostgreSQL cover a basic send and crash recovery; on 2026-11-14 a real adapter send first returned HTTP 403; a retry with a different sender domain was accepted by Resend. The user confirmed mailbox receipt; the limited live workflow and mocked original-server comparison are described below. Full Novu compatibility remains unverified. This standalone path is not production-ready.

An explicitly ignored `resend::tests::live_send` test sends a real message when `NOVU_RESEND_API_KEY`, `NOVU_RESEND_FROM` and `NOVU_RESEND_TEST_TO` are set. Run it only when an actual send is intended: `cargo test --locked --lib resend::tests::live_send -- --ignored`. It checks provider acceptance only, not mailbox receipt or the workflow path; each run generates a new idempotency key and may send another message.

`./scripts/test-resend-live.sh` also sends a real message and requires the same three environment variables plus Docker. It creates a disposable PostgreSQL container, inserts a trigger job directly, runs the Rust workflow and Resend workers, verifies provider acceptance and stored statuses, and removes the container. It does not run the API HTTP trigger, management API, webhook or original Novu, and it does not verify mailbox receipt. One successful run was performed on 2026-11-14 and the user confirmed receipt; each execution may send another message.

`cargo test --locked --test reference_resend_source -- --ignored` executes the original checked-out Resend provider's `sendMessage` with a mocked SDK and empty bridge data, comparing four selected option mappings to the Rust request. The test maps `replyTo`, attachment bytes and CID to HTTP fields itself; it does not exercise the original SDK serialization, full server, passthrough, the full attachment and header contract or webhooks. The checkout's provider source was verified against the pinned Novu commit.

With a built pinned source checkout and Docker, `NOVU_REFERENCE_SOURCE=/absolute/path cargo test --locked --test reference_resend_wire -- --ignored` runs the original provider and actual Node SDK with `fetch` mocked. Two selected request bodies match. For byte attachments the SDK serializes a JSON Buffer object, while Rust sends a Base64 string described by the API documentation: the raw request is different, and real attachment delivery has not been verified. Rust's queue also adds an idempotency header absent from the original default request. This comparison does not run the full Novu server.

The API harness `NOVU_TEST_PREFERENCE_DELIVERY=1 NOVU_TEST_SNOOZE_ONLY=1 NOVU_TEST_RESEND_ONLY=1 ./scripts/test-reference-subscribers.sh` (from `apps/api/rust-api`, with `NOVU_REFERENCE_SOURCE` set to a built pinned checkout) compares one trigger through both original and Rust API/workers to a mocked Resend request. The request body and selected `sent`/provider-ID history matched; Rust's additional delivery state was checked separately. Worker migration `0068` installs `public.novu_rust_lock_operator_grant(text,text)` as a security-definer function, with a fixed `pg_catalog` search path and an explicitly qualified `public` grant table. Install it in a database using that schema as a trusted owner with permission to lock grant rows. The function owner and the `public` schema must be protected from untrusted modification. It checks only the caller's `session_user`, environment and decision, takes a shared row lock until the operation's database transaction ends, and has no public EXECUTE privilege. A database administrator must grant EXECUTE explicitly to each scheduler/operator login or its role, for example:

```sql
GRANT EXECUTE ON FUNCTION public.novu_rust_lock_operator_grant(text,text) TO "scheduler-login";
```

Grant rows still need to be provisioned independently; function execution does not grant an action. The caller does not need UPDATE or DELETE on the grants table. A committed revocation cannot overtake an already-locked database decision or reservation, and a new operation after revocation is denied. Revocation may wait for long transactions; a reservation committed before revocation can still start or finish its external request afterward. Old binaries do not take this lock, and privileged direct SQL bypasses the tool. Apply migrations and grant EXECUTE before upgrading; remove or stop old binaries to obtain the stated guarantee. Docker PostgreSQL verifies the lock and revocation using a restricted session; production role provisioning, lock timeouts and all network failures remain untested.

Use the audited `operator-grant` command described above to bind the current role identity; grant only the required action and environment. New audit records contain the authenticated DB session user and effective `current_user`, plus the caller-supplied operator label and reason. Historical records have a null session user and are not backfilled. The caller needs execute access to the restricted grant-lock function described below; only administrators should change grant rows or audit records. This crate contains experimental Rust/PostgreSQL queue and worker implementations used by the Rust API. It is **not a fully Novu-compatible worker**. Do not deploy it as a replacement. The target is 100% compatibility with the selected Novu version, but this crate does not establish that compatibility.

The migration defines a queue table. The library exposes transactional enqueue (including delay), per-kind claim with `SKIP LOCKED`, lease renewal, token-fenced completion, failure and retry, pending-job cancellation scoped by environment, and explicit recovery of expired jobs. Claim and recovery policy are deliberately separate: automatically retrying every expired job could change Novu's delivery semantics or duplicate external side effects. The shared [`trigger_gate`](../../api/rust-contracts/src/trigger_gate.rs) module reproduces a small, explicitly bounded part of the stored-workflow trigger decisions from the reference source; it does not implement the full API or workflow engine.

Migration `0053` adds `delivery_state` to experimental email, SMS and push history: `not_attempted`, `dispatching`, `in_progress`, `accepted`, `rejected` or `unknown`. `accepted` means provider acceptance, not delivery. Expired in-flight attempts are reflected as `unknown`; existing historical rows without reliable attempts remain unknown. Novu-compatible `status` is retained separately and can still read `sent` without proof of delivery. This state is currently database-only; webhooks, actual delivery confirmation and alerting are not implemented. Each attempt adds history updates, and FCM target groups add an aggregation query.

SMS retries require API webhook migrations through `0007` and permission to read the event table, even without automatic callback configuration. A different dispatch or environment alone does not block a known-dispatch retry; legacy job-only evidence or unknown dispatches block conservatively. Missing evidence does not prove non-acceptance. The tool requires privileged DB access, records the supplied operator, DB user and reason, and serializes conflicting decisions; the operator name itself is not authenticated. Restrict DB and audit-table update/delete privileges separately and do not put secrets or PII in the reason. After the last unknown FCM attempt is accepted, a job failed solely for uncertainty resumes any unattempted prepared targets; other failure reasons are preserved, and retries are refused for them. Standalone FCM acceptance may leave the job failed, and actual provider testing, comprehensive delivery confirmation and production operator RBAC are incomplete.

A UUID alone cannot authenticate a dispatch. Treat the proof as a secret: it is sent to SendGrid and through the webhook, and a party that obtains both ID and proof can replay them. Protect provider access, transport and logs. Signed events are linked only when that ID and proof match a dispatch registered for the same job and environment; missing, malformed or mismatched IDs or proofs stay unbound. Pre-upgrade events are treated as unverified even if they already contain an ID; replay of the same event ID does not retroactively verify them. `delivery-reconcile email-dispatch-evidence ENV JOB` groups up to 100 event/dispatch pairs without revealing recipient hashes and errors if there are more. An event does not prove all recipients received the email. The API locks associated jobs in ID order while recording a signed batch, serializing with these checks. Upgrade every API instance before the worker and reconciliation tool; older APIs do not take these locks and older workers do not honor proof verification. Suspend retries until all instances have been upgraded. Apply API migrations through `0009` and worker migrations through `0058`; the email worker and reconciliation DB roles need read access to the event and audit tables, and the API role needs queue row-lock privileges. Missing/deleted message links, overridden message IDs, callbacks arriving after the dispatch check, absent events and actual SendGrid behavior remain unresolved. SendGrid may retain custom arguments long-term; the UUID and bearer proof require a retention policy and strict access control. A refused command is not separately audited.

An experimental worker loop supports the limited in-app and Inbox prototype described in the [API README](../../api/rust-api/README.md). Database failures still terminate the process and require an external restart; there is no attempt limit for crash recovery. Queue completion, failure, retry and renewal validate the lease after taking the row lock. Repeated expiration under sustained contention remains possible; throughput, concurrent behavior and the retry policy have not been compared with Novu.
