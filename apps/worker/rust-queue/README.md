# Experimental PostgreSQL queue primitives

This crate is an isolated starting point for a Rust/PostgreSQL rewrite. It is **not a Novu-compatible worker** and is not wired into the existing service. Do not deploy it as a replacement. The target is 100% compatibility with the selected Novu version, but this crate does not establish that compatibility.

The migration defines a queue table. The library exposes transactional enqueue (including delay), per-kind claim with `SKIP LOCKED`, lease renewal, token-fenced completion, failure and retry, pending-job cancellation scoped by environment, and explicit recovery of expired jobs. Claim and recovery policy are deliberately separate: automatically retrying every expired job could change Novu's delivery semantics or duplicate external side effects. The shared [`trigger_gate`](../../api/rust-contracts/src/trigger_gate.rs) module reproduces a small, explicitly bounded part of the stored-workflow trigger decisions from the reference source; it does not implement the full API or workflow engine.

An experimental worker loop supports the in-app prototype described in the [API README](../../api/rust-api/README.md). It atomically creates simple subscriber and message records and completes a job; it is not compatible with the Novu Inbox. On startup and at most every five seconds, this worker requeues expired leases **only for its in-app job kind**; other job kinds still require an explicit recovery policy. A malformed job or an input unsupported by the experimental renderer is recorded as failed without storing the payload in the diagnostic, and the worker continues. Database failures still terminate the process and require an external restart; there is no attempt limit for crash recovery. This is an experimental safety policy, not a verified reproduction of Novu's job failure or retry behavior. The limited interpolation implementation can be checked against the reference `handlebars@4.7.10` by installing that package in a temporary directory and running `NODE_PATH=/path/to/node_modules cargo test --test reference_template -- --ignored`. There is no scheduler process, cancellation of running work, generic queue deduplication, general retry/backoff, tenant authentication or complete workflow integration with external providers. In particular, a lease cannot prevent an already-started external call from completing after lease expiry. Consumers must decide their side-effect and recovery policy. The migrations are initial development artifacts, not a production migration system; run them only on an isolated database.

Overlapping in-app batches acquire transaction-scoped advisory locks in sorted hash-key order before subscriber row locks, preventing opposite recipient order deadlocks between these workers while preserving recipient processing order. This adds one query per job and one lock per distinct subscriber hash; collisions can serialize unrelated work. If a lease expires while waiting or processing, the worker rolls the transaction back and continues; periodic recovery can requeue the job. Queue completion, failure, retry and renewal validate the lease after taking the row lock. Repeated expiration under sustained contention remains possible; throughput, concurrent behavior and the retry policy have not been compared with Novu.

Run static checks with `cargo test` and `cargo clippy --all-targets -- -D warnings`. To launch a disposable PostgreSQL 17 Docker container, run `./scripts/test-postgres.sh`; it binds a random loopback port and removes the container on exit. The script runs both the queue contract and a test that starts the actual in-app worker to exercise lease recovery, rollback and failure isolation.

Alternatively, the integration test deliberately **drops and recreates** `novu_queue_jobs`; run it only against a disposable PostgreSQL database:

```sh
TEST_DATABASE_URL='postgresql://USER:PASSWORD@localhost:5432/DISPOSABLE_DATABASE' \
  cargo test --test postgres -- --ignored
```

The integration test is ignored by default so an unset database is not mistaken for a successful database test. For architectural context and compatibility requirements see [the design record](../../../RUST_POSTGRES_DESIGN_KO.md).

The in-app worker also processes `experimental-in-app-unsnooze` jobs with `subscriberId` and `notificationId` payload fields. It locks the subscriber, clears the snooze, makes the message unread, appends the delivery timestamp and completes the job atomically. Manual unsnooze cancels one matching pending job. The experimental API creates these jobs; reference retries and execution details remain unsupported. Each new in-app message or automatic unsnooze attempts to add an event to `0030_experimental_ws_events.sql` in the same transaction. `0031_experimental_ws_best_effort.sql` drops event-write failures without rolling back the message, matching the reference queue's best-effort policy. The experimental WS service can deliver a limited notification and counts from these events; reliable replay is not implemented. The worker checks for due unsnooze jobs before in-app jobs and performs an additional orphan-job query when none are due.

The single-step prototype uses migration `0033_experimental_in_app_step_active.sql` to distinguish an existing inactive step from the absence of steps. New-format jobs examine the current flag and `has_steps` at processing time; with no active step they update the subscriber but create no in-app message or step outcome. Older jobs retain their existing behavior. Migration `0034_experimental_notifications.sql` adds a partial notification record even without an active step; the full reference notification model remains incomplete.

The worker inserts one experimental notification per accepted recipient, including when the single in-app step is inactive or channel preferences suppress delivery. New messages refer to that notification; subscriber deletion leaves notification history. The reference comparison covers selected fields, active and inactive steps, message linkage and subscriber deletion. The table does not implement topics, workflow-run API, all reference fields, legacy-data backfill or full failure semantics; notification/message/job completion are committed together in Rust, unlike the original multi-stage workflow. Each recipient adds a notification insert and an index write.

`src/sendgrid.rs` provides an experimental standalone SendGrid HTTP adapter for HTML email, including global/EU endpoints, basic recipient lists, sender, reply-to, headers and Novu tracking arguments. The original provider wire body is compared in `tests/reference_sendgrid.rs`; local HTTP tests cover one-shot submission, 429 and redirects. It is connected to the experimental environment-scoped queue consumer and the limited manually configured email workflow step described below, but not to integration management or Novu delivery status. Dynamic template data, string alternatives and byte-array attachments are supported by the adapter, with selected request bodies compared to the original provider. Trigger attachment handling, arbitrary alternative binary content, provider passthrough, webhook handling and Novu-compatible retry and recovery are unsupported; no real provider delivery has been tested. Never treat a transport error as proof that a message was not accepted. Run the reference comparison with `NOVU_REFERENCE_SOURCE=/path/to/built/reference cargo test --locked --test reference_sendgrid -- --ignored`.

`src/twilio.rs` is an experimental SMS adapter supporting US/EU endpoints, account-token or API-key Basic authentication and form-encoded to/from/body. Three cases compare the built original provider's endpoint, request fields, credentials and response; a local mock exercises both authentication modes, 201, 429 and redirect rejection. Run `NOVU_REFERENCE_SOURCE=/path/to/built/reference cargo test --locked --test reference_twilio -- --ignored` for the original comparison.

`src/fcm.rs` provides experimental FCM message planning and a bounded HTTP v1 sender using a caller-provided OAuth access token or service-account credentials. Seven comparisons check the original provider's Firebase message plans; four compare the original firebase-admin's validated HTTP message conversion. Local HTTP tests check token-by-token multicast submission and 200/429 results. Limited manually configured workflow and queue processing are described below; FCM-only subscriber credentials are described below; integration management APIs are not connected. Service-account OAuth uses an RS256 assertion, the original Firebase Admin scope set and token endpoint, and caches tokens until five minutes before expiry; concurrent refreshes are serialized. Original google-auth-library claims and a local OAuth-to-FCM mock were compared using generated test keys. Private keys and tokens remain in process memory; credential rotation, real Google OAuth, Android/APNs/WebPush options, exact multicast result/error behavior, retries and real FCM delivery are not implemented or verified. Unsupported platform fields are rejected at HTTP conversion. Multicast sends sequentially, one request per token; a transport failure is ambiguous. Run `NOVU_REFERENCE_SOURCE=/path/to/built/reference cargo test --locked --test reference_fcm --test reference_fcm_wire -- --ignored` for the provider source comparisons. The OAuth comparison also requires OpenSSL: `NOVU_REFERENCE_SOURCE=/path/to/built/reference cargo test --locked --lib google_oauth::tests::original_google_auth_claims_match -- --ignored`.

`fcm-worker` consumes `experimental_fcm_push` jobs; manually enqueued jobs require migrations `0001` and `0045`, while workflow jobs require all migrations in order. Configure `DATABASE_URL`, `NOVU_FCM_ENVIRONMENT_ID`, `NOVU_FCM_PROJECT_ID`, and either `NOVU_FCM_ACCESS_TOKEN` or `NOVU_FCM_CLIENT_EMAIL` plus PKCS#8 PEM `NOVU_FCM_PRIVATE_KEY`. The job payload uses the snake_case `Push` fields: `title`, `content`, `targets`, `payload`, `overrides` and `provider_data`; it contains device tokens and content but no provider credentials. The worker records one attempt before each target request, requeues remaining targets after each result and marks an expired dispatch as unknown rather than automatically sending it again. If any target is unknown the job fails even when other targets succeeded; without unknowns, one acceptance completes the job, while all rejections fail it. A crash after recording an attempt but before requesting FCM can lose that target. Docker PostgreSQL and mock HTTP tests cover competing workers, isolation, mixed/all rejection and recovery; these queue semantics have not been compared with original Novu or real FCM. Workflow creation, message history, invalid device-token cleanup and full provider outcomes remain incomplete. Each target adds a queue lease, attempt insert and result transaction.

Migration `0046` supports one manually configured FCM workflow step and subscriber device-token row. The trigger creates a recipient job; at dispatch it rechecks subscriber, workflow and selected push preferences, reads stored devices, renders supported title and body variables, and prepares one FCM request and independent message ID per device. Prepared requests are persisted before dispatch and reused on recovery. Four original-server cases compare one and two devices, missing devices and disabled push through mocked FCM; independently generated IDs are checked only for format. Full device registration and integration management APIs, multiple integrations, push message history, invalid-token cleanup, full template/override behavior, all queued changes and original retry semantics remain incomplete or unverified. Changes after preparation do not update already prepared targets. This adds a job and outcome insert per recipient, a subscriber query and lock per preparation, an ID query per target and storage for the prepared requests.

Migration `0047` adds one manually configured FCM integration identity per environment and connects the bounded subscriber credentials API to the device row. `PUT` replaces tokens, `PATCH` appends unique tokens in order, and an empty array clears tokens; `DELETE` removes the FCM channel. The reference harness compares these operations and v1/v2 individual subscriber responses before triggering FCM delivery. The integration management API, multiple integrations, other credential fields and providers, full validation/error details, subscriber list responses and idempotent `updatedAt` behavior are incomplete or unverified. Integration activity is checked on registration but not rechecked during delivery. Subscriber deletion cascades the device row, and each individual subscriber response performs an additional channel query.

Migration `0048` adds partial per-target push message history. A message is inserted immediately before each attempt and updated with the message ID and accepted/error status after the response; `STORE_NOTIFICATION_CONTENT=true` stores rendered content. The original-server comparison covers one and two devices, a mock provider error, missing devices and disabled preferences with content storage off and on. For each system it checks that request and history IDs agree, without comparing independently generated IDs between systems. Provider error text is replaced with a fixed diagnostic, so it differs from the source. Older queued jobs without history metadata create no message, and a post-dispatch lease loss can leave `sent` history unreconciled. Full message API, fields, retention, deletion, webhooks and actual delivery remain incomplete. Each target adds a message insert and result update.

The queued-push original-server comparison checks eleven cases before dispatch preparation: changes to subscriber profile and devices, preferences, subscriber deletion and recreation, actor and context, template, and workflow deletion and recreation. It compares mocked FCM requests and selected results, including the absence of requests where applicable. In the tested recreation case both systems send to the new subscriber's device while retaining the old internal subscriber ID in job and message history; reusing external subscriber IDs can expose queued notifications to a new person. Changes after dispatch starts, integration deactivation, original cache and retry behavior, and real FCM delivery remain unverified.

`twilio-worker` consumes `experimental_twilio_sms` jobs after applying migrations `0001`, `0041` and `0043` for standalone jobs, or all worker migrations in order for workflow jobs. Configure `DATABASE_URL`, `NOVU_TWILIO_ENVIRONMENT_ID`, `NOVU_TWILIO_ACCOUNT_SID`, `NOVU_TWILIO_FROM`, either `NOVU_TWILIO_AUTH_TOKEN` or both `NOVU_TWILIO_API_KEY_SID` and `NOVU_TWILIO_API_KEY_SECRET`, and optionally `NOVU_TWILIO_REGION=eu` (default `us`). Standalone payload fields are `to`, `content` and optional `from`; no credentials belong in payloads. The worker records an attempt before sending. An expired lease is requeued only before that record exists; otherwise the outcome is unknown and is not retried automatically. A crash between the record and actual request can therefore lose a send. PostgreSQL and mock HTTP tests cover acceptance, rejection, malformed responses, competing consumers, environment isolation and both recovery paths. Integration management, full passthrough, status webhooks and original-compatible retries remain unimplemented. No real Twilio delivery has been tested, and transport or malformed-response errors can be ambiguous. Each dispatch adds an attempt insert and result update.

Migration `0042` adds a manually configured single SMS step and workflow preference. An active SMS workflow creates jobs per recipient; at dispatch the consumer rechecks the subscriber, workflow and selected preferences, chooses the first nonblank override/payload/subscriber phone, renders supported template expressions and applies SMS `to`, `from` and `content` overrides. Migration `0043` records a partial message history with missing-phone warning, provider ID and provider error status. The original-server harness compares three mock Twilio requests, a 429 rejection, missing-phone and disabled-preference cases and selected message fields with content storage both disabled and enabled. The Rust provider diagnostic is redacted and differs from the original. `STORE_NOTIFICATION_CONTENT=true` stores rendered content and was compared in those six cases. Older queued jobs without message metadata do not create history. Expired post-dispatch leases and invalid jobs can leave a message marked `sent`; recovery does not reconcile it. Novu management and message APIs, retention, execution order, provider and step overrides, integration selection, broad template semantics, actor/context changes, retries and full error contracts are incomplete or unverified. The experimental outcome remains `queued` after a send; consult queue and attempt state for the result. Each recipient adds a job and outcome insert, with a subscriber query and lock at dispatch, a message insert and result update, and extra actor/context lookups when present.

Migration `0044` adds an SMS step identifier for a bounded Twilio override subset: `to`, `from`, `content`, `body`, `statusCallback`, `applicationSid` and `messagingServiceSid`, plus the Twilio SDK message options for pricing, feedback, delivery, retention, scheduling, media and content, including supported fields in provider `_passthrough.body`. Channel, legacy provider, global provider and step provider values are layered in source order; passthrough can override the final provider request and blank destinations do not replace the resolved number. Four additional original-server cases compare legacy, conflicting step/passthrough, blank destination and typed options including repeated form keys with content storage enabled. A passthrough recipient can differ from the number recorded in message history, as in the original. Other value types and casing transformations, header/query passthrough, integration-specific selection and general nested merge behavior remain unsupported or unverified. Overrides are stored in PostgreSQL jobs.

The queued-SMS original-server comparison pauses the source standard queue, then checks ten cases including phone/profile and preference changes, subscriber deletion and recreation, actor/context changes, template changes and workflow deletion/recreation. In the tested recreation case, both systems send to the new subscriber's phone while retaining the old internal subscriber ID in the job and message history; reusing external subscriber IDs can expose previously queued notifications to a new person. Changes after dispatch begins, actor/context deletion or recreation, concurrent mutations, all cache/feature-flag modes and real provider delivery remain unverified.

`sendgrid-worker` consumes only `experimental_sendgrid_email` jobs for `NOVU_SENDGRID_ENVIRONMENT_ID`. Apply all worker migrations in order for workflow-produced jobs; standalone jobs require queue migration `0001_jobs.sql`, `0035_experimental_sendgrid_attempts.sql`, `0037_experimental_email_messages.sql`, and `0038_experimental_email_provider_result.sql`; configure `DATABASE_URL`, `NOVU_SENDGRID_API_KEY`, `NOVU_SENDGRID_FROM`, `NOVU_SENDGRID_SENDER_NAME` and optionally `NOVU_SENDGRID_REGION=eu` (default `global`). Queue payloads use the snake_case fields in `sendgrid::Email`; the experimental workflow processor creates them for configured email steps. Credentials are supplied through the process environment rather than queue payloads or the database.

The worker writes a dispatch marker before each external request. On lease expiry, jobs without a marker are requeued, while marked attempts become `unknown` and are not automatically resent. 2xx is recorded as provider acceptance, 4xx as rejection and transport/5xx as unknown; acceptance is not proof of delivery. PostgreSQL plus a local mock verifies these states, two-worker claiming, tenant separation and crash-boundary recovery. This conservative policy is not compared with Novu's retry behavior; provider webhooks, operator reconciliation, production secret management, full multi-tenant integration configuration and full workflow execution remain unimplemented. The worker can still lose a delivery when it crashes after recording the marker and before sending, and message data in jobs is stored in PostgreSQL. Per dispatch it adds a marker transaction and a result transaction; recovery locks up to 100 expired jobs per pass.

Migration `0036_experimental_email_step.sql` adds manually configured `email_subject`, `email_html`, `email_step_active`, and workflow email preference fields. A trigger for an active configured email-only workflow, or a workflow also containing the experimental in-app step, is expanded by the existing processor. It creates one SendGrid job per recipient in the workflow transaction and evaluates limited global/workflow/subscriber email preferences and renders supported variables during delivery. Missing email and preference suppression are recorded as experimental outcomes. The queue holds the template and workflow data, and the worker process receives its SendGrid key from environment variables. Configuration requires direct database setup; the Novu workflow and integration APIs do not configure it. Email-only and two-channel workflows, execution order, message history, layouts, advanced templates, preferences and error handling are not fully compatible. Before dispatch, new workflow email jobs recheck subscriber identity and email preferences and rerender with the current profile; changes after dispatch starts cannot cancel an in-flight request. No actual external send has been performed. The original-server differential harness compares two custom HTML workflows, including one CSS rule, from trigger through mocked SendGrid request; independently generated message IDs are checked only for format and consistency. The source email compiler comparison covers three simple custom HTML cases without layouts. Rust uses css-inline while the reference uses inline-css, so broader HTML/CSS equivalence remains unproven; remote stylesheets are not fetched. This adds one queue insert and one outcome insert per eligible email recipient, plus an outcome insert for skipped recipients, in addition to existing workflow queries.

Migration `0037_experimental_email_messages.sql` records partial email history for preference-eligible recipients. A missing email creates a warning record with the same selected fields observed in the original; a preference cancellation creates none. For queued mail, `sent` is the original message model's initial value and does not mean the provider accepted or delivered the message. The stored message ID is passed to the provider job. The original-server comparison covers selected fields for missing address and preference cancellation, not full message API, history retention, deletion, content storage policy, or all provider-error details. Each eligible recipient adds an object-ID query and a message insert plus an index write.

Migration `0038_experimental_email_provider_result.sql` allows a provider error status and identifier in partial email history. The SendGrid consumer writes the result and matching environment-scoped message update in the same lease-fenced transaction: acceptance sets the returned identifier, while provider or transport errors set `error` and a fixed diagnostic. A 429 mock was compared with the original API and worker; status and error ID match, but Rust intentionally does not persist the raw provider response, so the error text differs. A transport or 5xx outcome can still be externally accepted despite the local error state. If the worker loses its lease after dispatch or an invalid job fails before dispatch, message status may remain `sent`; recovery does not reconcile it. Full retry, provider webhook and original job lifecycle semantics remain unimplemented. The result transaction adds one environment- and job-scoped message update per processed email.

The experimental trigger passes a limited `overrides.email` subset to the email worker: `toRecipient`, nonempty address arrays, explicit nonempty replacement `to`, sender and reply fields, subject, HTML/text, headers and custom data. The original-server comparison covers selected append, deduplication and replacement cases through mocked provider requests. Empty replacement `to`, integration selection, IP pools, full provider/step-scoped overrides and full validation are unsupported. Override values are stored in the workflow job and applicable email job in PostgreSQL.

Migration `0039_experimental_email_step_id.sql` enables a bounded SendGrid provider/step override subset. For subject, HTML, from, sender name, address arrays and ASCII letter/hyphen header names, the worker applies channel, legacy provider, workflow provider and matching step layers in source order. The reference-server comparison checks one conflict across layers including the source provider's additional sender and header transforms. Passthrough, other providers, integration selection, arbitrary headers and all nested merge cases are not implemented or verified. Override values remain in the PostgreSQL workflow job.

Migration `0040_experimental_email_revalidation.sql` extends email outcome states. New workflow email jobs recheck the subscriber by external ID and current email preference under a subscriber row lock before dispatch, rerender the supported template with the current profile, and cancel or fail without sending when a preference is disabled or the subscriber is absent. The reference comparison pauses the original standard queue after job creation and compares changed email/name, disabled preference, deletion, enabling a preference and adding an address through mocked SendGrid. Changes after dispatch starts, deduplicated-step mode, workflow cache behavior and actor/context deletion or concurrent changes while queued are not equivalent or unverified. Queued metadata retains templates, payload, context and override values. Each dispatch adds a subscriber/preferences query and lock, message insert and template render.

New workflow email jobs store context keys and refresh the actor profile and context data at delivery; older jobs lacking context keys retain their stored context snapshot. The original-server comparison changes the actor and context after queueing and compares the mocked SendGrid output. Actor lookup adds one query when distinct from the recipient and context lookup adds one query when keys exist. Deletion, recreation, concurrent changes and all template forms remain unverified.

New workflow email jobs recheck that their workflow exists before dispatch and compare its internal ID when configured. With the reference default step-dedup flag off, a queued email uses its stored template snapshot; a deleted or replaced workflow fails without sending. The original-server comparison covers these selected cases. Reference step-dedup hydration, cache behavior, step changes and replacement where the experimental workflow has no internal ID remain unimplemented or unverified. The workflow existence lookup is included in the existing subscriber query.

If a subscriber is deleted and recreated with the same external ID before delivery, the original and Rust use the new profile and address while retaining the old internal subscriber ID in the job/message history. The comparison verifies this selected scenario. Reusing an external ID for a different person can therefore deliver a previous pending notification to that person. Concurrent deletion/recreation and the full preference and message API behavior remain unverified.
