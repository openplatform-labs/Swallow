# Optional completed attachment cleanup

Worker migration `0133` and `attachment-retention` provide an opt-in, environment-scoped cleanup of attachment bytes in completed workflow and workflow-generated Resend/SendGrid queue jobs. They do not run on a schedule. Pending, running, failed, cancelled and standalone email jobs are excluded. Completion means queue processing completed, not recipient delivery. Parent and child jobs have separate copies and eligibility; a pending child remains untouched. Existing completed jobs start their retention clock when the migration runs. Assess the migration's backfill, index creation and trigger overhead before deployment.

A DBA registers each PostgreSQL LOGIN and its role OID in `novu_rust_attachment_retention_grants` for the intended environment and grants EXECUTE only on the required functions. Example, replacing the environment and login names:

```sql
INSERT INTO public.novu_rust_attachment_retention_grants
  (environment_id, database_principal, principal_oid, can_view, can_scrub)
SELECT 'ENV', rolname, oid, true, false FROM pg_roles WHERE rolname = 'retention_view' AND rolcanlogin;
GRANT EXECUTE ON FUNCTION public.novu_rust_list_attachment_retention(text,integer,integer),
  public.novu_rust_attachment_retention_audit(text,bigint) TO retention_view;
INSERT INTO public.novu_rust_attachment_retention_grants
  (environment_id, database_principal, principal_oid, can_view, can_scrub)
SELECT 'ENV', rolname, oid, false, true FROM pg_roles WHERE rolname = 'retention_scrub' AND rolcanlogin;
GRANT EXECUTE ON FUNCTION public.novu_rust_scrub_attachment_retention(text,integer,integer,text) TO retention_scrub;
```

With `DATABASE_URL` configured for the appropriate login and TLS, run `attachment-retention list ENV MIN_AGE_SECONDS LIMIT`, `attachment-retention scrub ENV MIN_AGE_SECONDS LIMIT REASON`, or `attachment-retention audit ENV [AFTER_ID]`. Age is 0–31536000 seconds, limit is 1–100. Listing returns metadata only; scrubbing removes the relevant payload field and records the actor, job and non-secret reason atomically. A scrubbed job cannot normally be requeued or have its payload restored. Choose the age and batch size only after evaluating investigation and replay needs. Empty batches do not prove no eligible rows exist because locked rows are skipped. If a scrub response is lost or times out, reconcile audit and job states before retrying: a new call can scrub a different batch. Grant administration itself is not audited; database owners and privileged direct changes can bypass controls. Shared DB logins do not identify an individual operator.

This does not erase old PostgreSQL row versions, WAL, replicas, backups, logs, provider copies, or copies outside the named fields and job kinds. It does not encrypt attachments or guarantee secure deletion. Protect all such copies and set separate retention and recovery policies. Docker PostgreSQL tests cover role and environment isolation, exclusions, concurrent scrubbing, locked rows, audit rollback, revocation and replay prevention; production load, backup removal and HA failover are untested.

Attachment-job version fence (worker migration `0132`): the current API labels nonempty attachment-bearing workflow jobs `experimental_static_in_app_attachments_v1`; current in-app workers claim that kind and the original kind in one ordered query and recover expired leases for both. The migration's trigger also changes pending legacy-kind jobs containing nonempty or malformed `emailAttachments` into the new kind, including jobs produced by the prior attachment-capable API and expired legacy jobs returned to pending. It migrates existing pending rows, while ordinary legacy jobs remain unchanged. Old workers only claim the legacy kind and therefore cannot claim these fenced pending jobs. Queue health still counts all kinds; configure and monitor it so missing upgraded workers do not leave work waiting silently.

This does not stop an old worker that already claimed a legacy attachment job before the migration, nor an external writer that disables/bypasses the trigger or manually changes job state. Before rollout, stop or drain all old in-app workers and inspect any running legacy attachment jobs and downstream delivery evidence; a running job may already have created or sent a message without attachments. Apply 0132, deploy the updated workers and API, and allow normal lease recovery only after investigating uncertain in-flight work. Do not blindly requeue or replay externally dispatched email. If only old workers remain, fenced jobs remain pending; rollback to them alone does not process attachment jobs. The migration scans/updates pending queue rows and installs a trigger on inserts and selected updates, so assess locking and load before deployment. The generic expired-job recovery is safe here only for the pre-fanout workflow job; channel workers have separate external-delivery recovery rules. Disposable PostgreSQL tests cover upgrade of existing pending jobs, old/new claim isolation, malformed metadata, ordinary and attachment job ordering, legacy and new lease recovery, and an actual new worker process. The API-to-two-mock-provider attachment flow was rerun. Full multi-host rollout, DB failover and production load remain untested.

Experimental workflow email attachments: the trigger API accepts up to 10 attachments and 512 KiB of decoded data in total, using strict standard Base64 strings or JSON-serialized `Buffer` bytes. Each attachment requires `name` and `mime`; optional `cid`, `disposition` (`inline` or `attachment`) and `channels: ["email"]` are supported. Other channel combinations, unknown fields and invalid data are rejected at trigger time. The Resend adapter currently rejects any explicit disposition during dispatch; SendGrid supports these dispositions. The API can therefore accept a request that later fails at the Resend worker. Original Novu accepts other Base64/Buffer inputs and uploads files to external storage; this subset stores decoded bytes in the PostgreSQL workflow queue and duplicates them into per-recipient email jobs. File bytes are removed from the ordinary event payload and notification records, but queue rows, replicas, backups, DB logs, and privileged readers can contain them. No encryption or automatic removal is supplied for these copies; an optional manual cleanup for completed jobs is described below. Protect and manage all copies before use. Large fanouts multiply storage and query traffic, and the API request-body limit also applies. This is not the original storage contract or complete attachment compatibility. Worker migration 0132 and the current API route attachment-bearing jobs to a separate job kind that older in-app workers do not claim; the rollout and in-flight limitations are described below. Docker PostgreSQL tests exercise trigger, fanout and both workers against mock HTTP providers; pinned original provider wire comparisons cover selected attachments, not original-server attachment upload or real delivery. The original Resend SDK serializes its byte content as a Buffer object while this adapter uses Base64; no live attachment comparison was made.

Optional target binding (worker migration `0130`): set a common, randomly generated secret of at least 32 bytes in `SWALLOW_ALERT_BINDING_KEY_FILE` (or `SWALLOW_ALERT_BINDING_KEY`) on every alert sender. Grant its DB LOGIN EXECUTE on `public.novu_rust_bind_alert_destination(text,text,text,text)` and the environment's existing `alert_send`; apply this to each alert-state database used. The first successful check binds `(environment, channel, target ID)` to an HMAC-SHA256 fingerprint of the normalized Slack webhook URL, or the email provider and exact recipient address. Later checks with a different destination or key reject that target before condition observation or dispatch while other usable targets remain eligible; the command exits 1. `alert-fanout` inherits this setting for each child. The key and raw destinations are not written to the binding table, but the fingerprint and database parameter logs are sensitive and must be protected.

This is an opt-in first-use consistency check, not validation that a destination is correct or independently authorized. Before enabling it, verify existing target-to-destination mappings: the first binding cannot reconstruct an older slot's destination. Older binaries or senders without the key bypass the check, and privileged DB users can directly modify or pre-bind values; restrict DB permissions and update all cooperating senders. Changing a Slack webhook, email provider/recipient or binding key requires a new non-secret target ID and coordinated deployment; email sender address, provider credentials and SendGrid region are not included. No automatic binding deletion, key rotation or audited management UI is provided. Different alert-state databases have independent bindings and can diverge. When binding is enabled, `send-uncoordinated` fallback cannot validate a destination and fails without sending; choose another fallback or explicitly omit the binding policy after assessing the existing duplicate and audit limitations. This policy adds a database function call per configured target, including healthy checks; database unavailability or timeout fails that target. Docker PostgreSQL tests cover restricted role and environment isolation, concurrent conflicting first bindings, role revocation, actual fanout commands with Slack/email mismatches, and continued dispatch to other targets. Local tests cover uncoordinated fallback rejection. Actual external delivery, production scale and cross-database failover are unverified.

`alert-fanout` runs either existing alert command once per destination, allowing up to 32 Slack webhooks and/or Resend/SendGrid email recipients in one scheduled invocation. Install `alert-fanout`, `send-delivery-alert`, and `send-database-alert` in the same directory. Configure the existing DB, health checks, alert permissions, fallback and timeouts exactly as for the underlying command. Pass a JSON configuration file (maximum 64 KiB) containing absolute paths to secret files, for example:

```json
{"targets":[
  {"channel":"slack","id":"ops-team","webhook_file":"/secure/slack-webhook"},
  {"channel":"email","id":"primary-oncall","provider":"resend","to":"oncall@example.test","from":"alerts@example.test","api_key_file":"/secure/resend-key"},
  {"channel":"email","id":"backup-oncall","provider":"sendgrid","to":"backup@example.test","from":"alerts@example.test","api_key_file":"/secure/sendgrid-key","region":"eu"}
]}
```

Run `alert-fanout delivery ENV GRACE_SECONDS HEARTBEAT_MAX_SECONDS COOLDOWN_SECONDS /secure/targets.json` or `alert-fanout database MONITOR_ENV TARGET_LABEL COOLDOWN_SECONDS /secure/targets.json`. `sender_name` is optional for email and `region` is optional only for SendGrid (`global` or `eu`). IDs use 1–64 ASCII letters, digits, dot, underscore or hyphen and must be unique within each channel. Use stable, non-secret IDs; change the ID when the underlying destination changes and coordinate that change across every sender. Each destination gets the existing independent `(environment, channel, ID)` reservation, cooldown and unknown/rejected review. Do not use the same ID for different destinations or assume different IDs prevent duplicate delivery to the same address. The config includes addresses and paths, so protect it and the referenced secrets; no webhook or API key is embedded in JSON. Destination-specific legacy environment variables are removed from each child and replaced by the selected config. Child output is suppressed; the parent reports only channel, target ID and `completed`, `attention` (child exit 2), or `failed`. Exit 1 means any child failed or an interruption occurred; otherwise 2 means at least one child returned 2, and 0 means all returned 0. These codes do not prove receipt, and for database alerts exit 2 also represents an unhealthy probe.

Destinations execute sequentially by default. Set `SWALLOW_ALERT_FANOUT_CONCURRENCY` to 1–8 to choose bounded parallel child execution; invalid values fail before starting a child. Every child independently repeats health checks, so they observe different points in time; parallel mode increases simultaneous database connections, query load and provider requests, and output order follows completion rather than configuration order. Choose a limit the database and providers can sustain. Total work still grows with target count and runtime can accumulate across batches. Invalid configuration rejects the entire invocation before any child starts; a child configuration or transport failure does not prevent later destinations from being tried. After observing SIGTERM, the runner starts no further targets and waits for active children within the shared grace period; the signal can race with starting a child. A timeout terminates active child processes and may leave their external outcomes ambiguous. `SWALLOW_ALERT_SHUTDOWN_GRACE_SECONDS` bounds the wait and a timeout terminates the child. A request already sent may be ambiguous and must follow the existing lease and operator-review procedure. The database alert's optional uncoordinated fallback still has no durable slots or duplicate protection. Mock child-process tests cover target isolation, continued execution, result aggregation, malformed duplicate targets, the two-child concurrency bound, graceful interruption and timeout cleanup of multiple children. Disposable Docker PostgreSQL tests run both real child commands in sequential and parallel modes with four independent blocked targets and verify a missing credential does not suppress later targets. A separate local proxy closes four real child connections before TLS completes and verifies each slot records an independent unknown result. Run `cargo test --locked --test alert_fanout -- --ignored --test-threads=1` against a fully migrated disposable DB. These tests send no external messages and do not prove provider acceptance or actual receipt. Production load and multi-host orchestration remain unverified.

`send-delivery-alert` and `send-database-alert` handle SIGTERM and Ctrl-C with `SWALLOW_ALERT_SHUTDOWN_GRACE_SECONDS` (default 30; 1–300 seconds). They continue their current scheduled pass, including any remaining checks and configured destinations, for at most the grace period. Existing per-operation deadlines and exit codes still apply; the grace is an additional bound after the signal, not a total execution deadline. Configure the supervisor termination budget longer than the grace period. A timeout exits 1 and may interrupt an external request after acceptance, leaving a durable `dispatching` reservation; normal lease expiry and operator review conservatively convert it to `unknown` and block blind resend. In uncoordinated fallback there is no durable reservation or recovery history. An accepted provider response does not prove human receipt. Docker PostgreSQL and a local black-hole HTTPS proxy verify SIGTERM during each real command's Slack connection, normal unknown recording, a forced grace timeout and subsequent lease recovery; no real Slack or email is contacted. Run `TEST_DATABASE_URL=... cargo test --locked --test alert_shutdown -- --ignored` on a disposable fully migrated DB. Actual provider delivery, signal during all other execution phases and production orchestration remain unverified.

`resend-worker`, `sendgrid-worker`, `twilio-worker`, `fcm-worker`, `slack-worker`, `slack-webhook-worker`, `slack-workflow-worker`, and `in-app-worker` handle SIGTERM and Ctrl-C with `SWALLOW_WORKER_SHUTDOWN_GRACE_SECONDS` (default 30; range 1–300). A signal requests a stop, wakes polling/reconnect sleeps, and waits for the currently started operation; after that operation completes the worker stops before starting the next recovery or claim. A signal can race with an operation that has already begun, including claiming a job. If grace expires, the process exits with an error and may interrupt a provider request; use existing lease recovery and operator review for unknown outcomes. A successful process exit does not prove delivery or absence of a preceding database error. Keep the orchestrator's termination budget longer than the grace period and choose grace in relation to the channel's existing DB/whole-operation timeout. SIGKILL or host loss cannot be drained. Other processes do not necessarily use this shutdown mechanism; the three provider projectors are described below. An already started FCM job may continue sending to multiple targets until the operation completes; a Slack workflow stops between its fan-out and delivery operations when possible.

The Resend, SendGrid and Twilio projection workers also use the same shutdown grace. They finish a currently started database operation but stop before fetching another page or projecting another job. An interrupted scan does not advance its completion heartbeat; a completed scan can advance it. The next worker starts a new scan from the beginning. Concurrent projectors still share a heartbeat, so another instance can advance it; it is not proof of a cluster-wide complete scan. A signal can race with a just-started operation. If the grace expires, the process exits with an error and an in-flight transaction or heartbeat may have committed despite a lost response. Existing database transaction semantics and independent monitoring still apply. Docker PostgreSQL tests stop each real projector while its page is locked, verify stale heartbeat and a successful subsequent scan, and test timeout; a Resend projection already in its transaction is also allowed to commit without falsely completing the interrupted scan. Run `TEST_DATABASE_URL=... cargo test --locked --test projection_shutdown -- --ignored` against a disposable fully migrated database. Actual production failover, load and all event races remain unverified.

Docker PostgreSQL tests start all eight real binaries, block recovery on a database lock, signal each, release the lock and confirm pending work remains unclaimed; a timed-out Resend worker exits with an error. Unit tests exercise waiting for an in-flight future and timeout. These tests do not send a real external provider request during shutdown, verify deployment orchestration, or prove HA. On a disposable fully migrated database run `TEST_DATABASE_URL=... cargo test --locked --test worker_shutdown -- --ignored`; nonignored configuration tests and `cargo test --locked --lib shutdown::tests` cover validation and signal coordination.

For a new shared database, initialize migrations in dependency order: `migrate-worker apply api API_DIR --through 17`, then `migrate-worker apply worker WORKER_DIR`, `migrate-worker apply api API_DIR`, and `migrate-worker apply ws WS_DIR`. API migration `0018` requires the worker FCM integration table. `--through` applies an actual verified prefix, rejects versions older than the recorded history or outside the available files, and does not baseline an existing untracked database. Future inter-service dependencies must also be reviewed.

Worker migration `0096` stores exact-byte SHA-256 recipient hashes by tracked SendGrid dispatch, including `to`, `cc`, and `bcc` order. It snapshots at most 1,000 total addresses; larger sends, tracking-disabled sends and older attempts have no snapshot. Hashes may be guessable and require access controls. API migration `0020` preserves new SendGrid bounce subtypes where provided; historical or missing types remain unknown. Migration `0097` and the optional `sendgrid-projection-worker` use these records to project delivery results as described below. Apply API migration `0020` and worker migrations `0096`–`0097` before starting the projector.

When the optional SendGrid health check fails, `send-delivery-alert` exits 1 even if its destination is cooling down or requires review; other checks and configured destinations are still attempted. Monitor the command's exit status independently. A successful run or provider acceptance does not prove delivery to an operator. Docker PostgreSQL tests cover a missing projection with both a blocked destination and an accepted cooldown; actual Slack/email delivery and scheduler integration remain unverified.

`send-delivery-alert` bounds each database connection, health check, condition observation and destination dispatch with `SWALLOW_ALERT_OPERATION_TIMEOUT_SECONDS` (default 30; 1–300 seconds), and applies the same PostgreSQL statement timeout. A timed-out check is reported as failed while remaining checks and destinations are attempted. Timing out an external send can leave its reservation in flight until the normal unknown-outcome recovery and operator review; it is not evidence that the provider did not accept the alert. Individual limits may accumulate and are not a total runtime deadline. If the state database itself is unavailable, use the independent database alert path or monitor the scheduler failure separately.

## PostgreSQL synchronous failover test

`./scripts/test-postgres-failover.sh` creates a private disposable Docker network, PostgreSQL 17 primary and synchronous physical standby, applies current API and worker migrations, and starts two actual in-app workers. The standby is listed first in a multi-host connection URL with `target_session_attrs=read-write`, so the workers initially skip the read-only standby. The test commits a pending workflow job and an unexpired running lease, verifies both on the replica, forcibly stops the primary, promotes the standby, and makes the pending job runnable and the lease expire. Both workers reconnect to the promoted server; each job completes once, with one notification and one in-app message. The test checks that the committed lease token and pending state survived promotion. It uses test-only trust authentication and loopback ports and removes its own containers, volume and network. It requires Docker, Rust, and the local `postgres:17-alpine` image; `CARGO_TARGET_DIR` can select build output.

Run `SWALLOW_FAILOVER_TEST_SCENARIO=resend ./scripts/test-postgres-failover.sh` for the separate Resend dispatch scenario. The Rust queue function starts a workflow email and sends to a loopback mock, which captures the request and holds its successful response until after the primary is killed and standby promoted. Before the request, the `dispatching` attempt and message state are committed and replayed on the synchronous standby. The original sender cannot store the later success on the dead primary; after the test expires the lease, two actual Resend worker processes reconnect to the promoted node and leave the job failed and both attempt and message delivery state `unknown`. A local proxy records no further worker outbound connections during a six-second observation. No real Resend request is made; the initial sender is the same queue code in a test harness, not a production worker process. Unknown still requires external investigation; it is not evidence of failure or recipient delivery.

This verifies one controlled synchronous failover, not an HA system. The test forcibly fences the old primary; `target_session_attrs=read-write` does not elect a leader or prevent split brain, and the application does not supply a failover manager, replication configuration, fencing or automatic standby rejoin. Synchronous replication can block commits when the required standby is unavailable; asynchronous replication or forced promotion before acknowledged WAL is available can lose queue jobs, attempt markers, request deduplication and audit records. Loss of an attempt marker can cause duplicate external sends. Configure durable replication, tested leader fencing, routing, TLS and monitoring for the deployment; choose the connection mode and failover policy explicitly. Real external email/SMS/push requests, network partitions, other unacknowledged transactions, long-running load, and production orchestration are not exercised by these tests. The safety of replaying external requests remains channel-specific.

# Experimental worker operations

FCM Android `notification` supports title/body, icon, sound, color, tag, ticker, boolean `sticky`, click action, channel ID, localization keys and string arguments, image URL, local-only, priority, visibility, proxy, vibration timings, default sound/vibration/light settings and notification count. Selected Firebase Admin field-name, enum and integer-millisecond conversions are applied. Light settings accept #RRGGBB or #RRGGBBAA and integer-millisecond on/off durations, converting them to Firebase RGBA and duration fields. The optional Swallow JSON extension `overrides.fcm.android.notification.eventTime` accepts an RFC 3339 timestamp, converts offsets to UTC and truncates sub-millisecond precision, producing the FCM `event_time` field. Valid UTC range is years 0001–9999; leap seconds and invalid values are rejected. For example: `{"fcm":{"android":{"notification":{"eventTime":"2026-11-14T21:34:56.999987+09:00"}}}}` under the event `overrides` becomes `2026-11-14T12:34:56.999Z`. The pinned Firebase Admin Node SDK requires a JavaScript `Date` for `eventTimestamp` and rejects a JSON string, so `eventTime` is explicitly a Swallow extension rather than the same input contract; a JSON `eventTimestamp` remains rejected. Equivalent SDK `Date` wire conversions were compared for three timestamps. Fractional millisecond durations and unsupported fields are rejected. Image URLs are restricted to HTTP(S). The API accepts platform objects without validating all nested fields; failures can occur later in the worker. SDK comparisons cover `sticky` true and false; Rust rejects non-boolean values while the pinned SDK passes them to the service. Other SDK comparisons and original-versus-Rust API/workflow mock cases, including SDK-normalized LED settings, cover selected cases; actual Android receipt and complete platform behavior remain unverified. SWALLOW_WORKER_TEST_TARGET_DIR=/absolute/worker/target cargo test --locked --test fcm_event_time_workflow -- --ignored` from the Rust API directory against a fully migrated disposable DB; the nested worker harness uses Cargo offline. Worker migration `0127` adds `SWALLOW_PUSH_PREFERENCE_POLICY=snapshot|recheck`, independent of `SWALLOW_PUSH_WORKFLOW_STEP_POLICY`. The existing worker table SELECT/INSERT/UPDATE grants are required. Existing rows receive `snapshot`. Protect direct access; reapplying older migrations can replace newer functions.

Requests already reserved can still complete. Existing attempts are preserved, partial message groups remain conservatively incomplete, and no automatic replay occurs. The check does not refresh device tokens, rendered output or topic subscription preferences; workflow identity and step validation are controlled separately by `SWALLOW_PUSH_WORKFLOW_STEP_POLICY`. Worker migration `0126` lets authorized operators resolve an unknown FCM attempt on a policy-cancelled job without resuming the job or dispatching remaining targets. Worker migration `0118` and `SWALLOW_FCM_TOKEN_CLEANUP_GUARD=reference|version` choose how an invalid-token response interacts with concurrent credential changes. It adds a row read/lock per eligible dispatch and a UUID update on every device-row update even when the guard is disabled.

## SendGrid delivery projection

Set `NOVU_SENDGRID_ENVIRONMENT_ID` and run `sendgrid-projection-worker` with database access to the queue, attempts, recipient snapshots, email messages, signed webhook events, and projection heartbeat. `NOVU_SENDGRID_PROJECTION_DB_TIMEOUT_SECONDS` defaults to 30 (1–300). The worker repeatedly scans each environment in pages of 100, locks each job, and records recipient and aggregate `sendgrid_delivery_result` values without changing the original queue status or dispatch attempt. It writes a heartbeat after each complete traversal. Locked jobs can be skipped; events arriving after a scan are reflected on a later pass. Monitor the process and heartbeat independently. Repeated full-history scans and their performance at scale are not yet validated.

Only signed events bound to the current dispatch with a verified proof, matching message and exact recipient hash are used. A permanent bounce or dropped event is failed; a temporary blocked bounce is pending; delivery and failure evidence together are conflicting. Missing subtype, duplicate addresses, unmatched current events, old sends without snapshots and other ambiguous evidence remain unknown. An accepted attempt without final evidence is pending. Aggregate results are unknown, pending, delivered, failed, partial or conflicting. A delivery event reports acceptance by the receiving server, not that a person read the message. Unverified or older dispatch events do not establish the current result; address spelling differences can prevent matching. Snapshot hashes are sensitive to dictionary guessing.

The projection is an additional database field, not an original Novu-compatible status API, and it neither changes attempt or job status nor decides retries. The integration test uses synthetic signed webhooks and a disposable Docker PostgreSQL, including reconnect and environment isolation; real SendGrid webhooks, production volume, prolonged outages and original Novu parity for this projection have not been verified.

Worker migration `0111` adds an optional Resend webhook job lock. Invalid values are rejected at API configuration time. This ordering protects the case where a verified callback acquires the matching job lock before a retry decision or guarded worker check, and makes a callback that is waiting on a prior retry acquire that lock before inserting the event. Worker migration `0137` and `NOVU_RESEND_PROJECTION_AUTO_CORRELATE=true` opt the Resend projection worker into automatic recovery of an unknown attempt with no provider ID. The default is `false`. Acceptance is not delivery: incomplete recipients remain pending. If the audit insert fails, no recovery is committed.
