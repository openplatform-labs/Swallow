FCM 반복 선점 조사 목록: 워커 0201을 적용하고 모니터 로그인에 `public.novu_rust_fcm_unrecorded_claim_list(text,integer,integer,uuid)` EXECUTE와 환경별 `alert_view`를 부여한다. 함수 소유자에게 큐·시도 테이블 SELECT 및 권한 확인 함수 실행 권한이 필요하다. `delivery-reconcile list-fcm-unrecorded-claims ENV MIN_GAP GRACE_SECONDS [AFTER_JOB]`은 0200 집계와 같은 조건으로 작업 ID·상태·가용 시각·선점 수·기록된 시도 수·차이만 반환한다. 결과의 `next`가 있으면 다음 요청의 AFTER_JOB으로 사용한다. 한 페이지는 최대 100건이고 UUID 순서는 시간순이 아니며 각 페이지와 건수는 서로 다른 시점이므로 작업 변화에 따라 누락이나 중복이 생길 수 있다. 목록은 조사 대상이며 구버전 오류나 미발송의 증거가 아니다. 제한 로그인·임시 PostgreSQL에서 별도 실행 권한, 환경 격리, 정보 제외 및 두 페이지를 확인했다. 실제 운영 부하·HA는 미검증이며 HTTP·관리 화면은 [API README](../../api/rust-api/README.md)를 참고한다. 재현은 `TEST_PG_BIN=/path/to/postgresql/bin scripts/test-fcm-unrecorded-claims-local.sh`.

FCM 반복 선점 진단·경보: 워커 0200을 적용하고 모니터 DB 로그인에 `public.novu_rust_fcm_unrecorded_claim_health(text,integer,integer)` EXECUTE와 환경별 `alert_view`를 부여한다. 함수 소유자는 큐와 FCM 시도 테이블 SELECT 및 권한 확인 함수 실행 권한이 필요하다. `delivery-reconcile check-fcm-unrecorded-claims ENV MIN_GAP GRACE_SECONDS`는 조회 시점에 실행 가능 시각이 유예 시간보다 오래된 pending/running FCM 작업 중 선점 횟수에서 기록된 대상별 시도 수를 뺀 값이 MIN_GAP 이상인 건수를 반환한다. MIN_GAP은 2~100000, 유예 시간은 1~86400초이며 결과 0은 종료 0, 양수는 2, 조회 오류는 1이다. 미래 예약 작업은 제외하고 다른 환경의 정보나 payload는 반환하지 않는다.

Slack·메일 경보에는 `SWALLOW_ALERT_FCM_UNRECORDED_CLAIM_MIN_GAP`과 `SWALLOW_ALERT_FCM_UNRECORDED_CLAIM_GRACE_SECONDS`를 함께 지정한다. 대상과 `alert_send`, 스케줄은 기존 경보 설정을 사용한다. `new-condition`을 선택하면 `SWALLOW_ALERT_CONDITIONS_V2=true`가 필요하고 별도 조건 비트 49·50을 사용하므로 동일 대상의 실행기를 모두 업데이트해야 한다. 이 수치는 구버전 차단 여부의 증거가 아니다. 정상 공유 대기 재선점, 발송 전 장애나 관리 작업 등에서도 차이가 누적될 수 있고 임계값·DB 시계·경보 스케줄에 따라 누락 또는 지연될 수 있다. 작업이 완료되면 집계에서 사라진다. DB 로그·워커 버전·시도 기록을 함께 조사한다. 대량 데이터 성능·실제 공급자 발송·운영 HA는 미검증이다. `TEST_PG_BIN=/path/to/postgresql/bin scripts/test-fcm-unrecorded-claims-local.sh`로 제한 DB 권한, 환경 격리, 경보 실행기 및 실제 구버전 반복 선점을 재현한다. 모의 Slack·Resend 전송 단위 시험도 수행했다.

FCM 지수 대기 구버전 프로세스 시험: 보호 도입 직전 커밋 `2fd94b90`의 실제 FCM 워커를 임시 소스에서 빌드했다. 임시 PostgreSQL에서 구버전이 작업을 선점한 후 0199 트리거가 시도 삽입을 거절하고 로컬 프록시에 외부 연결이 없음을 확인했다. 구버전 중지와 임대 만료 처리 후 최신 실제 워커가 작업을 복구해 프록시에 연결했고 연결 중단은 결과 불명으로 기록됐다. `TEST_PG_BIN=/path/to/postgresql/bin scripts/test-fcm-exponential-local.sh`로 재현한다. 단일 DB·관리자 계정·모의 프록시 시험으로 제한 운영 계정의 전체 워커 실행, 실제 FCM 및 운영 HA는 미검증이다.

FCM 지수 대기 버전 보호: 워커 0199는 환경의 등록 정책이 `exponential`인 동안 호환 워커가 임대를 확인하고 트랜잭션 한정 표시를 설정한 발송 시도만 허용한다. 구버전은 시도 삽입에서 거절되므로 외부 요청을 시작할 수 없지만 작업을 선점해 임대 만료까지 지연시킬 수 있다. 0198까지만 지원하는 워커도 이 보호에는 구버전이다. 배포 시 최신 워커를 먼저 준비하고 기존 워커 중지·진행 작업 확인 후 0199를 적용하며, 지수 정책 전환 절차도 아래 설명대로 수행한다. 트리거 함수 소유자는 정책 테이블의 SELECT와 행 잠금 권한, 큐 테이블 SELECT가 필요하다. SECURITY DEFINER 함수 소유자와 스키마를 보호하고 특권 DB 사용자의 직접 수정·표시 위조는 방지하지 못한다. 이미 발송 시도를 기록한 요청, 정책 미등록 환경, 구버전 함수 재적용과 DB 복구는 보호 범위 밖이다. 임시 PostgreSQL에서 제한 역할의 구버전 방식 삽입 거절 및 새 큐의 모의 FCM 503과 후속 발송을 검증했다. 실제 구버전 워커 프로세스 시험은 위 최신 항목을 참고하며 실제 FCM·다중 호스트 HA는 미검증이다. 재현 명령은 아래 FCM 지수 대기 항목을 참고한다.

FCM 지수 대기 장애 전환 시험: 로컬 동기 복제에서 모의 503의 `Retry-After: 120`이 지수 정책의 기본 대기보다 길 때 120초 일정과 결과 불명 시도가 복제되는지 확인했다. 주 서버를 중지하고 복제본을 승격한 뒤 `exponential` 설정의 실제 워커 두 개가 이 일정을 지키고, 테스트에서 일정을 강제로 앞당긴 후 미시도 대상만 연결을 시작했다. `SWALLOW_LOCAL_FAILOVER_SCENARIO=fcm-exp scripts/test-postgres-failover-local.sh`로 재현한다. 이 시험은 120초 공급자 안내를 사용하며 반복 503 지수 증가의 장애 전환 시험은 위 최신 항목을 참고한다. 단일 호스트·관리자 DB 계정·모의 공급자 시험이며 실제 FCM·비동기 복제·네트워크 분리 및 운영 HA는 미검증이다.

FCM 다중 대상 503 지수 대기: 워커 마이그레이션 `0198` 적용 후 `SWALLOW_FCM_MULTICAST_503_POLICY=exponential`을 선택할 수 있다. 같은 작업에서 기록된 503 횟수마다 아직 시도하지 않은 다음 대상의 기본 대기를 10초부터 두 배로 늘려 최대 3600초로 제한하고 0~25%의 무작위 지연을 더한다(합계 상한 3600초). 유효한 `Retry-After`가 더 길면 최대 86400초까지 그 값을 따른다. 해당 503 대상은 결과 불명으로 남으며 자동으로 재발송하지 않는다. 횟수는 연속 횟수가 아닌 작업별 누적 횟수로, 다른 작업이나 환경·FCM 프로젝트에 공유하지 않는다. 다른 선택지는 그대로이며 기본값은 `continue`다. 정책을 변경할 때 기존 워커를 모두 중지하고 진행 중 발송을 정리한 후 아래 등록 절차대로 DB의 해당 설정을 초기화하고 모든 워커에 동일하게 설정한다. 구버전 워커는 새 선택지를 인식하지 못하며 기존 작업을 차단하지 않으므로 혼합 운영은 안전하지 않다. 마이그레이션은 테이블 잠금이 필요하며 기존 체크 제약을 식별할 수 없으면 실패한다. 모의 FCM·임시 PostgreSQL에서 반복 503, 결과 불명 보존, 나머지 대상만 발송, 실제 워커의 정책 등록·충돌 거절을 검증했다. 재현은 `TEST_PG_BIN=/path/to/postgresql/bin scripts/test-fcm-exponential-local.sh`. 실제 FCM과 운영 부하·다중 호스트 HA는 미검증이다.

Resend 날짜형 429의 장애 전환 시험: 로컬 PostgreSQL 동기 복제에서 모의 공급자가 `Date`와 날짜형 `Retry-After`로 300초를 안내하고 fallback은 600초로 설정했다. 복제본에 300초 시도와 대기 시각이 복제된 뒤 주 서버를 중지·복제본을 승격하자 실제 새 워커가 후속 작업을 같은 시각까지 연기하고 공급자 연결을 열지 않았다. `SWALLOW_LOCAL_FAILOVER_SCENARIO=resend-cooldown scripts/test-postgres-failover-local.sh`로 재현한다. 단일 호스트·관리자 DB 계정·모의 공급자 시험이며 비동기 복제, 네트워크 분리, 실제 Resend 및 운영 HA는 검증하지 않았다.

Slack 앱·웹훅 및 Twilio SMS의 429 `Retry-After`도 HTTP 날짜를 지원한다. FCM·Resend와 공통 해석기를 사용하며 서버 `Date` 또는 워커 시계, 24시간 상한 및 오류 처리 조건은 아래 설명과 같다. Slack 공유 대기를 활성화하면 계산한 값이 해당 정책에 반영되고 Twilio에서는 저장된 안내를 선택형 운영자 지연 예약이 사용한다. 기존 설정을 변경하거나 재시도를 자동 활성화하지 않는다. 날짜형 헤더가 이전에는 미지원이었으므로 해당 응답의 대기·예약 동작이 바뀐다. 모의 Slack의 세 발송 경로와 모의 Twilio에서 날짜형 120초가 DB에 기록되는 것을 확인했다. 실제 공급자의 날짜형 응답·운영 HA는 미검증이다. `TEST_PG_BIN=/path/to/postgresql/bin scripts/test-channel-retry-date-local.sh`로 재현한다.

Resend 429의 `Retry-After`는 초 또는 HTTP 날짜를 지원한다 ([RFC 9110 §10.2.3](https://www.rfc-editor.org/rfc/rfc9110.html#section-10.2.3)). 날짜는 유효한 단일 응답 `Date`를 기준으로 계산하며 `Date`가 없으면 워커 시계를 쓴다. 소수 초는 올림하고 과거 날짜는 0초로 취급한다. 중복·잘못된 헤더와 24시간 초과는 안내 없음으로 처리하고 공유 대기 사용 시 설정된 fallback을 적용한다. 응답 `Date`가 실제 시각과 다르거나 중간 프록시가 바꾸면 대기 시간도 달라지며 워커·DB 시계와 프록시를 신뢰해야 한다. 기존 재시도 정책은 변하지 않는다. 모의 Resend와 임시 PostgreSQL에서 날짜형 기록 및 공유 대기를 검증했으며 실제 Resend 날짜형 응답과 운영 HA는 미검증이다.

Resend shared cooldown fallback administration: worker migration `0197` adds a revision to the existing policy and independent environment-scoped DB login grants `novu_rust_resend_cooldown_policy_admins` (`can_read`, `can_write`, `can_audit`). A trusted DBA registers each intended LOGIN with its current role OID and grants only the corresponding EXECUTE privileges on `public.novu_rust_resend_cooldown_policy_read(text)`, `public.novu_rust_resend_cooldown_policy_set(text,uuid,bigint,integer,text)`, `public.novu_rust_resend_cooldown_policy_request(text,uuid)` and `public.novu_rust_resend_cooldown_policy_audit_read(text,bigint)`. The protected security-definer owner needs access to the policy, admin, request and audit tables plus the audit sequence; protect those objects and their owners. 워커 0166은 `delivery-reconcile list-resend-auto ENV GRACE_SECONDS FILTER [AFTER_JOB]`으로 0165의 주의 집계에 해당하는 작업을 UUID 순 20건씩 조회한다. 워커 0165는 환경별 Resend 429·자동 재시도 주의 상태를 집계한다. `delivery-reconcile check-resend-auto ENV GRACE_SECONDS`는 JSON의 `rateLimited`(기준 시간 이상 실패한 429), `exhausted`(그중 활성 정책의 횟수를 소진한 건), `guardDeferred`(보호 설정 불일치로 보류된 pending 건), `overdueAuto`(예약 시각과 기준 시간이 지난 자동 재시도 pending 건)를 반환한다. `exhausted`는 `rateLimited`의 부분집합이며 다른 항목도 겹칠 수 있다. 선택적으로 `SWALLOW_ALERT_RESEND_AUTO_GRACE_SECONDS=300`을 설정하면 기존 `send-delivery-alert`가 이 집계를 Slack·이메일 대상에 포함한다. 생략하면 비활성화되며 기존 Resend 전달 상태 검사와 독립적으로 켜거나 끌 수 있다. 검사 자체의 실패도 경보를 시도하고 오류로 종료한다. 모니터링 로그인에 위 조회 권한과 기존 발송 경로의 권한을 부여하고, 누락 실행·DB 장애·경보 전송 결과는 별도로 감시한다. `new-condition` 쿨다운에서는 기존 미확인 실패 작업과 같은 조건 범주를 공유하므로 이미 그 범주가 활성 상태인 동안 다른 항목이 추가되어도 별도 즉시 경보가 보장되지 않는다. 한 검사가 실패하면 공유 범주를 정상으로 지우지 않는다.

집계는 조회 시점의 DB 상태이며 발송·수신이나 모든 워커의 정상 동작을 보장하지 않는다. `rateLimited`는 실패 작업의 별도 확인 여부를 반영하지 않아 상태가 바뀌기 전까지 계속 집계된다. `exhausted`는 현재 활성 정책과 cutoff 기준이고 정책 비활성화 시 0이 될 수 있다. `guardDeferred`는 특정 오류 문자열과 pending 상태를 사용하며 직접 DB 수정·구버전 워커·다른 실패 유형은 탐지하지 못한다. 향후 예약 시각이 아직 지나지 않은 작업은 overdue가 아니다. 환경의 pending·failed Resend 작업과 관련 이력 집계가 추가되므로 실제 규모에서 실행 계획·부하를 확인한다. 제한 DB 계정·실제 CLI·임시 PostgreSQL에서 집계·환경 격리·권한 회수 및 차단된 경보 예약을 검증했고, 로컬 모의 Slack·Resend 어댑터에서 경보 내용 전달을 확인했다. 실제 외부 수신·스케줄러·운영 HA는 미검증이다. 재현: `TEST_DATABASE_URL=... cargo test --test resend_auto_health -- --ignored` (전체 마이그레이션을 적용한 폐기 가능한 DB와 역할 생성 권한 필요).

워커 0164는 Resend 자동 정책에 요청 ID 기반 변경과 결과 조회를 추가한다. 기존 정책 쓰기 권한 `can_write`와 다음 두 함수에 대한 별도 EXECUTE 권한이 필요하다. 요청 ID는 운영자가 전송 전에 생성·보관한다.

```sql
GRANT EXECUTE ON FUNCTION public.novu_rust_resend_auto_policy_set_v2(text,uuid,bigint,boolean,integer,text,text),
 public.novu_rust_resend_auto_policy_request(text,uuid) TO operator_role;
```

`delivery-reconcile resend-auto-policy-set-v2 ENV REQUEST_ID EXPECTED enabled|disabled MAX now|preserve REASON`은 요청·조건부 정책 변경·감사를 함께 기록한다. 같은 환경과 DB 로그인·역할 OID에서 같은 ID와 동일한 내용을 재제출하면 원래 결과와 `replayed:true`를 반환하고 변경과 감사를 반복하지 않는다. 같은 ID에 다른 내용을 사용하면 거절한다. `delivery-reconcile resend-auto-policy-request ENV REQUEST_ID`는 현재 쓰기 권한을 재확인하고 같은 DB 로그인·역할 OID의 요청만 조회한다. 감사 조회에도 요청 ID가 표시되며 기존 기록은 null이다.

응답 유실 시 요청 ID와 내용을 보관한 뒤 조회하거나 정확히 같은 요청만 재제출한다. `found:false`는 이전 요청이 아직 진행 중일 가능성을 배제하지 않는다. 조회 결과는 당시 변경의 결과이며 현재 정책이 이후 변경되지 않았다는 뜻이 아니다. 조회와 재제출은 권한 회수 후 거절된다. DB 직접 변경, 요청 기록 삭제·보존 기간 관리 실패, 오래된 백업 복원·비동기 장애 전환 또는 별도 DB는 중복 방지 보장을 깨뜨릴 수 있다. 사유와 요청 메타데이터는 평문으로 저장되므로 비밀을 포함하지 말고 접근·보존을 관리한다. 이 기능은 동일 DB 로그인에 묶이며 다른 로그인이나 사람의 신원을 보증하지 않는다. 기존 `resend-auto-policy-set` 경로는 요청 ID 없이 계속 사용 가능하다.

임시 PostgreSQL 17, 제한 DB 로그인 및 실제 CLI에서 동일 요청 동시 제출·재제출, 다른 내용의 ID 충돌, 다른 로그인·환경 격리, 이후 정책 변경 후 원래 결과 조회, stale 요청과 감사 오류 롤백, 권한 회수를 확인했다. 클라이언트가 첫 응답을 무시하는 상황을 재제출로 모델링했으며 실제 네트워크 단절·운영 HA는 미검증이다. 재현: `TEST_DATABASE_URL=... cargo test --test resend_auto_policy_requests -- --ignored` (전체 마이그레이션을 적용한 폐기 가능한 DB와 역할 생성 권한 필요).

워커 0163은 Resend 자동 429 정책을 DB 직접 쓰기 없이 관리하는 선택형 CLI를 제공한다. 최초 권한은 DB 관리자가 환경과 로그인 역할별로 `novu_rust_resend_auto_policy_admins`에 등록하며 `can_read`, `can_write`, `can_audit`을 따로 선택한다. 역할 이름과 로그인 역할 OID를 함께 확인하므로 역할을 삭제·재생성하면 다시 등록해야 한다. 각 경로에는 해당 함수의 EXECUTE 권한도 부여한다. 예를 들어 세 권한을 모두 부여하려면 다음 SQL을 DB 관리자가 환경·역할에 맞게 실행한다.

```sql
INSERT INTO public.novu_rust_resend_auto_policy_admins
 (environment_id,database_principal,principal_oid,can_read,can_write,can_audit)
SELECT 'ENV',rolname,oid,true,true,true FROM pg_roles WHERE rolname='operator_role' AND rolcanlogin;
GRANT EXECUTE ON FUNCTION public.novu_rust_resend_auto_policy_read(text),
 public.novu_rust_resend_auto_policy_set(text,bigint,boolean,integer,text,text),
 public.novu_rust_resend_auto_policy_audit_read(text,bigint) TO operator_role;
```

`delivery-reconcile resend-auto-policy-read ENV`는 정책 유무와 `revision`을 표시한다. 생성은 `resend-auto-policy-set ENV -1 enabled 3 now REASON`, 변경은 조회한 revision을 사용해 예를 들어 `resend-auto-policy-set ENV 0 disabled 3 preserve REASON`으로 수행한다. 최대 횟수는 1~10이고 `now`는 대상 시작 시각을 현재 DB 시각으로 변경하며 `preserve`는 기존 시각을 유지한다. 신규 정책에는 `now`가 필요하다. 비활성화 후 `preserve`로 다시 켜면 이전 시각 이후의 오래된 실패도 자동 재시도 대상이 될 수 있다. 한 번의 변경마다 revision이 증가하고 사유·이전/변경 내용·DB 로그인은 감사에 원자적으로 기록된다. 이미 예약된 작업은 정책 변경으로 취소되지 않는다. `resend-auto-policy-audit ENV [BEFORE]`는 ID 내림차순 50건과 다음 커서를 반환하며 ID 순서는 커밋 순서나 여러 페이지의 단일 스냅샷을 보장하지 않는다.

동일 revision의 동시 변경은 하나만 성공하고 권한 회수는 진행 중인 변경을 기다린다. 응답 유실은 성공 여부가 불명이며 새 요청으로 자동 재시도하지 않는다. 현재 revision과 감사를 확인해 변경 내용과 사유를 대조한다. 기존 명령에는 요청 ID가 없으며 위 최신 0164 경로는 요청 ID를 지원한다. 감사에는 이 함수 경로만 기록되고 직접 DB 변경은 기록되지 않으며, DB 소유자와 감사 보관·사유의 민감정보를 별도 관리해야 한다. DB 로그인은 사람의 신원을 독립적으로 증명하지 않는다. 기존 직접 SQL 설정도 계속 작동하지만 revision·감사를 우회한다. 제한 DB 역할·실제 CLI·임시 PostgreSQL 17에서 권한 분리, 환경 격리, revision 경합, 감사 실패 롤백, 스케줄러 정책 잠금과 권한 회수 경합을 확인했다. 실제 IdP·운영 HA와 정책 대량 감사 페이지는 미검증이다. 재현: `TEST_DATABASE_URL=... cargo test --test resend_auto_policy_admin -- --ignored` (전체 마이그레이션을 적용한 폐기 가능한 DB와 역할 생성 권한 필요).

워커 0162는 자동 429 재시도 감사에 별도 표시를 남기고, 새 Resend 워커가 작업을 잠근 상태에서 마지막 재시도 표시를 확인한다. 자동 재시도 작업에 태그·두 증거 가드·retry별 키 중 하나라도 빠졌으면 외부 요청이나 발송 시도를 만들지 않고 5초 뒤 다시 대기열에 넣는다. 정책을 끈 뒤에도 이미 예약한 자동 작업은 보호한다. 대기 중 부적절한 워커가 반복해서 가져가면 시작 지연과 작업 claim 횟수 증가가 발생하며 로그·대기열을 감시하고 워커 설정을 수정해야 한다. 기존 수동 재시도에는 이 추가 조건을 적용하지 않는다.

모든 새 Resend 워커의 DB 계정에 `GRANT EXECUTE ON FUNCTION public.novu_rust_resend_auto_dispatch_allowed(text,uuid,boolean,boolean,boolean,boolean) TO worker_role`이 필요하며, 기능을 끈 경우에도 새 함수 실행 권한이 필요하다. 배포 전 0162를 적용하고 권한을 부여한 뒤 모든 구버전 워커를 교체한다. 0162는 0161에서 기록한 고정 이름·사유의 기존 감사 행을 자동으로 표시한다. 운영자가 동일한 이름·사유를 수동 입력한 과거 행은 보수적으로 자동으로 표시될 수 있다. 감사 테이블 변경·과거 행 갱신의 잠금과 부하를 계획한다. 함수 실행 권한이 있는 DB 계정은 알려진 환경·작업 ID에 대한 자동 여부를 유추할 수 있으므로 워커 계정에만 부여한다. 이전 바이너리, 직접 테이블 변경, 등록 정책을 사용하지 않는 라이브러리 호출과 DB 복원은 이 검사를 우회할 수 있다. DB 작업 잠금 이후 공급자 요청을 보내기 전에도 콜백이 도착할 수 있으며 중복 방지를 보장하지 않는다.

임시 PostgreSQL 17·제한 함수 실행 계정에서 네 설정을 각각 빠뜨린 경우의 차단을 확인했다. 실제 큐 함수·모의 Resend에서 정책 비활성화 후에도 미보호 워커는 외부 요청 없이 작업을 연기하고, 보호 설정을 가진 워커가 발송하는 것을 확인했다. 0161 감사 행을 가진 별도 DB를 0162로 업그레이드하여 기존 자동 판정이 표시되고 차단되는 것도 확인했다. 실제 공급자, 혼합 구버전 운영과 다중 호스트 HA는 미검증이다. 재현은 위 `resend_auto_429` 테스트를 사용한다. 등록 정책을 사용하는 발송 준비마다 DB 함수 호출 1회와 최근 감사 이력 조회가 추가된다.

선택형 Resend 429 자동 재시도는 워커 0161 적용 후 DB 관리자가 환경별 정책을 등록하고, 해당 환경의 모든 Resend 워커를 새 버전과 아래 설정으로 통일해 사용한다. 기본값은 꺼짐이며 기존 수동 지연·즉시 재시도도 계속 선택할 수 있다. 정책의 `not_before` 기본값은 등록 시각이고 그 이전에 시작한 발송 시도는 자동 예약하지 않는다. 비활성 후 다시 활성화할 때는 `not_before=clock_timestamp()`도 함께 지정한다. 운영자가 별도로 과거 시각을 지정하면 오래된 작업도 대상이 될 수 있다. DB 직접 변경과 기존 바이너리는 정책을 우회하므로 활성화 전 모든 이전 워커를 중지·교체한다.

```sql

INSERT INTO public.novu_rust_resend_auto_retry_policy(environment_id,enabled,max_retries)
VALUES ('ENV',true,3);
GRANT EXECUTE ON FUNCTION public.novu_rust_resend_auto_retry(text) TO worker_role;
-- worker_role에 환경별 기존 retry 권한도 필요하다.
INSERT INTO public.novu_rust_delivery_operator_grants(environment_id,database_principal,decision,principal_oid)
SELECT 'ENV',rolname,'retry',oid FROM pg_roles WHERE rolname='worker_role';
```

모든 해당 환경 워커에 `NOVU_RESEND_AUTO_RETRY_429=true`, `NOVU_RESEND_RETRY_EVIDENCE_GUARD=true`, `NOVU_RESEND_CORRELATION_TAG=true`, `NOVU_RESEND_RETRY_CORRELATION_GUARD=true`, `NOVU_RESEND_IDEMPOTENCY_SCOPE=retry`를 설정한다. 자동 모드에서 필수 설정이 빠진 워커는 시작을 거절한다. 기존 idempotency 정책 및 배포 전환 절차도 지켜야 한다. 자동 검사에는 함수 실행 권한과 환경별 retry 권한이 필요하다. 정책이 없거나 비활성이면 예약하지 않는다. 정책 변경은 검사 트랜잭션과 잠금으로 직렬화되지만 이미 예약된 작업은 취소되지 않는다.

워커는 약 5초마다 해당 환경의 429 실패 건 하나를 검사한다. 지원되는 `Retry-After`가 있고 이전 판정이 모두 429 재시도이며 총 재시도 판정 횟수가 정책 상한보다 작을 때만 기존 지연 판정과 감사 기록을 사용한다. 기존 수동 재시도도 이 상한에 포함한다. 결과 불명, 헤더 누락, 다른 상태·과거 비429 판정과 확인된 콜백은 자동 재시도하지 않는다. 재시도 준비 시 기존의 공급자 ID·상관 태그 증거 검사를 전체 이력에 적용한다. 검사와 발송 준비 후에 도착한 콜백까지 차단하지 못하며, 태그가 없거나 외부 시스템에서 누락된 증거는 식별하지 못한다. 실패한 검사와 DB 연결은 운영자가 감시해야 한다. 이 기능은 환경별 고정 횟수 제한이지 공급자 계정 전체의 처리율 제한이 아니다. DB 시계, 복제 장애 전환과 이전 버전 혼합 운영은 별도 고려가 필요하다. 잘못된 429 판정, 프록시 응답, 지연된 증거 또는 멱등성 기간·요청 내용 변경으로 중복이 발생할 수 있다. 자동 모드는 retry별 멱등성 키를 사용하므로 특히 공급자 접수 여부가 불확실하면 켜지 않는다.

임시 PostgreSQL 17·제한 DB 로그인·모의 Resend와 실제 큐 함수에서 기본 비활성, 권한·환경 격리, 두 동시 예약 중 한 건, 최대 횟수, 오래된 상관 태그의 예약 전·후 콜백 차단을 확인했다. 실제 워커 프로세스에서 모의 429 작업의 미래 예약도 확인했으며 외부 발송은 하지 않았다. 실제 Resend 429와 다중 호스트 HA, 혼합 버전 배포는 미검증이다. 재현: `TEST_DATABASE_URL=... cargo test --features test-mocks --test resend_auto_429 -- --ignored` (전체 마이그레이션을 적용한 폐기 가능한 DB와 역할 생성 권한 필요). 활성 검사에는 워커마다 약 5초에 DB 호출 1회가 추가되고, 선택된 재시도에는 감사·큐 변경 트랜잭션이 추가된다.

Resend 429의 대기 안내를 적용하려면 워커 0160 적용 후 `delivery-reconcile resend-retry-after ENV JOB OPERATOR REASON`을 선택한다. 환경별 기존 `retry` 권한과 별도의 `GRANT EXECUTE ON FUNCTION public.novu_rust_resolve_resend_after(text,uuid,text,text) TO 운영자_DB_역할`이 필요하다. 별도 scoped 설정 없이 이 함수 경로를 사용한다. 실패한 Resend 429에 유효한 대기 안내가 있을 때만 기존 증거 검사와 감사·큐 변경을 한 트랜잭션에서 수행하고, 작업을 DB 시계 기준 안내 시각 이후로 예약한다. 안내가 이미 지났으면 즉시 대기열에 넣는다. 기존 `retry ENV JOB - OPERATOR REASON`은 즉시 재시도로 계속 사용할 수 있다.

감사 행의 `resend_retry_not_before`에는 원래 안내 시각이 기록된다. 시도·안내가 없거나 이미 변경된 작업, 해당 공급자 콜백 증거가 있는 경우는 거절한다. 동시 결정은 작업 잠금으로 직렬화하며 감사 기록 오류는 전체 변경을 롤백한다. DB 직접 수정과 기존 즉시 재시도 경로는 이 선택형 대기를 우회할 수 있다. DB 시계 변경, 데이터 손실·비동기 장애 전환, 대기 기간 중 공급자 상태 변경, 다른 작업·계정 전체의 요청률은 보호하지 않는다. 이 명령은 운영자의 명시적 판정이며 별도 자동 정책은 위 최신 항목을 참고한다. 잘못된 판정과 공급자 수신 확인의 한계로 중복 발송이 가능하다.

임시 로컬 PostgreSQL 17, 제한 DB 계정과 실제 CLI에서 권한·환경 격리, 누락된 안내와 콜백 거절, 감사 실패 롤백, 두 동시 결정 중 하나만 성공, 감사 시각 보존을 확인했다. 실제 큐 함수와 모의 Resend에서 기한 전 미처리 및 기한을 테스트에서 앞당긴 뒤 발송을 확인했다. 실제 Resend 429와 다중 호스트 HA는 미검증이다. 재현: `TEST_DATABASE_URL=... cargo test --features test-mocks --test resend_retry_after_schedule -- --ignored` (전체 서비스 마이그레이션을 적용한 폐기 가능한 DB와 역할 생성 권한 필요).

Resend가 HTTP 429와 단일 `Retry-After` 초 값을 보내면 워커 0159는 0~86,400초 정수만 수집하고 해당 시도의 `retry_after_seconds` 및 DB 시계 기준 `retry_not_before`를 저장한다. 다른 형식·여러 헤더·범위 초과·누락은 값을 저장하지 않는다. 원문 헤더와 응답 본문은 저장하지 않는다. API 0089는 기존 운영자 결과 조회 권한으로 이 안내를 제공한다. 새 워커 적용 전 0159를 배포하고 제한된 워커 DB 계정에 두 새 열의 UPDATE 권한을 부여한다. 이전 워커와 이 변경 전 시도에는 값이 없다. 새 API를 적용하기 전에 워커 0159가 필요하다. [Resend의 속도 제한 안내](https://www.resend.com/changelog/api-rate-limit)는 `Retry-After`를 재요청 전 대기 초로 설명한다.

이 값은 참고 정보이며 재시도를 자동 예약하거나 강제하지 않는다. 수동 재시도는 운영자가 시각과 전송 결과를 독립 확인하고 결정하며 동일 계정의 다른 워커·서비스 요청률도 별도로 관리해야 한다. 저장 시 DB 시계가 정확해야 하고 중간 프록시가 헤더를 바꿀 수 있다. 해당 시도를 재시도하면 기존 시도 행과 안내는 삭제된다. HTTP 날짜 형식은 위 최신 항목을 참고한다. 범위 밖 대기 값은 지원하지 않으며 실제 Resend 429는 미검증이다. 모의 Resend 및 임시 PostgreSQL로 헤더 범위, DB 기록 및 재발송 없음, 제한 JWT API와 실제 브라우저의 표시를 확인했다. 운영 HA는 미검증이다.

FCM HTTP 성공 응답은 스트리밍으로 최대 16 KiB까지 읽는다. `name`이 없거나 비어 있거나 1,024바이트 초과 또는 제어 문자를 포함하면 잘못된 응답으로 처리한다. 본문 초과·잘못된 JSON·읽기 오류도 발송 여부를 확인할 수 없으므로 큐는 해당 시도를 `unknown`으로 기록하고 자동 재전송하지 않는다. 이 제한을 초과하는 공급자의 유효한 성공 응답도 수동 조사가 필요하다. API를 호출하기 전 요청 검증은 바뀌지 않으며 기존 워커를 모두 교체해야 같은 제한이 적용된다. 이 보호는 전송 요청당 메모리를 제한하며 네트워크나 공급자 자체의 과부하를 해결하지 않는다.

로컬 모의 FCM에서 정상·빈 ID·긴 ID·제어 문자·잘못된 JSON·크기 초과 응답을 테스트했다. 임시 PostgreSQL 17과 실제 큐 처리 함수에서는 크기 초과 응답을 받은 작업이 `failed`/`unknown`으로 남고 다음 큐 조회에서 다시 보내지 않는 것을 확인했다. 실제 FCM과 운영 부하·HA는 검증하지 않았다.

## Attempt-fenced Slack resolution

Worker migration `0158` assigns a random UUID to each current Slack delivery attempt, including attempts already present during migration. New app, webhook and workflow-delivery attempts get new IDs automatically. `delivery-reconcile list-slack-v2 ENV [AFTER_JOB]` returns the existing authorized attention list plus `attemptId` (null for entries without an attempt). After independently investigating the current outcome, `delivery-reconcile slack-resolve-v2 ENV JOB ATTEMPT_ID retry|accepted OPERATOR REASON` locks the operator grant, job and attempt, checks the exact ID and eligible state, and atomically records the attempt ID and decision in the audit. An old ID is rejected if the job has since been retried and acquired a new attempt. Two concurrent decisions on one attempt cannot both succeed. `accepted` remains an operator assertion and `retry` can duplicate a message; neither proves delivery.

Use existing environment-specific `slack_view` and `slack_retry`/`slack_accepted` grants. Give the CLI login EXECUTE on `public.novu_rust_list_slack_attention_v2(text,uuid)` and/or `public.novu_rust_resolve_slack_v2(text,uuid,uuid,text,text,text)`. The trusted list function owner needs EXECUTE on the existing list function and SELECT on attempts; the resolve owner needs EXECUTE on the grant-lock function, SELECT/UPDATE on jobs and attempts, DELETE on attempts and INSERT on resolutions. Grant owners the underlying rights required by their nested functions, and protect owners, schema and tables. Existing audit rows and legacy decisions have null `attempt_id`; UUIDs are local identifiers, not Slack evidence. List pages are snapshots in UUID order, not chronological or exhaustive during concurrent changes.

Deploy the migration and new CLI before using the v2 commands. The legacy `slack-resolve` and `novu_rust_resolve_slack` remain unfenced; to enforce the new path, stop old operators, revoke their legacy function execution and direct table write privileges, and protect privileged owners. Old workers can still create attempts via the column default, but direct writes or changing IDs bypass the guard. The migration adds a volatile default to existing attempts and may rewrite or lock a large table; plan space and maintenance. Lost responses must be reconciled against current state and audit before a new decision. Asynchronous DB loss, split brain and restored snapshots can weaken fencing.

A disposable local PostgreSQL 17 integration test uses a restricted login and actual CLI to verify listing, environment isolation, retry, new attempt ID, stale retry/accept rejection, permission revocation, audit IDs and two simultaneous decisions. It inserts synthetic attempts and does not contact Slack. Actual Slack delivery, every lock interleaving, production migration cost and multi-host HA remain unverified. Run `TEST_DATABASE_URL=... cargo test --locked --test slack_attempt_fence -- --ignored` on a fresh disposable database; the test applies migrations and creates a role.

## Manual retry for Resend HTTP 429

A Resend response with HTTP 429 remains a `rejected` attempt and is not automatically retried. With worker migration `0157` and the updated CLI, an authorized operator may use the existing `delivery-reconcile retry ENV JOB - OPERATOR REASON` for that specific status after investigating it. The scoped path requires the existing `retry` grant and `novu_rust_resolve_email_sms` EXECUTE; the direct path uses the existing database privileges. Both preserve the 429 and prior correlation tag in the audit, reject a matching authenticated callback, and atomically reset the job for a later worker. `accepted` is still restricted to unknown attempts, and other rejected HTTP statuses remain ineligible. The existing `list` command lists unknown attempts, not rejected 429s; use failed-job monitoring and separately authorized result/evidence or database inspection to identify the job and status.

[Resend describes HTTP 429 and its `Retry-After` header](https://www.resend.com/changelog/api-rate-limit); Swallow does not persist that header or implement automatic backoff/rate control here. Investigate the provider response and capacity before retrying. A late or missing callback does not establish non-acceptance; a retry can duplicate delivery, particularly with retry-scoped idempotency keys. Existing worker retry guards and idempotency configuration remain independent. Deploy migration and updated CLI together; old direct CLI binaries still reject the 429. Do not reapply older migrations 0110 or 0135 afterward without reapplying 0157. The migration replaces existing functions and needs the same trusted ownership and permissions; it can acquire DDL locks.

A local disposable PostgreSQL 17 integration test uses a restricted operator login and actual CLI to verify 429 retry, denial of manual acceptance and other rejections, tagged callback blocking, audit and both direct/scoped paths. A separate queue-harness test obtains a 429 from a mock provider, applies an authorized retry and records a mocked successful response. ## Resend idempotency policy dispatch fence

Worker migration `0156` and updated `resend-worker` check the registered idempotency scope in the transaction that prepares an attempt. Grant the worker login `EXECUTE` on `public.novu_rust_check_resend_idempotency_scope(text,text)` as well as the policy table `SELECT` and `UPDATE` required by the row lock and the registration permissions described below. A missing row, different scope, revoked privilege or database error prevents attempt creation and dispatch. The already-claimed job remains leased until recovery; monitor the worker and queue. The guard locks the policy row through commit, so a concurrent update/delete waits, or a guard arriving after the change rejects the old scope. The worker reconnects after a guard error; a conflicting registration then exits.

The lock ends **before** the external request. A configuration change after commit cannot cancel a request already prepared or in flight, and older workers, direct function callers that omit the guard, DB privilege bypass and inconsistent or lost database state remain outside the fence. Stop all workers and reconcile in-flight work before changing the policy; do not treat the guard as a substitute for coordinated rollout. Each dispatch adds a locked DB lookup and policy changes can wait on active transactions.

A disposable local PostgreSQL 17 test uses actual idle workers and verifies a stale worker does not create an attempt after policy change; the request path uses a closed local proxy and no external provider. It checks a policy update waiting on the guard, stale-scope rejection and restricted SQL function privilege revocation. Actual provider requests, every lock ordering, production load and multi-host HA remain unverified. Run `TEST_DATABASE_URL=... cargo test --locked --test resend_idempotency_policy -- --ignored` against a fresh disposable database.

## Resend idempotency scope agreement

Worker migration `0155` adds a per-environment idempotency scope registration. The updated `resend-worker` registers its selected `job` or `retry` scope after connecting and before consuming jobs; a conflicting scope exits with an error. Concurrent first registrations serialize, so one scope wins. Grant the worker DB login `SELECT, INSERT, UPDATE` on `public.novu_rust_resend_idempotency_policy` in addition to its existing permissions. Missing migration, registration privileges or DB access prevents processing and causes reconnect attempts; monitor the worker and queue. This registration is required even for the default `job` mode.

To change scope, stop **all** Resend workers for that environment, verify no previous dispatch remains in flight, reconcile unknown and pending jobs, then have a trusted administrator delete the environment's registration using a parameterized `DELETE FROM public.novu_rust_resend_idempotency_policy WHERE environment_id=$1`. Start only updated workers with the same new scope. Protect that table and its owner: registration is checked on connection; the separate dispatch fence described above also checks each new guarded attempt. Older binaries do not register or enforce it. A DB restore, asynchronous failover, split brain, separate databases or direct SQL can lose or bypass the agreement; this does not prevent duplicate email or replace the retry evidence checks.

A fresh local PostgreSQL 17 test runs real idle worker processes and checks identical scopes, conflicting scopes, simultaneous conflicting first registrations and environment isolation. It uses the DB administrator account and sends no email. Limited-role deployment, real provider delivery, rolling upgrades, cross-host failure and production HA remain unverified. Reproduce with `TEST_DATABASE_URL=... cargo test --locked --test resend_idempotency_policy -- --ignored` against a **fresh disposable** database; the test applies migrations and creates environments.

## Optional Resend retry-scoped idempotency key

`NOVU_RESEND_IDEMPOTENCY_SCOPE=retry` selects a key derived from the job UUID and the latest persisted manual retry decision UUID. The first dispatch without a retry decision retains `swallow/<job UUID>`; a retried dispatch uses `swallow/<job UUID>/retry/<decision UUID>`. The default `job` retains the existing job-wide key. Other values reject startup. The retry mode requires worker migration 0056 and SELECT on `novu_rust_delivery_reconciliations` for the worker DB login; a DB error stops dispatch before the attempt transaction commits. Existing webhook evidence guards remain independent and should be configured as appropriate.

This choice permits a new provider request after a manual retry decision, including when a new correlation tag changes the request body. It also removes provider-level deduplication across those decisions: **a mistaken retry can deliver a second email**. An operator must independently establish non-acceptance before deciding to retry; missing or delayed webhooks do not prove it. Resend retains keys for a limited period and can return 409 for a reused key with a changed payload ([Resend documentation](https://resend.com/changelog/idempotency-keys)). No automatic retry is added. Coordinate the same mode across all worker replicas, stop old workers before switching, and review in-flight and pending jobs; older or differently configured workers use different keys, increasing duplicate risk. Reusing a decision ID after DB restore, direct DB changes, concurrent old workers or failover may also change the outcome. Guard against database data loss and unauthorized writes.

The existing disposable local PostgreSQL integration fixture exercises a real manual retry decision and mock provider request, checking the decision-scoped header, acceptance and existing callback guard. It also checks the legacy key. Tests use a DB administrator and a queue harness, not the `resend-worker` process or real Resend. Actual provider delivery, mixed-version rollout, all failure interleavings and production HA remain unverified. Run `TEST_DATABASE_URL=... cargo test --locked --lib resend_queue::tests::workflow_delivery_revalidates_subscriber -- --ignored` against a **fresh disposable** database; the fixture creates schema objects.

`SWALLOW_ALERT_FANOUT_TARGET_TIMEOUT_SECONDS` optionally limits each alert-fanout child to 1–3600 seconds; unset or `0` disables the limit. On timeout the parent attempts to kill and reap that child for up to two seconds, reports `timed out; outcome unknown`, returns failure, and continues the remaining destinations subject to concurrency and shutdown policy. It does not retry the timed-out target. The child may already have sent an alert or committed DB state; inspect its alert slot and provider evidence before taking action. A forced stop can leave a slot in flight until normal recovery, and killing the direct child does not guarantee termination of descendants or a process stuck in the kernel. The timeout starts after the child is spawned and does not cover reading the fanout configuration itself; slow filesystem operations can still block that read; the optional regular-file policy described above rejects FIFOs on Unix. Test fixture child processes verify both alert modes, subsequent destinations, no automatic second attempt, direct-child termination and invalid limits. A separate Unix process test stalls the real delivery alert command on a FIFO and confirms the next target is attempted. These tests do not send an external alert or demonstrate production process supervision, DB recovery or filesystem stalls.

For startup secrets loaded through `novu_rust_contracts::secret::from_env`, `SWALLOW_SECRET_REGULAR_FILES_ONLY=true` opts into reading only regular files, including symlinks to regular files; the default `false` preserves existing behavior. On Unix the opened file is checked after a nonblocking open, so a FIFO with no writer is rejected instead of hanging the process. This applies to the shared `from_env` calls used by delivery and database Slack/email alert commands and other consumers, including alert-fanout child processes that inherit the setting. Invalid policy values and simultaneous inline/file sources are rejected. Existing secret size and content limits still apply. It also covers the FCM worker’s non-reloaded `NOVU_FCM_PRIVATE_KEY_FILE` and `NOVU_FCM_INTEGRATIONS_FILE`, including their multiline size limits. FCM reload modes already require regular files independently of this setting. Other direct file reads and external clients are not covered; changing the variable does not reload a running process. A slow or stalled filesystem may still block regular-file reads; non-Unix FIFO behavior is unverified. Protect secret files and monitor each target: a rejected credential can prevent that target's alert. Unix process tests exercise both actual alert commands with FIFO Slack/Resend credentials, symlinked regular files, conflicting sources and invalid policy. FCM tests reject FIFO private-key and integration files without reload and start the actual worker using symlinks to valid test credentials against local PostgreSQL. No external alert or FCM notification is sent.

# Reloadable credential file types

Reloadable Resend, SendGrid, Twilio and standalone Slack credential files must resolve to a regular file. On Unix the worker opens them with nonblocking mode before checking the opened handle, so a FIFO without a writer is rejected instead of hanging; symlinks to regular files remain supported. This applies at startup and reload only when the reloadable source is selected. Legacy startup-only sources retain their previous behavior. Filesystem operations on a slow or unavailable filesystem may still block; nonblocking mode is not a filesystem timeout. Tests exercise FIFO startup for all four workers, a FIFO during a running Slack worker with Docker PostgreSQL, and symlink-to-regular-file reading. Non-Unix blocking behavior and production secret mounts are not tested.

# Optional completed attachment cleanup

Worker migration `0133` and `attachment-retention` provide an opt-in, environment-scoped cleanup of attachment bytes in completed workflow and workflow-generated Resend/SendGrid queue jobs. They do not run on a schedule. Pending, running, failed, cancelled and standalone email jobs are excluded. Completion means queue processing completed, not recipient delivery. This crate contains experimental Rust/PostgreSQL queue and worker implementations used by the Rust API. It is **not a fully Novu-compatible worker**. Do not deploy it as a replacement. The target is 100% compatibility with the selected Novu version, but this crate does not establish that compatibility.

The migration defines a queue table. Claim and recovery policy are deliberately separate: automatically retrying every expired job could change Novu's delivery semantics or duplicate external side effects. An experimental worker loop supports the limited in-app and Inbox prototype described in the [API README](../../api/rust-api/README.md). It atomically creates simple subscriber and message records and completes a job; complete Novu Inbox compatibility is not established. On startup and at most every five seconds, this worker requeues expired leases **only for its in-app job kind**; other job kinds still require an explicit recovery policy. A malformed job or an input unsupported by the experimental renderer is recorded as failed without storing the payload in the diagnostic, and the worker continues. Database failures still terminate the process and require an external restart; there is no attempt limit for crash recovery. This is an experimental safety policy, not a verified reproduction of Novu's job failure or retry behavior. The migrations are initial development artifacts, not a production migration system; run them only on an isolated database.

If a lease expires while waiting or processing, the worker rolls the transaction back and continues; periodic recovery can requeue the job. Queue completion, failure, retry and renewal validate the lease after taking the row lock. Repeated expiration under sustained contention remains possible; throughput, concurrent behavior and the retry policy have not been compared with Novu.

## SendGrid delivery projection

Set `NOVU_SENDGRID_ENVIRONMENT_ID` and run `sendgrid-projection-worker` with database access to the queue, attempts, recipient snapshots, email messages, signed webhook events, and projection heartbeat. `NOVU_SENDGRID_PROJECTION_DB_TIMEOUT_SECONDS` defaults to 30 (1–300). The worker repeatedly scans each environment in pages of 100, locks each job, and records recipient and aggregate `sendgrid_delivery_result` values without changing the original queue status or dispatch attempt. It writes a heartbeat after each complete traversal. Locked jobs can be skipped; events arriving after a scan are reflected on a later pass. Monitor the process and heartbeat independently. Repeated full-history scans and their performance at scale are not yet validated.

Only signed events bound to the current dispatch with a verified proof, matching message and exact recipient hash are used. A permanent bounce or dropped event is failed; a temporary blocked bounce is pending; delivery and failure evidence together are conflicting. Missing subtype, duplicate addresses, unmatched current events, old sends without snapshots and other ambiguous evidence remain unknown. An accepted attempt without final evidence is pending. Aggregate results are unknown, pending, delivered, failed, partial or conflicting. A delivery event reports acceptance by the receiving server, not that a person read the message. Unverified or older dispatch events do not establish the current result; address spelling differences can prevent matching. Snapshot hashes are sensitive to dictionary guessing.

The projection is an additional database field, not an original Novu-compatible status API, and it neither changes attempt or job status nor decides retries. The integration test uses synthetic signed webhooks and a disposable Docker PostgreSQL, including reconnect and environment isolation; real SendGrid webhooks, production volume, prolonged outages and original Novu parity for this projection have not been verified.

### Transaction-scoped projection authorization

### Optional alert scheduler

`alert-scheduler` runs the existing `alert-fanout` immediately and then waits a fixed delay **after each run finishes**. It accepts the same fanout arguments after a required 1–86400 second interval, for either delivery or database alerts:

```sh
alert-scheduler 60 delivery ENV 300 120 60 /absolute/path/targets.json
alert-scheduler 60 database ENV DATABASE_LABEL 60 /absolute/path/targets.json
```

It waits for a run to finish before starting another in the same process. A run's exit 2 is reported as `attention required`; other failures, including a missing executable, are logged as failures. By default it continues after failures; `SWALLOW_ALERT_SCHEDULER_FAILURE_MODE=exit` instead exits nonzero on a failed run, allowing a supervisor to restart or alert. This setting does not turn attention (exit 2) into failure. Monitor logs, process liveness, absent runs and child outcomes independently: a running scheduler does not establish that checks succeeded or alerts reached recipients. An external scheduler remains an alternative.

SIGTERM or Ctrl-C prevents a new run and allows the current fanout to finish for `SWALLOW_ALERT_SCHEDULER_SHUTDOWN_GRACE_SECONDS` (default 30; 1–300). If grace expires, the scheduler exits with an error. On Unix it starts each fanout in a separate process group and sends SIGKILL to that group on timeout; elsewhere it kills only the direct child. This cannot stop a descendant that escaped the group, a process stuck in uninterruptible kernel sleep, or survive abrupt scheduler termination such as SIGKILL. A provider may already have accepted a request; never infer non-delivery or immediately retry. The fixed delay is not a clock-aligned schedule or missed-run replay. Multiple scheduler instances do not coordinate scheduling or guarantee exactly-once delivery: existing database reservation and cooldown policies apply per target, while uncoordinated fallback can duplicate alerts. Database outages, shared failure domains, long/hung children and scheduler failure still need independent monitoring.

### Discord 429 retry policy

Apply worker migration `0208` before deploying this version of `discord-webhook-worker`; the new worker requires the tables even when retry is disabled. `NOVU_DISCORD_429_RETRY_MODE` is `off` by default, `known` to retry only an HTTP 429 with a valid provider delay, or `fallback` to use `NOVU_DISCORD_429_FALLBACK_SECONDS` when no valid delay is available. `NOVU_DISCORD_429_MAX_RETRIES` defaults to 3 and accepts 0–10; the fallback defaults to 60 and accepts 1–86400 seconds. The delay is at least one second. These are retries after the first attempt, bounded per job across worker restarts. Invalid startup settings fail the worker. `fallback` is an explicit availability tradeoff: missing, malformed, duplicated, timed-out or over-24-hour guidance is indistinguishable from no guidance and can cause a retry earlier than the provider intended. A proxy-generated 429 may not establish what happened at Discord. Choose the mode and fallback with this risk in mind. Responses classified as unknown, including connection loss and 5xx, are never automatically retried by this policy.

The first worker registers the mode, retry limit and fallback for its environment and destination; another worker with different values rejects startup. The database fence rejects new attempt inserts by incompatible workers while `known` or `fallback` is enabled; it cannot cancel an outbound request already reserved before the switch and privileged SQL can bypass it. Direct policy changes while workers run are not audited and take effect for later queue operations; restarting workers with stale settings then fails. No grant-management API or UI for this policy is provided.

Each scheduled 429 is atomically copied to `novu_rust_discord_retry_history`, removed from the current attempt table, and the job is requeued for the calculated delay. Every new workflow attempt rechecks subscriber identity, preferences, workflow and endpoint revision. History remains after success; when the retry limit is exhausted the current 429 remains rejected and visible to existing health checks. Scheduled 429 history is not included in current Discord health or review counts. History retention and monitoring are operator responsibilities. A failure to commit the history or queue update leaves the prior dispatching attempt to expire as unknown; it is not retried automatically. The fence is cooperative and the protected tables and function owner must not be exposed to untrusted writers.

The worker DB login additionally needs SELECT, INSERT and UPDATE on `novu_rust_discord_retry_policy`, SELECT and INSERT on `novu_rust_discord_retry_history`, USAGE on `novu_rust_discord_retry_history_id_seq`, and DELETE on `novu_rust_discord_attempts` in addition to its previous privileges. ### Discord workflow mixed-version fence

Worker migration `0206` creates `novu_rust_discord_workflow_policy`, initially disabled for every existing and newly created environment. With the migration applied, `NOVU_DISCORD_WORKFLOW_ENABLED=true` enables the new worker capability, but each environment still needs its policy explicitly set to true by a trusted DB administrator, for example `UPDATE public.novu_rust_discord_workflow_policy SET enabled=true WHERE environment_id=...`. A capable worker can serve both enabled and disabled environments. The in-app worker DB login needs EXECUTE on `public.novu_rust_discord_workflow_guard(text,uuid,uuid)` when the process setting is true. The function and trigger owner must read and lock policy rows and queue jobs; the environment-insert trigger owner must insert policy rows. Do not grant direct policy mutation to application workers. The independently authorized policy CLI is described below; no HTTP policy API or UI is provided yet.

For enabled environments the compatible worker locks the policy and sets a transaction-local marker tied to the job and lease before writing child jobs and completing the parent. A database trigger rejects a legacy or disabled worker that tries to mark a running in-app/attachment job completed or failed without the marker; its transaction rolls back, and lease recovery can make it available to an updated worker. A compatible worker can still mark malformed jobs failed. Policy changes wait on in-flight policy locks. Jobs completed before enablement are not backfilled, and already-running or externally dispatched work is not reversed. Legacy workers may repeatedly claim and fail, causing backlog; monitor queue age and remove them.

To avoid a gap for an existing deployment that used the previous process-only option, stop or drain in-app workers, apply `0206`, explicitly enable each desired environment, deploy compatible workers with the process option and EXECUTE permission, then resume. Migration takes a lock on the environments table, backfills policy rows and adds a trigger; assess locking, privileges, rollout and monitoring before deployment. Disabling policy stops generation only after in-flight guarded transactions finish; changing only the process option while policy remains enabled will block affected jobs. These cooperative checks are not an authorization boundary: a DB role able to run arbitrary SQL and set session variables, a privileged policy editor, disabled triggers or direct data changes can bypass them. Missing or deleted policy rows fail closed. A selected historical worker binary is tested as described below; production load, replica failover and multi-host HA remain unverified.

It checks policy initialization, restricted role, enablement locking, stale leases, transaction-local marker and disabled environments. The API `discord_workflow` integration test exercises a disabled-capability worker failing to commit in an enabled environment, lease recovery, a compatible worker, malformed job handling and mocked delivery. It simulates old behavior with the current queue function; it does not execute an old worker binary.


`apps/worker/rust-queue/scripts/test-discord-legacy-worker.sh` (from the repository root) builds the `75cd2ecc` pre-fence in-app worker from an isolated Git archive and starts its own disposable Docker PostgreSQL. ### Discord workflow policy administration

Apply worker migration `0207` after `0206`. A trusted DBA provisions a row in `public.novu_rust_discord_policy_admins` for the exact environment and login name/OID with `can_read`, `can_write` and `can_audit` independently selected. Grant the login EXECUTE only on the appropriate `public.novu_rust_discord_policy_read(text)`, `public.novu_rust_discord_policy_set(text,uuid,bigint,boolean,text)`, `public.novu_rust_discord_policy_request(text,uuid)` and `public.novu_rust_discord_policy_audit_read(text,bigint)` functions. The security-definer owner requires access to the admin, policy, request and audit tables and the audit identity sequence. The restricted login needs no direct table access; protect the function owner and direct DB policy writes. No user or DB login receives policy rights by default.

`delivery-reconcile discord-policy-read ENV` returns `enabled` and a decimal-string revision. `discord-policy-set ENV REQUEST_ID EXPECTED_REVISION enabled|disabled REASON` locks the policy, rejects a stale revision and records the change and request atomically. Repeating exactly the same request with the same DB login and role OID returns the stored result; changing its input is rejected. `discord-policy-request ENV REQUEST_ID` looks up that login's request, and `discord-policy-audit ENV [BEFORE]` returns up to 50 reverse-ID entries with a cursor. Every policy UPDATE, including direct updates and same-value writes, increments the revision; direct DB writes do not receive an API audit. A successful same-value CLI write is audited and increments the revision. A failed audit insert rolls back both change and request. Policy updates wait for guarded workers holding the policy lock; enablement alone does not start workers or register destinations.

Audit uses the DB session login and is not tamper-proof; shared logins cannot identify individual operators. Reasons must not include secrets or personal data. Audit is retained when an environment is deleted and a reused environment ID can therefore show older audit entries; requests and administrator grants are deleted with the environment. The audit sequence order is not commit order, and separate pages are not a consistent snapshot. Rejected requests and direct DB changes are not audited. Protect audit data and arrange retention independently. Environment policy settings before migration are not retroactively audited. The experimental JWT policy API, JWT grant delegation and dashboard are described in the [API README](../../api/rust-api/README.md) and [dashboard README](../../dashboard/swallow/README.md); actual production load and HA are unverified.

`TEST_DATABASE_URL=... cargo test --manifest-path apps/worker/rust-queue/Cargo.toml --test discord_policy_admin -- --ignored` creates a fresh disposable PostgreSQL schema and login roles. It checks independent rights, tenant isolation, replay, stale and concurrent updates, audit rollback, a held policy lock and direct-update revision changes; it does not contact Discord or test multi-host HA.
