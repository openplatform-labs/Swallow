# Experimental PostgreSQL queue primitives

This crate is an isolated starting point for a Rust/PostgreSQL rewrite. It is **not a Novu-compatible worker** and is not wired into the existing service. Do not deploy it as a replacement. The target is 100% compatibility with the selected Novu version, but this crate does not establish that compatibility.

The migration defines a queue table. The library exposes transactional enqueue (including delay), per-kind claim with `SKIP LOCKED`, lease renewal, token-fenced completion, failure and retry, pending-job cancellation scoped by environment, and explicit recovery of expired jobs. Claim and recovery policy are deliberately separate: automatically retrying every expired job could change Novu's delivery semantics or duplicate external side effects. The shared [`trigger_gate`](../../api/rust-contracts/src/trigger_gate.rs) module reproduces a small, explicitly bounded part of the stored-workflow trigger decisions from the reference source; it does not implement the full API or workflow engine.

Migration `0053` adds `delivery_state` to experimental email, SMS and push history: `not_attempted`, `dispatching`, `in_progress`, `accepted`, `rejected` or `unknown`. `accepted` means provider acceptance, not delivery. Expired in-flight attempts are reflected as `unknown`; existing historical rows without reliable attempts remain unknown. Novu-compatible `status` is retained separately and can still read `sent` without proof of delivery. This state is currently database-only; webhooks, actual delivery confirmation and alerting are not implemented. Each attempt adds history updates, and FCM target groups add an aggregation query.

Migration `0054` provides an operator decision log. `cargo run --bin delivery-reconcile -- list ENV` lists up to 100 unknown attempts without payloads. After independently checking the provider, `cargo run --bin delivery-reconcile -- retry ENV JOB - OPERATOR TICKET` requeues one confirmed-unaccepted email/SMS attempt; use a numeric target index instead of `-` for FCM. Replace `retry` with `accepted` only after confirming provider acceptance. A wrong retry decision can duplicate a delivery; no provider verification is automated. Email/SMS retries re-read subscriber and preference data and may render different content. The tool requires privileged DB access, records the supplied operator, DB user and reason, and serializes conflicting decisions; the operator name itself is not authenticated. Restrict DB and audit-table update/delete privileges separately and do not put secrets or PII in the reason. The list has no pagination, standalone FCM acceptance may leave the job failed, and actual provider webhooks, delivery confirmation and production operator RBAC are incomplete.

An experimental worker loop supports the limited in-app and Inbox prototype described in the [API README](../../api/rust-api/README.md). It atomically creates simple subscriber and message records and completes a job; complete Novu Inbox compatibility is not established. On startup and at most every five seconds, this worker requeues expired leases **only for its in-app job kind**; other job kinds still require an explicit recovery policy. A malformed job or an input unsupported by the experimental renderer is recorded as failed without storing the payload in the diagnostic, and the worker continues. Database failures still terminate the process and require an external restart; there is no attempt limit for crash recovery. This is an experimental safety policy, not a verified reproduction of Novu's job failure or retry behavior. The limited interpolation implementation can be checked against the reference `handlebars@4.7.10` by installing that package in a temporary directory and running `NODE_PATH=/path/to/node_modules cargo test --test reference_template -- --ignored`. There is no scheduler process, cancellation of running work, generic queue deduplication, general retry/backoff or complete workflow integration with external providers. In particular, a lease cannot prevent an already-started external call from completing after lease expiry. Consumers must decide their side-effect and recovery policy. The migrations are initial development artifacts, not a production migration system; run them only on an isolated database.

Overlapping in-app batches acquire transaction-scoped advisory locks in sorted hash-key order before subscriber row locks, preventing opposite recipient order deadlocks between these workers while preserving recipient processing order. This adds one query per job and one lock per distinct subscriber hash; collisions can serialize unrelated work. If a lease expires while waiting or processing, the worker rolls the transaction back and continues; periodic recovery can requeue the job. Queue completion, failure, retry and renewal validate the lease after taking the row lock. Repeated expiration under sustained contention remains possible; throughput, concurrent behavior and the retry policy have not been compared with Novu.

Run static checks with `cargo test` and `cargo clippy --all-targets -- -D warnings`. To launch a disposable PostgreSQL 17 Docker container, run `./scripts/test-postgres.sh`; it binds a random loopback port and removes the container on exit. The script runs both the queue contract and a test that starts the actual in-app worker to exercise lease recovery, rollback and failure isolation.

Alternatively, the integration test deliberately **drops and recreates** `novu_queue_jobs`; run it only against a disposable PostgreSQL database:

```sh
TEST_DATABASE_URL='postgresql://USER:PASSWORD@localhost:5432/DISPOSABLE_DATABASE' \
  cargo test --test postgres -- --ignored
```

The integration test is ignored by default so an unset database is not mistaken for a successful database test. For architectural context and compatibility requirements see [the design record](../../../RUST_POSTGRES_DESIGN_KO.md).

The in-app worker also processes `experimental-in-app-unsnooze` jobs with `subscriberId` and `notificationId` payload fields. It locks the subscriber, clears the snooze, makes the message unread, appends the delivery timestamp and completes the job atomically. Manual unsnooze cancels one matching pending job. The experimental API creates these jobs; reference retries and execution details remain unsupported. Each new in-app message or automatic unsnooze attempts to add an event to `0030_experimental_ws_events.sql` in the same transaction. `0031_experimental_ws_best_effort.sql` drops event-write failures without rolling back the message, matching the reference queue's best-effort policy. The experimental WS service can deliver a limited notification and counts from these events; reliable replay is not implemented. The worker checks for due unsnooze jobs before in-app jobs and performs an additional orphan-job query when none are due.

The single-step prototype uses migration `0033_experimental_in_app_step_active.sql` to distinguish an existing inactive step from the absence of steps. New-format jobs examine the current flag and `has_steps` at processing time; with no active step they update the subscriber but create no in-app message or step outcome. Older jobs retain their existing behavior. Migration `0034_experimental_notifications.sql` adds a partial notification record even without an active step; the full reference notification model remains incomplete.

The worker inserts one experimental notification per accepted recipient, including when the single in-app step is inactive or channel preferences suppress delivery. New messages refer to that notification; subscriber deletion leaves notification history. The reference comparison covers selected fields, active and inactive steps, message linkage and subscriber deletion. The table does not implement topics, workflow-run API, all reference fields, legacy-data backfill or full failure semantics; notification/message/job completion are committed together in Rust, unlike the original multi-stage workflow. Each recipient adds a notification insert and an index write.

`src/sendgrid.rs` provides an experimental standalone SendGrid HTTP adapter for HTML email, including global/EU endpoints, basic recipient lists, sender, reply-to, headers and Novu tracking arguments. The original provider wire body is compared in `tests/reference_sendgrid.rs`; local HTTP tests cover one-shot submission, 429 and redirects. It is connected to the experimental environment-scoped queue consumer and the limited manually configured email workflow step described below, but not to integration management or Novu delivery status. Dynamic template data, string alternatives and byte-array attachments are supported by the adapter, with selected request bodies compared to the original provider. Trigger attachment handling, arbitrary alternative binary content, provider passthrough, webhook handling and Novu-compatible retry and recovery are unsupported; no real provider delivery has been tested. Never treat a transport error as proof that a message was not accepted. Run the reference comparison with `NOVU_REFERENCE_SOURCE=/path/to/built/reference cargo test --locked --test reference_sendgrid -- --ignored`.

`src/twilio.rs` is an experimental SMS adapter supporting US/EU endpoints, account-token or API-key Basic authentication and form-encoded to/from/body. Three cases compare the built original provider's endpoint, request fields, credentials and response; a local mock exercises both authentication modes, 201, 429 and redirect rejection. Run `NOVU_REFERENCE_SOURCE=/path/to/built/reference cargo test --locked --test reference_twilio -- --ignored` for the original comparison.

`src/fcm.rs` provides experimental FCM message planning and a bounded HTTP v1 sender using a caller-provided OAuth access token or service-account credentials. Seven comparisons check the original provider's Firebase message plans; four compare the original firebase-admin's validated HTTP message conversion. Local HTTP tests check token-by-token multicast submission and 200/429 results. Limited manually configured workflow and queue processing are described below; FCM-only subscriber credentials are described below; integration management APIs are not connected. Service-account OAuth uses an RS256 assertion, the original Firebase Admin scope set and token endpoint, and caches tokens until five minutes before expiry; concurrent refreshes are serialized. Original google-auth-library claims and a local OAuth-to-FCM mock were compared using generated test keys. Private keys and tokens remain in process memory; credential rotation, real Google OAuth, Android/APNs/WebPush options, exact multicast result/error behavior, retries and real FCM delivery are not implemented or verified. Unsupported platform fields are rejected at HTTP conversion. Multicast sends sequentially, one request per token; a transport failure is ambiguous. Run `NOVU_REFERENCE_SOURCE=/path/to/built/reference cargo test --locked --test reference_fcm --test reference_fcm_wire -- --ignored` for the provider source comparisons. The OAuth comparison also requires OpenSSL: `NOVU_REFERENCE_SOURCE=/path/to/built/reference cargo test --locked --lib google_oauth::tests::original_google_auth_claims_match -- --ignored`.

`fcm-worker` consumes `experimental_fcm_push` jobs; all jobs require worker migrations through `0054` in order. Configure `DATABASE_URL`, `NOVU_FCM_ENVIRONMENT_ID`, `NOVU_FCM_PROJECT_ID`, and either `NOVU_FCM_ACCESS_TOKEN` or `NOVU_FCM_CLIENT_EMAIL` plus PKCS#8 PEM `NOVU_FCM_PRIVATE_KEY`. The job payload uses the snake_case `Push` fields: `title`, `content`, `targets`, `payload`, `overrides` and `provider_data`; it contains device tokens and content but no provider credentials. The worker records one attempt before each target request, requeues remaining targets after each result and marks an expired dispatch as unknown rather than automatically sending it again. If any target is unknown the job fails even when other targets succeeded; without unknowns, one acceptance completes the job, while all rejections fail it. A crash after recording an attempt but before requesting FCM can lose that target. Docker PostgreSQL and mock HTTP tests cover competing workers, isolation, mixed/all rejection and recovery; these queue semantics have not been compared with original Novu or real FCM. Workflow creation, message history, complete invalid device-token cleanup and full provider outcomes remain incomplete. Each target adds a queue lease, attempt insert and result transaction.

Migration `0046` introduced one manually configured FCM workflow step and subscriber device-token row. The trigger creates a recipient job; at dispatch it rechecks subscriber, workflow and selected push preferences, reads stored devices, renders supported title and body variables, and prepares one FCM request and independent message ID per device. Prepared requests are persisted before dispatch and reused on recovery. Four original-server cases compare one and two devices, missing devices and disabled push through mocked FCM; independently generated IDs are checked only for format. Later changes add limited subscriber credentials, message history, invalid-token cleanup and multiple integrations as described below. Full device registration and integration management APIs, template/override behavior, all queued changes and original retry semantics remain incomplete or unverified. Changes after preparation do not update already prepared targets. This adds a job and outcome insert per recipient, a subscriber query and lock per preparation, an ID query per target and storage for the prepared requests.

Migration `0047` initially adds one manually configured FCM integration identity per environment (extended by `0051`) and connects the bounded subscriber credentials API to the device row. `PUT` replaces tokens, `PATCH` appends unique tokens in order, and an empty array clears tokens; `DELETE` removes the FCM channel. The reference harness compares these operations and v1/v2 individual subscriber responses before triggering FCM delivery. The integration management API, full integration selection, other credential fields and providers, full validation/error details and broader timestamp behavior are incomplete or unverified. Selected no-op credential updates and FCM channel data in v2 lists are compared with the reference. Before preparing delivery the worker checks that the registered integration identity still exists and is active; legacy manually inserted device rows without an integration ID bypass this check. Subscriber deletion cascades the device row, and each individual subscriber response performs an additional channel query.

FCM workflow delivery checks `Requested entity was not found` in the message generated by the pinned Firebase SDK error conversion. Unknown JSON errors and non-JSON errors include the raw response in that message, so unrelated data containing the phrase can cause the same false-positive token removal as the reference. When `IS_EXPIRED_TOKENS_REMOVAL_ENABLED=true`, the worker removes that token only from the original environment, subscriber internal ID and integration ID; the default is disabled. The reference harness compares mocked invalid-token behavior with the flag enabled and disabled, including mixed valid and invalid tokens and preservation after a generic error when enabled. Sixteen JSON and non-JSON cases are compared against the pinned Firebase SDK and Novu provider using `NOVU_REFERENCE_SOURCE=/path/to/built/reference cargo test --locked --lib original_firebase_error_classification_matches -- --ignored`. Error bodies over 16 KiB, other SDK conversion cases, integration changes and other concurrent mutations during delivery, legacy jobs and real FCM failures are unsupported or unverified. Raw provider error bodies are not stored. Unlike the reference, cleanup is part of the fenced result transaction: a database error can fail that transaction, and cleanup is not retried after a lease loss. Removal adds a device-array and subscriber-timestamp update.

`tests/reference_push_race_compare.py` holds mocked FCM responses while changing tokens or deleting and recreating a subscriber, then compares cleanup with the original. Five selected cases match with cleanup enabled. Recreating the subscriber prevents the old attempt from removing its tokens, while re-registering the same token on the same subscriber does not protect it from removal. The comparison covers one integration and one target; it does not establish behavior under arbitrary concurrency or with a real provider.

Migration `0051` supports multiple manually configured FCM integrations and channel-specific device tokens. Set `NOVU_FCM_INTEGRATIONS` to a JSON object keyed by integration internal ID; each value contains `project_id` and either `access_token` or both `client_email` and PKCS#8 PEM `private_key`. Credentials remain in process environment and memory; this is not a production secret manager. The worker snapshots per-target integration and channel tokens, and refuses the entire job before sending if any active target lacks configured credentials. Existing `NOVU_FCM_PROJECT_ID` single-provider configuration remains available for one channel and rejects multiple channels. The original-server harness compares registration, reads, three mocked sends with distinct test authorization headers, selected message history, disabled-integration selection, per-integration invalid-token cleanup, missing-credential behavior and a worker restart between targets. Full routing overrides, conditions, integration management, credential rotation, all error/retry semantics, legacy queued jobs and real FCM are incomplete or unverified. The mapped mode requires integration metadata and does not send standalone or older prepared jobs without it. A multi-channel preparation adds one channel query and stores per-target routing metadata in PostgreSQL.

For workflow triggers, legacy `overrides.fcm` accepts a nonempty `deviceTokens` string array, string-valued `data`, and `type` of `data` or `notification`. For an eligible channel with registered tokens, it replaces the per-channel targets and applies the data to the FCM message; overrides are persisted in the trigger and push queue payloads. The original-server harness compares target replacement, notification data and data-only requests and selected history against mocked FCM. Migration `0052` adds a manually configured `push_step_id`; global `providers.fcm` and the matching step's provider override support string-valued `data`, notification `title`, `body`, `imageUrl`, and those fields inside `_passthrough.body`. Global and step layers merge in order, then passthrough is applied last. The original comparison covers conflicting data and title/body values and an unrelated step, but not `imageUrl`. Provider-wide `token` routes send once per populated active subscriber integration; `topic`, `condition`, and subscribers with no populated channels use the newest active integration. Five single-integration original-server cases compare these routes, step precedence and passthrough precedence; three multi-integration cases compare token fan-out, topic selection and token fallback, using mocked requests and selected history. Multiple token-route integrations require the mapped worker configuration. Conditional integration selection, equal creation times and absence of active integrations are not fully compared. Integration and bridge overrides, platform options, empty target arrays, other data types, and complete multi-integration and error/concurrency behavior remain unsupported or unverified; real FCM has not been tested. Direct routes add one active-integration query and store target metadata in the queue. Apply migrations through `0054`; existing workflows need a step ID configured to use step overrides.

Provider-wide and step `tokens` routes accept 1–500 nonempty strings and send once per eligible integration, or use the newest active integration when there is no populated channel. Each token is sent as a separate sequential HTTP request, while one message ID and history record are shared per integration. Original-server comparisons cover global, step and passthrough routing with successful mocked responses and an all-rejected case. Selected partial success, restart between targets and two-integration cases were compared using mock providers; crashes during dispatch and real FCM remain unverified; unknown outcomes result in an error even if another token was accepted, unlike the original SDK aggregation. The history is provisional until all group results are recorded. Group result aggregation adds a database query per target, in addition to per-target dispatch transactions.

For example, the value of `NOVU_FCM_INTEGRATIONS` can have this shape, with actual secrets supplied by the deployment environment:

```json
{
  "integration-internal-id-1": {"project_id": "project-a", "access_token": "<oauth-token-a>"},
  "integration-internal-id-2": {"project_id": "project-b", "client_email": "service@example.test", "private_key": "<PKCS8-PEM>"}
}
```

`sendgrid-worker` consumes only `experimental_sendgrid_email` jobs for `NOVU_SENDGRID_ENVIRONMENT_ID`. Apply all worker migrations in order for workflow-produced jobs; standalone jobs require queue migration `0001_jobs.sql`, `0035_experimental_sendgrid_attempts.sql`, `0037_experimental_email_messages.sql`, and `0038_experimental_email_provider_result.sql`; configure `DATABASE_URL`, `NOVU_SENDGRID_API_KEY`, `NOVU_SENDGRID_FROM`, `NOVU_SENDGRID_SENDER_NAME` and optionally `NOVU_SENDGRID_REGION=eu` (default `global`). Queue payloads use the snake_case fields in `sendgrid::Email`; the experimental workflow processor creates them for configured email steps. Credentials are supplied through the process environment rather than queue payloads or the database.

The worker writes a dispatch marker before each external request. On lease expiry, jobs without a marker are requeued, while marked attempts become `unknown` and are not automatically resent. 2xx is recorded as provider acceptance, 4xx as rejection and transport/5xx as unknown; acceptance is not proof of delivery. PostgreSQL plus a local mock verifies these states, two-worker claiming, tenant separation and crash-boundary recovery. This conservative policy is not compared with Novu's retry behavior; provider webhooks, operator reconciliation, production secret management, full multi-tenant integration configuration and full workflow execution remain unimplemented. The worker can still lose a delivery when it crashes after recording the marker and before sending, and message data in jobs is stored in PostgreSQL. Per dispatch it adds a marker transaction and a result transaction; recovery locks up to 100 expired jobs per pass.

Migration `0040_experimental_email_revalidation.sql` extends email outcome states. New workflow email jobs recheck the subscriber by external ID and current email preference under a subscriber row lock before dispatch, rerender the supported template with the current profile, and cancel or fail without sending when a preference is disabled or the subscriber is absent. The reference comparison pauses the original standard queue after job creation and compares changed email/name, disabled preference, deletion, enabling a preference and adding an address through mocked SendGrid. Changes after dispatch starts, deduplicated-step mode, workflow cache behavior and actor/context deletion or concurrent changes while queued are not equivalent or unverified. Queued metadata retains templates, payload, context and override values. Each dispatch adds a subscriber/preferences query and lock, message insert and template render.

New workflow email jobs store context keys and refresh the actor profile and context data at delivery; older jobs lacking context keys retain their stored context snapshot. The original-server comparison changes the actor and context after queueing and compares the mocked SendGrid output. Actor lookup adds one query when distinct from the recipient and context lookup adds one query when keys exist. Deletion, recreation, concurrent changes and all template forms remain unverified.

New workflow email jobs recheck that their workflow exists before dispatch and compare its internal ID when configured. With the reference default step-dedup flag off, a queued email uses its stored template snapshot; a deleted or replaced workflow fails without sending. The original-server comparison covers these selected cases. Reference step-dedup hydration, cache behavior, step changes and replacement where the experimental workflow has no internal ID remain unimplemented or unverified. The workflow existence lookup is included in the existing subscriber query.

If a subscriber is deleted and recreated with the same external ID before delivery, the original and Rust compatibility mode use the new profile and address while retaining the old internal subscriber ID in the job/message history. The default Rust safety mode rejects the changed internal identity for workflow email, SMS and push; new trigger jobs also snapshot direct recipient identities. FCM prepared jobs recheck identity between targets. Set `NOVU_ALLOW_RECREATED_SUBSCRIBER=true` in API and worker processes only when the original behavior is required. Existing trigger jobs without snapshots fail in the default safety mode; standalone jobs and some topic/actor races are not fully protected or tested; already-started external requests cannot be recalled. The comparison verifies this selected scenario. Reusing an external ID for a different person can therefore deliver a previous pending notification to that person. Concurrent deletion/recreation and the full preference and message API behavior remain unverified.
