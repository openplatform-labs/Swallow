## Idempotent WS event retention requests

Worker migration `0169_ws_retention_requests.sql` adds the optional `delete-v2` and `request` paths. Keep the same cutoff, batch limit, request UUID and reason when repeating an uncertain request:

```sh
ws-event-retention delete-v2 ENV 2024-01-01T00:00:00Z 100 REQUEST_UUID 'retention ticket'
ws-event-retention request ENV REQUEST_UUID
```

In addition to the environment-scoped `can_delete` grant described below, grant the maintenance DB login EXECUTE on `public.novu_rust_ws_retention_delete_v2(text,timestamptz,integer,uuid,text)` and `public.novu_rust_ws_retention_request(text,uuid)`. Request identity is scoped to the environment and original database login name and role OID. Within that scope, the same UUID and same parameters return the original count and `replayed: true` without deleting another batch; different parameters conflict. A separate login or environment has its own request namespace. Request lookup returns the stored result and reason only to the same login while its `can_delete` permission is valid. A not-found result does not prove a concurrently running transaction will not commit. Revoked users cannot replay or look up their earlier requests.

The request record, deletion and audit (including request UUID) commit together. The original cutoff and count are historical: they do not describe the current table and do not prove all instances consumed the rows. Keep each UUID and exact parameters in a trusted operational record. A new UUID intentionally deletes another batch. Request records and audit records require a retention and access policy; deleting or restoring them from an older backup can defeat deduplication. Direct DB writes and the legacy `delete` path bypass this protection. Migration 0169 also enforces the documented 512-byte full reason limit for new legacy and v2 audit records; pre-existing entries are not validated. The manual selection and event-loss warnings below continue to apply.

The disposable PostgreSQL 17 local test runs two simultaneous CLI processes with the same request UUID, checks only one batch is deleted and one audit written, exercises request lookup, conflicting replay, another login and revocation, and verifies audit failure rolls back the request and deletion. It simulates a lost response by repeating the completed call; a real network interruption, production HA, failover and restore behavior remain unverified.

## Optional WS event retention maintenance

The WS event table stores ephemeral Socket.IO notification payloads and is not a replay log. Worker migration `0168_ws_event_retention.sql` adds an environment-scoped maintenance function, an audit table, and an index on `(environment_id, created_at, id)`. It does not delete anything automatically. Building the index can block writes and increase storage/write cost; assess table size, backups, and deployment timing before applying it.

A database administrator grants a dedicated login schema USAGE and EXECUTE on `public.novu_rust_ws_retention_batch(text,timestamptz,integer,boolean,text)`, and inserts one row per environment in `public.novu_rust_ws_retention_grants` with the login name, its current `pg_roles.oid`, and independent `can_preview` / `can_delete` flags. The function checks and share-locks this grant during the transaction. The maintenance login does not need direct event or audit table access. The owner of this SECURITY DEFINER function must be a trusted role, and grants, audit records and direct table access must remain restricted. DB administrators can inspect `novu_rust_ws_retention_audit` for the caller, cutoff, batch size, deleted count and reason. Role recreation requires a new OID grant; an audited delete failure rolls the entire batch back.

Build `cargo build --locked --bin ws-event-retention`, then configure `DATABASE_URL` and TLS as for the WS server. Choose the UTC cutoff and batch size according to the deployment's actual recovery delay, for example:

```sh
ws-event-retention preview ENV 2024-01-01T00:00:00Z 100
ws-event-retention delete ENV 2024-01-01T00:00:00Z 100 'retention ticket'
```

The cutoff must be a past ISO 8601 UTC timestamp ending in `Z`, and each batch is limited to 1–1000 rows strictly older than the cutoff. Preview reports at most one batch, not the total eligible count; it is a snapshot and may differ from deletion. Delete locks selected rows with `SKIP LOCKED`, so concurrent batches can skip busy rows and must be repeated to drain a backlog. A zero count does not prove no eligible rows are locked. Every delete invocation, including a zero-row batch, records an audit entry in the same transaction. The operator supplies a nonempty reason of at most 512 bytes. A lost response may follow a committed deletion; repeated invocations delete additional eligible rows, so inspect the audit before retrying. The legacy `delete` path has no request-ID deduplication; use `delete-v2` above when retry recovery is needed. There is no scheduler, automatic vacuum configuration or automatic retention policy.

**A time cutoff is not proof that all WS instances consumed an event.** PostgreSQL `created_at` uses the transaction start time, so an event can commit long after its timestamp; listener backlog, paused hosts and DB locks can also delay lookup. Removing a still-needed row can lose an event or trigger the optional event-gap disconnect. LISTEN/NOTIFY has no replay and this tool does not create it. Before deletion choose a conservative cutoff, inspect transactions and WS health, and arrange client reconnect/Inbox re-fetch. No finite age alone guarantees delivery. Existing direct DB access can bypass this tool and its audit. Removing event rows does not remove notification messages or other delivery history.

It exercises preview, environment and role separation, cutoff, bounded deletion, audit failure rollback, locked-row skipping and permission revocation. It does not test an actual load balancer, stalled live WS listener, real deployment, HA, or recovery from an unknown commit response. On non-macOS set `SWALLOW_TEST_POSTGRES_BIN` appropriately.

The WS process handles SIGTERM and Ctrl-C. Set `SWALLOW_WS_DRAIN_SECONDS` (default 0, 0–300) to allow load-balancer removal: while draining, optional readiness returns 503, existing sockets remain connected, and new Socket.IO namespace registrations are rejected. Engine.IO transport handshakes may still occur during this interval. After it ends the server closes socket transports and waits up to `SWALLOW_WS_SHUTDOWN_GRACE_SECONDS` (default 30, 1–300) for in-flight registrations and tracked disconnect cleanup. It schedules idempotent cleanup for registered sockets as well as callbacks, and a registration overlapping shutdown is cleaned after it resolves. Timeout exits with an error; a DB outage or lost commit response may leave state uncertain. Keep the orchestrator termination budget above drain plus grace and configure load-balancer readiness propagation. A client must reconnect and re-fetch Inbox; Socket.IO event gaps are not replayed. SIGKILL, network partitions and host failures cannot drain. In normal identity mode another WS process can reclaim expired 30-second leases; compatibility-mode and legacy NULL leases are not reclaimed by this path and require separate cleanup. Multiple healthy instances, correct presence policy and independent health monitoring are still required.

The file is read once, at most 16 KiB, with one trailing newline removed. # Experimental Rust Socket.IO service

Set `SWALLOW_INBOX_REQUIRE_JWT_EXP=true` on every WS and API instance to reject subscriber JWTs without a numeric, unexpired `exp` claim. The default `false` preserves the previous admission behavior; other values fail startup. Configure this consistently across instances and restart to change it. This does not cap the token lifetime, revoke individual tokens or add operator authentication. In strict subscriber mode an admitted connection is also checked for expiration periodically and during delivery. In `NOVU_ALLOW_RECREATED_SUBSCRIBER=true` compatibility mode, existing sockets are not periodically disconnected at token expiry; this option only changes admission there. A client must reconnect with a fresh token as needed.

With `NOVU_WS_DISCONNECT_ON_EVENT_GAP=true`, choose `NOVU_WS_EVENT_LOOKUP_RECOVERY=immediate|probe`. The default `immediate` preserves the previous behavior: a failed event lookup disconnects sockets but does not hold new connections closed. In `probe` mode, the instance rejects new sockets and reports `/health/ready` as 503 (if enabled) after an event lookup failure, until an event-table/subscriber lookup probe succeeds. It retries once per second with a two-second timeout; a failure concurrent with an older successful probe cannot be cleared by that probe. Invalid settings and `probe` without the disconnect option fail startup. Each instance manages its own state. The probe adds a DB query once per recovery attempt and can contend with the shared query connection. It checks query availability and permissions, not delivery of the lost event, all count queries, or future events. Missing event rows can clear on the next successful probe; it does not replay them. Clients must explicitly reconnect and resync Inbox after a server disconnect. LISTEN gaps, undetected partitions, failed event writes, ignored socket emit errors, load-balancer behavior and actual SDK resync are not solved by this option. `scripts/test-listener-gap.sh` exercises three Rust processes and Docker PostgreSQL, including a sustained lookup failure and recovery; actual load and a reference-server failure comparison are unverified.

For applications using the Socket.IO SDK, [`sdk/recovery.mjs`](sdk/recovery.mjs) is an optional, dependency-free recovery helper, with TypeScript declarations alongside it. Install it before the SDK connects; call its returned stop function **before** an intentional disconnect, logout, subscriber/session change, or component destruction. It explicitly replaces a disconnected SDK socket and invokes the supplied refresh callback after reconnection. By default it retries at a fixed `retryDelayMs` (1000 ms). Set `backoffFactor` greater than 1, `maxRetryDelayMs` (default 30000 ms or the initial delay if larger), and optional `jitterRatio` (0–1) to increase and randomize retry delays. Jitter is symmetric around the current delay and capped by the maximum; delay resets after successful recovery. `connectTimeoutMs` bounds each helper wait, in addition to the retry delay. These settings do not control the SDK’s own Socket.IO automatic reconnection: configure `socketOptions.reconnection` separately if desired. By default recovery begins after a disconnect. Set `recoverInitialConnection: true` to also report and retry a Socket.IO connection error before the first successful connection. Optionally set `initialConnectTimeoutMs` with `recoverInitialConnection: true` to detect an initial connection that stays pending without an error; it emits an Error with `code` `SWALLOW_SOCKET_INITIAL_TIMEOUT` to `onError` and starts recovery. The timer begins on the SDK `socket.connect.pending` event and is canceled on connect, error, disconnect or stop. Choose a threshold suitable for the network; a slow healthy connection can be replaced. These options require the SDK to attempt a socket connection and do not retry session initialization. The callback must fetch and apply the application's own lists, pages and counts, throw on an SDK `{ error }` result, and honor its `AbortSignal` before applying results. A subsequent disconnect aborts the old callback; a refresh failure is reported and retried. Calling stop aborts the callback and timers but does not close the SDK socket. `onError` receives refresh failures, errors returned directly by SDK connect/disconnect, and asynchronous SDK connection errors while recovering. Initial connection errors are reported only when `recoverInitialConnection` is enabled. Permanent authorization failures require the application to stop recovery or update the session. This helper does not replay events, repair SDK caches, update any UI by itself, guarantee a coherent multi-page snapshot, or prevent stale updates from callbacks that ignore cancellation. It has not been packaged or enabled automatically in the Angular console or other clients.

```js
import { startSocketRecovery } from './recovery.mjs';
const stopRecovery = startSocketRecovery(novu, {
  refresh: async ({ signal }) => {
    const result = await novu.notifications.list({ useCache: false });
    if (result.error) throw result.error;
    if (!signal.aborted) renderNotifications(result.data.notifications);
    // Fetch and apply any other pages and counts the application needs.
  },
  recoverInitialConnection: true, initialConnectTimeoutMs: 10000,
  backoffFactor: 2, maxRetryDelayMs: 30000, jitterRatio: 0.2,
  onError: error => console.error('Inbox recovery failed', error),
});
// Before logout, subscriber change, or intentionally disconnecting: stopRecovery();
```

Limitations: `LISTEN/NOTIFY` is ephemeral and has no replay; the event listener retries its dedicated connection once per second after a failure, but events during the gap can be missed. A closed shared query connection is reconnected lazily by the next operation. Failed disconnect cleanup and cleanup after a failed connection registration are retried in memory with exponential backoff from one to 30 seconds, using token validity at disconnect time. Other failed operations are not retried, and events can be lost while either connection is unavailable. A test-only PostgreSQL protocol proxy drops COMMIT acknowledgements after PostgreSQL has committed, verifying cleanup after a registration and idempotent retry after a disconnect. The tests use disposable local PostgreSQL and do not compare the original WS service under the same faults. Retry tasks are unbounded and are lost if the WS process exits; delayed cleanup can observe a different number of concurrent connections than at disconnect time. The event table accumulates until an operator explicitly runs the optional bounded retention tool described above. Notification fields, severity counts, API mutation events, activity webhooks and the SDK are only partially supported. Strict-mode connections have a 30-second lease, renewed every five seconds. A live instance reclaims up to 32 subscribers' expired leases and 100 expired orphan rows per sweep, then sets presence according to remaining unexpired or unleased connections. A socket whose lease already expired is disconnected rather than renewed. Recovery can lag the expiry during DB outages or backlog; long pauses can disconnect healthy sockets. Pre-migration and compatibility-mode rows have NULL leases and are not reclaimed, so drain old processes and handle their stale rows separately before relying on this policy. Graceful shutdown and the strict-mode cleanup policy are not identical to the original. Only the tested HS256 JWT and string context-key subset is supported; the original JWT library accepts additional algorithms and claim shapes. Browser cross-origin behavior has not been compared. Authentication and connection handling are not yet hardened for production load. Strict mode adds a five-second token-expiry check and a five-second batched identity query per WS instance and a subscriber existence query per delivered event. The registry adds an insert/update transaction on connect and a lock/delete/count/update transaction on disconnect; each emitted event adds a best-effort outbox write and each WS instance reads it and, for matching recipients, queries counts and optionally the message.

For the experimental single-step workflow, `notification_received` includes stored severity, and unread counts include per-severity capped counts excluding snoozed messages. The delivery test runs both workers with a medium default and high trigger override, compares each session count with the reference API and checks SDK and Rust Socket.IO delivery. The original message still reaches the source gateway through manual forwarding; its complete WS worker path and broader severity, context and load combinations are unverified.
