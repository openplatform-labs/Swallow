`JWT_SECRET_FILE` can supply the subscriber JWT secret from a mounted file instead of `JWT_SECRET`; configure exactly one. Invalid, missing, or conflicting sources fail WS startup. The file is read once, at most 16 KiB, with one trailing newline removed. The API and WS must share the same value; permissions, zero-downtime rotation, and external secret managers remain deployment responsibilities.

# Experimental Rust Socket.IO service

This prototype covers Socket.IO connections, presence and a limited in-app event path. It is not a production Novu WS service or a complete SDK-compatible replacement. It uses Socketioxide 0.18.9 (Rust 1.94 or newer), the experimental PostgreSQL API and worker schemas, worker migrations `0030_experimental_ws_events.sql` through `0034_experimental_notifications.sql`, and WS migrations `0001_connections.sql`, `0002_subscriber_revocation.sql` and `0003_connection_leases.sql`. Start it with `DATABASE_URL`, `JWT_SECRET`, and an optional `LISTEN_ADDR` (default `127.0.0.1:3002`). Apply migrations explicitly; the service does not run them itself.

By default, connection registration also requires the token's internal subscriber ID to exist in the token's environment. A deleted or recreated subscriber's old token is disconnected on a new connection. `NOVU_ALLOW_RECREATED_SUBSCRIBER=true` restores the reference gateway's behavior of admitting a signed token even if its subscriber row is missing; the reference comparison uses this compatibility mode. After migration 0002, subscriber deletion sends a post-commit notification to every WS instance, which disconnects matching local sockets. Each strict-mode instance also rechecks connected identities every five seconds to recover missed notifications; delivery checks subscriber existence before emitting an event. A database outage delays rechecking, and deletion can race with a delivery already in progress, so immediate or atomic revocation is not guaranteed. This is not complete revocation or production authentication.

The `/socket.io/` endpoint supports websocket and HTTP polling transports. The default namespace accepts `handshake.auth.token`, falling back to `query.token` using the reference's JavaScript truthiness rules. HS256 subscriber JWTs with the `widget_user` audience are verified, including expiration and not-before. Connections join the subscriber's internal ID room and retain context keys. Presence updates are scoped to environment and internal subscriber ID. A PostgreSQL connection registry lets the tested processes count connections across instances; the reference gateway's observed `remaining connections > 1` behavior on disconnect is preserved. In compatibility mode, as in the reference, an expired JWT at disconnect skips the presence update. In strict mode, a five-second independent check disconnects expired tokens, event delivery rejects expired tokens, and disconnect cleanup updates presence even after expiry. Tokens without an expiration remain accepted; revocation is not instantaneous, and database failures can delay presence cleanup.

The [comparison script](scripts/test-reference-gateway.sh) runs the checked-out reference `WSGateway` and `SubscriberOnlineService` source with a real Socket.IO server and client, but stubs the original subscriber repository, Nest dependency injection, and New Relic. Rust uses disposable Docker PostgreSQL; the reference uses an in-memory subscriber. It compares valid and invalid JWTs, auth/query precedence, websocket and polling, other-environment isolation, two/three socket presence and context-filtered events. Separate Rust-only strict-mode tests kill one WS process, accelerate lease expiry, verify another live connection remains online and confirm expired sockets and orphan rows are reclaimed; they also check token expiry during a PostgreSQL outage, deletion rollback, cross-instance disconnect, deleted/recreated and cross-environment identities, missed notifications, and suppression of events for a deleted identity. Another Rust-only check uses two WS processes sharing PostgreSQL, forcibly terminates their event listener and query connections, restarts the disposable PostgreSQL server, and verifies subsequent fan-out to already-connected sockets and new socket presence. This harness does not run the actual original WS application, MongoDB or Redis adapter.

The in-app worker records a `notification_received` event in PostgreSQL in the same transaction as each newly created message and automatic unsnooze. Every WS instance listens for event IDs, reads the event, filters local sockets by environment and exact context, and emits a limited message DTO followed by unseen and unread counts. [The delivery test](tests/worker_delivery.cjs) triggers both real workers, forwards the original worker's stored message through the original gateway, and compares selected raw message fields; it also connects the reference-built `@novu/js` SDK to each server using that server’s own session, compares selected SDK notification fields, and checks an accelerated Rust unsnooze. Generated IDs and timestamps are validated for format and normalized for comparison. The original message is forwarded manually through the gateway; original WS worker dispatch and complete message DTOs are not compared. The Rust raw event includes the stored organization and configured workflow ID, empty context and device tokens, and the prototype in-app provider `novu`; new messages include their notification ID; job/step-template IDs and updated timestamps are not implemented. Earlier messages are not backfilled. Nested values, empty objects and arrays in payloads are compared against messages from the original worker, both in PostgreSQL and over Rust Socket.IO. The API rejects triggers containing attachments with 501, so attachment delivery is not compared end to end. Older stored prototype messages are normalized for Socket.IO and Inbox payload-as-data responses when read; their stored rows are not migrated. The reference comparison covers a REGULAR workflow, legacy rows, read responses and explicit data precedence. Run the API's disposable reference runner with `NOVU_TEST_WS_DELIVERY=1`, `NOVU_TEST_PREFERENCE_DELIVERY=1` and `NOVU_TEST_MONGO_REPLICA=1` to execute this test; `NOVU_TEST_SNOOZE_ONLY=1` skips unrelated comparisons.

Selected Inbox reads, archives, snoozes, unsnoozes and deletes enqueue an unread-count refresh; seen operations enqueue an unseen-count refresh. `0031_experimental_ws_best_effort.sql` makes event insertion best effort, matching the original WS queue's failure policy: a failed event write does not roll back the underlying mutation or worker delivery. The delivery test compares event types in the original Redis queue and exercises resulting count events through both Rust Socket.IO and the reference-built SDK, including a context-specific JWT.

Limitations: `LISTEN/NOTIFY` is ephemeral and has no replay; the event listener retries its dedicated connection once per second after a failure, but events during the gap can be missed. A closed shared query connection is reconnected lazily by the next operation. Failed disconnect cleanup and cleanup after a failed connection registration are retried in memory with exponential backoff from one to 30 seconds, using token validity at disconnect time. Other failed operations are not retried, and events can be lost while either connection is unavailable. A test-only PostgreSQL protocol proxy drops COMMIT acknowledgements after PostgreSQL has committed, verifying cleanup after a registration and idempotent retry after a disconnect. The tests use disposable local PostgreSQL and do not compare the original WS service under the same faults. Retry tasks are unbounded and are lost if the WS process exits; delayed cleanup can observe a different number of concurrent connections than at disconnect time. The event table has no retention policy, so rows accumulate. Notification fields, severity counts, API mutation events, activity webhooks and the SDK are only partially supported. Strict-mode connections have a 30-second lease, renewed every five seconds. A live instance reclaims up to 32 subscribers' expired leases and 100 expired orphan rows per sweep, then sets presence according to remaining unexpired or unleased connections. A socket whose lease already expired is disconnected rather than renewed. Recovery can lag the expiry during DB outages or backlog; long pauses can disconnect healthy sockets. Pre-migration and compatibility-mode rows have NULL leases and are not reclaimed, so drain old processes and handle their stale rows separately before relying on this policy. Graceful shutdown and the strict-mode cleanup policy are not identical to the original. Only the tested HS256 JWT and string context-key subset is supported; the original JWT library accepts additional algorithms and claim shapes. Browser cross-origin behavior has not been compared. Authentication and connection handling are not yet hardened for production load. Strict mode adds a five-second token-expiry check and a five-second batched identity query per WS instance and a subscriber existence query per delivered event. The registry adds an insert/update transaction on connect and a lock/delete/count/update transaction on disconnect; each emitted event adds a best-effort outbox write and each WS instance reads it and, for matching recipients, queries counts and optionally the message.

For the experimental single-step workflow, `notification_received` includes stored severity, and unread counts include per-severity capped counts excluding snoozed messages. The delivery test runs both workers with a medium default and high trigger override, compares each session count with the reference API and checks SDK and Rust Socket.IO delivery. The original message still reaches the source gateway through manual forwarding; its complete WS worker path and broader severity, context and load combinations are unverified. Four bounded severity count subqueries are added per recalculation and may scan separately.
