# Experimental Rust Socket.IO service

This prototype covers Socket.IO connections, presence and a limited in-app event path. It is not a production Novu WS service or a complete SDK-compatible replacement. It uses Socketioxide 0.18.9 (Rust 1.94 or newer), the experimental PostgreSQL API and worker schemas, worker migrations `0030_experimental_ws_events.sql`, `0031_experimental_ws_best_effort.sql` and `0032_experimental_message_severity.sql`, and `migrations/0001_connections.sql`. Start it with `DATABASE_URL`, `JWT_SECRET`, and an optional `LISTEN_ADDR` (default `127.0.0.1:3002`). Apply migrations explicitly; the service does not run them itself.

The `/socket.io/` endpoint supports websocket and HTTP polling transports. The default namespace accepts `handshake.auth.token`, falling back to `query.token` using the reference's JavaScript truthiness rules. HS256 subscriber JWTs with the `widget_user` audience are verified, including expiration and not-before. Connections join the subscriber's internal ID room and retain context keys. Presence updates are scoped to environment and internal subscriber ID. A PostgreSQL connection registry lets the tested processes count connections across instances; the reference gateway's observed `remaining connections > 1` behavior on disconnect is preserved. As in the reference, if the JWT has expired by disconnect time, presence is not updated, although the experimental registry entry is removed.

The [comparison script](scripts/test-reference-gateway.sh) runs the checked-out reference `WSGateway` and `SubscriberOnlineService` source with a real Socket.IO server and client, but stubs the original subscriber repository, Nest dependency injection, and New Relic. Rust uses disposable Docker PostgreSQL; the reference uses an in-memory subscriber. It compares valid and invalid JWTs, auth/query precedence, websocket and polling, other-environment isolation, two/three socket presence and context-filtered events. A separate Rust-only check uses two WS processes sharing PostgreSQL, forcibly terminates their event listener and query connections, restarts the disposable PostgreSQL server, and verifies subsequent fan-out to already-connected sockets and new socket presence. This harness does not run the actual original WS application, MongoDB or Redis adapter.

The in-app worker records a `notification_received` event in PostgreSQL in the same transaction as each newly created message and automatic unsnooze. Every WS instance listens for event IDs, reads the event, filters local sockets by environment and exact context, and emits a limited message DTO followed by unseen and unread counts. [The delivery test](tests/worker_delivery.cjs) triggers both real workers, forwards the original worker's stored message through the original gateway, and compares selected raw message fields; it also connects the reference-built `@novu/js` SDK to each server using that server’s own session, compares selected SDK notification fields, and checks an accelerated Rust unsnooze. Generated IDs and timestamps are validated for format and normalized for comparison. The original message is forwarded manually through the gateway; original WS worker dispatch and complete message DTOs are not compared. The Rust raw event includes the stored organization and configured workflow ID, empty context and device tokens, and the prototype in-app provider `novu`; notification/job/step-template IDs and updated timestamps are not implemented. Nested values, empty objects and arrays in payloads are compared against messages from the original worker, both in PostgreSQL and over Rust Socket.IO. The API rejects triggers containing attachments with 501, so attachment delivery is not compared end to end. Older stored prototype messages are normalized for Socket.IO and Inbox payload-as-data responses when read; their stored rows are not migrated. The reference comparison covers a REGULAR workflow, legacy rows, read responses and explicit data precedence. Run the API's disposable reference runner with `NOVU_TEST_WS_DELIVERY=1`, `NOVU_TEST_PREFERENCE_DELIVERY=1` and `NOVU_TEST_MONGO_REPLICA=1` to execute this test; `NOVU_TEST_SNOOZE_ONLY=1` skips unrelated comparisons.

Selected Inbox reads, archives, snoozes, unsnoozes and deletes enqueue an unread-count refresh; seen operations enqueue an unseen-count refresh. `0031_experimental_ws_best_effort.sql` makes event insertion best effort, matching the original WS queue's failure policy: a failed event write does not roll back the underlying mutation or worker delivery. The delivery test compares event types in the original Redis queue and exercises resulting count events through both Rust Socket.IO and the reference-built SDK, including a context-specific JWT.

```sh
NOVU_REFERENCE_SOURCE=/absolute/path/to/reference ./scripts/test-reference-gateway.sh
```

Limitations: `LISTEN/NOTIFY` is ephemeral and has no replay; the event listener retries its dedicated connection once per second after a failure, but events during the gap can be missed. A closed shared query connection is reconnected lazily by the next operation. Failed disconnect cleanup and cleanup after a failed connection registration are retried in memory with exponential backoff from one to 30 seconds, using token validity at disconnect time. Other failed operations are not retried, and events can be lost while either connection is unavailable. A test-only PostgreSQL protocol proxy drops COMMIT acknowledgements after PostgreSQL has committed, verifying cleanup after a registration and idempotent retry after a disconnect. The tests use disposable local PostgreSQL and do not compare the original WS service under the same faults. Retry tasks are unbounded and are lost if the WS process exits; delayed cleanup can observe a different number of concurrent connections than at disconnect time. The event table has no retention policy, so rows accumulate. Notification fields, severity counts, API mutation events, activity webhooks and the SDK are only partially supported. No connection lease or crash cleanup exists, so stale rows can leave presence incorrect after process failure; graceful shutdown is not equivalent to the original. Only the tested HS256 JWT and string context-key subset is supported; the original JWT library accepts additional algorithms and claim shapes. Browser cross-origin behavior has not been compared. Authentication and connection handling are not yet hardened for production load. The registry adds an insert/update transaction on connect and a lock/delete/count/update transaction on disconnect; each emitted event adds a best-effort outbox write and each WS instance reads it and, for matching recipients, queries counts and optionally the message.

For the experimental single-step workflow, `notification_received` includes stored severity, and unread counts include per-severity capped counts excluding snoozed messages. The delivery test runs both workers with a medium default and high trigger override, compares each session count with the reference API and checks SDK and Rust Socket.IO delivery. The original message still reaches the source gateway through manual forwarding; its complete WS worker path and broader severity, context and load combinations are unverified. Four bounded severity count subqueries are added per recalculation and may scan separately.
